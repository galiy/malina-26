# kes-emu — эмулятор КЭС (MPPT)

Программный эмулятор солнечного контроллера **КЭС (MPPT, Микроарт)** для разработки и
тестов `kes-reader` **без железа**. Один процесс обслуживает **несколько виртуальных КЭС**,
каждый — на своём последовательном порту; реализует **штатный протокол MicroArt** и
регистровую карту КЭС.

Документ — **предлагаемая архитектура** (реализацию не начинаем). Связано:
`docs/kes-reader.md` (§5 «Эмулятор»), `docs/kes-memory.md` (карта регистров/настроек),
`docs/legacy/kes-legacy-malina2.md` (разбор legacy), `docs/map-reader.md` (образец демона).

## 0. В деплой НЕ входит

- `kes-emu` **не включается** в целевой образ и в штатный деплой (`deploy/`, `stage2.sh`,
  автозапуск) — это **только инструмент разработки/тестов**.
- Собирается и ставится **вручную на конкретный хост при необходимости** (напр. на `.60`
  для e2e). Никаких systemd-юнитов в тираже, никаких записей в `deploy/manifest.tsv`.
- Временная установка на тестовом хосте — по правилам проекта (локальный деплой,
  потом прибираем за собой).

> Ранее в документации эмулятор назывался `kes-sim` — переименовываем в **`kes-emu`**
> (каталог `daemons/kes-emu`). Эмулируемое устройство по имени — тоже КЭС; имена приведём
> к `kes-emu`/`kes-reader` во всех доках.

## 1. Роль и границы

- **Роль:** вести себя как реальный КЭС по MicroArt-протоколу (искать/принимать кадры
  чтения/записи, отвечать корректно и с реальными таймингами на «живых» значениях).
- **Для кого:** `kes-reader` (опрос/публикация), менеджер событий, панели — но эмулятор
  ничего не публикует и не ходит в сеть; это «устройство на проводе».
- **Не production:** только dev/test; в целевой образ не входит.

## 2. Топология портов

Основной путь — **USB-serial gadget на самом устройстве** (`.60`), без сети/usbip:

```
kes-emu ──write──▶ /dev/ttyGSn  (gadget-CDC-ACM, сторона устройства)
kes-reader ──read─▶ /dev/ttyACMx (host-сторона, реальный ttyACM)
```

- `dummy_hcd` + `g_serial` (`g_serial`/`acm`) дают пары `ttyGSn ↔ ttyACMx`.
- **Старт — 3 КЭС** (`ttyGS0/ttyGS1/ttyGS2`), конфигурируемо.
- Скан `kes-reader` включает `/dev/ttyACM*` (host-стороны), gadget-сторону (`ttyGS*`) — нет.
- Резервный путь (без ядра): `socat` PTY-пара (`/dev/ttyKESa ↔ /dev/ttyKESb`); протокол
  проверяется полностью, но без USB-слоя.

Каждый «порт» = один независимый экземпляр виртуального КЭС (свой UID, модель, состояние,
настройки, сценарий).

## 3. Архитектура процесса (Go)

Один бинарник `kes-emu`, внутри — N экземпляров устройств:

```
main
 ├─ config            # YAML/JSON: порты, модели, UID, сценарий, seed
 ├─ transport/port    # open tty, termios (8N1, baud), RS232; чтение/запись байт
 ├─ proto/microart    # кадры r/w: P, A1A0, esc(0xDB 0xDC/0xDD), CRC=sum mod256, '\n', эхо
 ├─ device/kes        # модель устройства: RAM/EEPROM, UID, Mode, реле, ошибки, версия
 ├─ scenario          # драйвер «живых» значений (солнце/ветер, случайность, файл-сценарий)
 ├─ control           # unix-сокет: инъекции, смена сценария, set/get регистров, drop/reconnect
 └─ runner            # на каждый порт: цикл «байт→кадр→ответ», единый такт времени
```

Общий код с `kes-reader`/`map-reader` (пакет **`microart`**: сборка/разбор кадров,
эскейп, CRC, эхо) — **переиспользуем**, не дублируем (рефакторинг — `docs/kes-reader.md` §3).

### 3.1. Транспорт
- Открытие tty, `termios`: 8N1, без чётности, 1 стоп-бит; скорости КЭС — как МАП
  (`19200` дефолт, `57600`, `115200`).
- Байтовый ввод: сборка посылки до `\n`, эхо каждого принятого байта, снятие экранирования,
  проверка CRC. Ответ — тем же форматом (`o`/`e` + данные + CRC + `\n`), тоже с эскайпом.
- Тайминги: реакция «как устройство» (не мгновенно); пауза между байтами > 5 с — разрыв.

### 3.2. Модель устройства (`device/kes`)
- **Регистры:** RAM-измерения и EEPROM-настройки — по `docs/kes-memory.md`.
  Внутреннее хранилище — плоский буфер с «RAM-адресами» (как в карте); при чтении адрес
  устройства `A` → байт по `RAM = A - 0x1F0` для RAM-окон (правило `+0x1F0`), ID-окно
  (`0x0000..`) — как есть.
- **Идентификация:** `_Device (0x0000) = 5`; версия ПО (для FW ≥ 6.3 — UID/реле), модель
  (`200/100`, `250/60`, `200/60`) влияет на пределы тока/мощности в значениях.
- **UID/серийник:** `UID` (RAM `0x2C9`, 16 бит LE; `0` → `idx+1`) и ID-окно `0x18/0x19/0x23`.
- **Mode/Sign/MPP/windspeed:** отдаются из модели (`0x2C2/0x379/0x37A/0x3F8`).
- **Реле:** `Relay_C (0x3E3)` — состояние (биты 0/1/2); приём команды записи (legacy-ячейка
  `0x0E3D` — **конфигурируемо**, до подтверждения на железе) обновляет `Relay_C`.
- **Редж. запись:** по протоколу — сначала байт `3` (`ComMAP_EEPromWR`) в адрес 0, затем
  байт(ы) данных по адресу «как есть»; изменения живут в памяти процесса (reload по команде).
- **Ошибки:** `RSErrSis (0x3B6)` / `I2C_Err (0xD5A)` — по инъекции/сценарию (для проверки
  менеджера событий и `kes-reader`).

### 3.3. Сценарий значений (`scenario`)
- Профиль источника: **солнце** (Vc_PV/Ic_PV по времени суток), **ветер** (windspeed +
  мощность), стационарный/ручной.
- Значения согласованы: `P_PV ≈ Vc_PV·Ic_PV`, `P_curr/I_Ch` — заряд, `Pwr_W/Pwr_kW` —
  суточные счётчики (интегрируются), `Temp_*` — медленно дрейфуют.
- Источники: встроенный генератор (с `seed` для детерминизма), файл-сценарий (таймсерия),
  ручное управление через `control`.

### 3.4. Управление (`control`, unix-сокет)
Локальный JSON-API (по образцу `map-reader` control), команды:
`ping`, `list`, `get <port> <cell>`, `set <port> <cell> <val>`, `scenario <port> <name|file>`,
`inject-error <port> <code>`, `drop <port>` / `reconnect <port>`, `relay <port> <n> <on|off>`.

## 4. Конфигурация (пример)

```yaml
device: kes-emu
ports:
  - path: /dev/ttyGS0     # gadget-сторона; kes-reader читает /dev/ttyACM0
    baud: 19200
    model: "200/100"
    uid: 9191
    scenario: sun_day
  - path: /dev/ttyGS1
    baud: 19200
    model: "250/60"
    uid: 0                # → idx+1
    scenario: sun_fixed
  - path: /dev/ttyGS2
    baud: 19200
    model: "200/60"
    uid: 1234
    scenario: wind
seed: 42
```

## 5. Запуск и systemd

- CLI: `kes-emu -config /etc/malina/kes-emu.yaml [-ports N] [-v]`.
- **Только dev/test:** в целевой образ и штатный деплой не входит (см. §0). Для e2e
  ставится **вручную на конкретный хост** (напр. `.60`); systemd-юнит — ad hoc, в репозитории
  деплоя не фиксируется.
- Подготовка gadget: `modprobe dummy_hcd`, `g_serial`/`acm`, права на `ttyGS*`.

## 6. Резервный режим (PTY)

`socat -d -d pty,raw,echo=0,link=/dev/ttyKESa pty,raw,echo=0,link=/dev/ttyKESb`:
`kes-emu` пишет в `ttyKESb`, `kes-reader` читает `ttyKESa`. Полностью проверяет протокол и
тайминги; не покрывает USB-слой (дискавери `ttyACM*`/udev).

## 7. Тесты

- **unit:** кадры/эскейп/CRC/эхо; маппинг адресов (`+0x1F0`); регистры и дефолты; `UID`/`Mode`.
- **e2e (emu+reader):** детект по `_Device==5` (и что `map-reader` не берёт КЭС), чтение всех
  окон, серийник (`UID`), реле (`Relay_C`), ошибки/события, потеря/возврат порта.

## 8. Связь с `kes-reader`

- `kes-emu` **реализует только сторону устройства** (протокол/регистры). `kes-reader` —
  опрос, публикация в shm/`kes-list`, управление (реле/запись).
- Общий пакет `microart` (кадры/CRC/эскейп) и общий код транспорта — шарить.

## 9. Открытые вопросы

1. Носитель портов: **USB-gadget** (основной) vs PTY (резерв) — что станет рабочим для e2e.
2. Число эмулируемых КЭС (старт — 3; лимит legacy — 4).
3. Формат файла-сценария (таймсерия значений).
4. Подтвердить командную ячейку реле (`0x0E3D`) на реальном железе (см. `docs/kes-reader.md` §7.7).
5. Версии FW для эмуляции (≥ 6.0; для UID/реле — ≥ 6.3).

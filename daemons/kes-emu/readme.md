# kes-emu — эмулятор КЭС (MPPT)

Программный эмулятор солнечного контроллера **КЭС (MPPT, Микроарт)** для разработки и
тестов `kes-reader` **без железа**. Один процесс обслуживает **несколько виртуальных КЭС**,
каждый — на своём последовательном порту; реализует **штатный протокол MicroArt** и
регистровую карту КЭС.

Документ — **предлагаемая архитектура** (реализацию не начинаем). Связано:
`docs/kes-reader.md` (§5 «Эмулятор»), `docs/kes-memory.md` (карта регистров/настроек),
`docs/legacy/kes-legacy-malina2.md` (разбор legacy), `docs/map-reader.md` (образец демона).

## 0. В деплой НЕ входит

- `kes-emu` **не включается** в целевой образ и в штатный деплой (`deploy/`, `stage2.sh`,
  автозапуск) — это **только инструмент разработки/тестов**.
- Собирается и ставится **вручную на конкретный хост при необходимости** (напр. на `.60`
  для e2e). Готовые артефакты постоянного запуска — `scripts/` (systemd-юнит), но они
  ставятся **только вручную** и **не попадают** в целевой образ, `deploy/`, `stage2.sh` и
  `deploy/manifest.tsv`.
- Временная установка на тестовом хосте — по правилам проекта (локальный деплой,
  потом прибираем за собой).

> Ранее в документации эмулятор назывался `kes-sim` — переименовываем в **`kes-emu`**
> (каталог `daemons/kes-emu`). Эмулируемое устройство по имени — тоже КЭС; имена приведём
> к `kes-emu`/`kes-reader` во всех доках.

## 0a. Реализовано (текущий код)

- транспорт: **PTY** (создаёт сам) или готовые tty через `-ports`;
- **полный разбор/сбор кадров Микроарт** (`lib/microart`: `ParseRequestFrame`, `BuildReply`,
  `BuildErrorReply`) с эхо и экранированием;
- **чтение** страниц, **запись** блоков, **команды** (`3` EEPromWR, `6/7/8` — ok, прочие → `e 04`);
- модель КЭС: `_Device=5`, ID-окно (FW `0x63`), **«живые» измерения** (см. §3.3), `UID`, `Mode`;
  **реле**: командная ячейка (`0x0E3D`) обновляет `Relay_C (0x3E3)`;
- **виртуальные устройства в `/dev`**: `/dev/ttyUSB9..11` (симлинки на PTY); при старте
  чистятся «битые» симлинки от прошлого запуска, «живые» не дублируются; при остановке —
  удаляются;
- **без control-сокета** и без CLI-наворотов (см. §3.4/§5).

## 1. Роль и границы

- **Роль:** вести себя как реальный КЭС по MicroArt-протоколу (искать/принимать кадры
  чтения/записи, отвечать корректно и с реальными таймингами на «живых» значениях).
- **Для кого:** `kes-reader` (опрос/публикация), менеджер событий, панели — но эмулятор
  ничего не публикует и не ходит в сеть; это «устройство на проводе».
- **Не production:** только dev/test; в целевой образ не входит.

## 2. Топология портов

Основной путь — **USB-serial gadget на самом устройстве** (`.60`), без сети/usbip:

```
kes-emu ──write──▶ /dev/ttyGSn  (gadget-CDC-ACM, сторона устройства)
kes-reader ──read─▶ /dev/ttyACMx (host-сторона, реальный ttyACM)
```

- `dummy_hcd` + `g_serial` (`g_serial`/`acm`) дают пары `ttyGSn ↔ ttyACMx`.
- **Старт — 3 КЭС** (`ttyGS0/ttyGS1/ttyGS2`), конфигурируемо.
- Скан `kes-reader` включает `/dev/ttyACM*` (host-стороны), gadget-сторону (`ttyGS*`) — нет.
- Резервный путь (без ядра): `socat` PTY-пара (`/dev/ttyUSBa ↔ /dev/ttyUSBb`); протокол
  проверяется полностью, но без USB-слоя.

Каждый «порт» = один независимый экземпляр виртуального КЭС (свой UID, модель, состояние,
настройки, сценарий).

## 3. Архитектура процесса (Go)

Один бинарник `kes-emu`, внутри — N экземпляров устройств:

```
main
 ├─ config            # YAML/JSON: порты, модели, UID, сценарий, seed
 ├─ transport/port    # open tty, termios (8N1, baud), RS232; чтение/запись байт
 ├─ proto/microart    # кадры r/w: P, A1A0, esc(0xDB 0xDC/0xDD), CRC=sum mod256, '\n', эхо
 ├─ device/kes        # модель устройства: RAM/EEPROM, UID, Mode, реле, ошибки, версия
 ├─ scenario          # драйвер «живых» значений (солнце/ветер, случайность, файл-сценарий)
 ├─ control           # unix-сокет: инъекции, смена сценария, set/get регистров, drop/reconnect
 └─ runner            # на каждый порт: цикл «байт→кадр→ответ», единый такт времени
```

Общий код с `kes-reader`/`map-reader` (пакет **`microart`**: сборка/разбор кадров,
эскейп, CRC, эхо) — **переиспользуем**, не дублируем (рефакторинг — `docs/kes-reader.md` §3).

### 3.1. Транспорт
- Открытие tty, `termios`: 8N1, без чётности, 1 стоп-бит; скорости КЭС — как МАП
  (`19200` дефолт, `57600`, `115200`).
- Байтовый ввод: сборка посылки до `\n`, эхо каждого принятого байта, снятие экранирования,
  проверка CRC. Ответ — тем же форматом (`o`/`e` + данные + CRC + `\n`), тоже с эскайпом.
- **Эхо ответа от клиента обрабатывается побайтовой сверкой** с последним отправленным
  ответом: байт совпал → это эхо (игнорируем), иначе — новый запрос. Так корректно
  работают и клиенты, которые НЕ эхуют ответы устройства (legacy `mpptd`), без «залипания».
- Тайминги: реакция «как устройство» (не мгновенно); пауза между байтами > 5 с — разрыв.

### 3.2. Модель устройства (`device/kes`)
- **Регистры:** RAM-измерения и EEPROM-настройки — по `docs/kes-memory.md`.
  Внутреннее хранилище — плоский буфер с «RAM-адресами» (как в карте); при чтении адрес
  устройства `A` → байт по `RAM = A - 0x1F0` для RAM-окон (правило `+0x1F0`), ID-окно
  (`0x0000..`) — как есть.
- **Идентификация:** `_Device (0x0000) = 5`; версия ПО (для FW ≥ 6.3 — UID/реле), модель
  (`200/100`, `250/60`, `200/60`) влияет на пределы тока/мощности в значениях.
- **UID/серийник:** `UID` (RAM `0x2C9`, 16 бит LE; `0` → `idx+1`) и ID-окно `0x18/0x19/0x23`.
- **Mode/Sign/MPP/windspeed:** отдаются из модели (`0x2C2/0x379/0x37A/0x3F8`).
- **Реле:** `Relay_C (0x3E3)` — состояние (биты 0/1/2); приём команды записи (legacy-ячейка
  `0x0E3D` — **конфигурируемо**, до подтверждения на железе) обновляет `Relay_C`.
- **Редж. запись:** по протоколу — сначала байт `3` (`ComMAP_EEPromWR`) в адрес 0, затем
  байт(ы) данных по адресу «как есть»; изменения живут в памяти процесса (reload по команде).
- **Ошибки:** `RSErrSis (0x3B6)` / `I2C_Err (0xD5A)` — по инъекции/сценарию (для проверки
  менеджера событий и `kes-reader`).

### 3.3. Требования к модели (СОГЛАСОВАНО) и реализация

Эмулятор **«живой»** (значения меняются во времени), всегда день, только солнце,
масштаб времени 1 c = 1 c, без неисправностей.

**Модель:** КЭС **200/100** — Uпанелей ≤ 200 В (типично **110…160 В**), Iзаряда АКБ
≤ **100 А**. АКБ **48 В**: 46…57.6 В, рабочее ~**51.2…54.4 В** (до отсечек не доводим).
`Ic_PV` получается из закона Ома: `P = V·I` → `I_PV = I_АКБ · V_АКБ / V_PV` (т.к. `V_АКБ < V_PV`,
ток панелей ниже тока АКБ).

**Поведение (реализовано в `device.go`):**
- День: `day = 0.5−0.5·cos(2π(t−0.25))`, **ночью не ниже 20 %**; облачность — медленный
  дрейф множителя **±10 %**; итог `sun = day·cloud`.
- **Поиск МППТ («S»)**: раз в **2–5 мин**, длительность **15 с**, выработка **плавно
  падает до 15 %** и возвращается; в это время `Mode='S'`, падают `I_Ch/Vc_PV/P_*`; иначе `Mode='A'`.
- **АКБ**: плавный дрейф; при избытке (`I_Ch` высокий) — растёт, при недостатке — падает
  (слабая возвратность к `~52.8 В`), clamp `48…56.5 В`.
- **Температуры**: `Temp_Bat = 20…32 °C`, `Temp_Int = 20…65 °C`, тем больше, чем больше ток
  (медленный дрейф); кодируются как `x−50`.
- **Мощности/токи**: `P_curr = V_АКБ·I_Ch`, `P_Out = 0.98·P_curr`, `P_PV = V_PV·I_PV`,
  `I_Out = I_Ch`. **`P_Load = 0`** (КЭС только отдаёт в АКБ, не потребляет).
- **ВДТ** (`Sign_C*`, `I_EXTS*`, `P_EXTS*`) — **нули**; `windspeed = 0xFFFF` (н/д).
- **Энергия** `Pwr_W/Pwr_kW` — монотонно растут (условный счётчик; точность не важна).

**Не в модели:** ветер, ночная тьма «в ноль» (минимум 20 %), неисправности/аварии,
произвольная ручная правка измерений (только реле/команды снаружи).

### 3.4. Управление — БЕЗ сокета
Сокет/CLI-команды не нужны: эмулятор — это «устройство на проводе». Всё задаётся ключами
запуска (`-ports`, `-baud`), прочие параметры — константы в коде (FW, UID, командная ячейка
реле). Управлять состоянием можно **штатно** — записью/командами по serial (как реальный КЭС).

## 4. Конфигурация (пример)

```yaml
device: kes-emu
ports:
  - path: /dev/ttyGS0     # gadget-сторона; kes-reader читает /dev/ttyACM0
    baud: 19200
    model: "200/100"
    uid: 9191
    scenario: sun_day
  - path: /dev/ttyGS1
    baud: 19200
    model: "250/60"
    uid: 0                # → idx+1
    scenario: sun_fixed
  - path: /dev/ttyGS2
    baud: 19200
    model: "200/60"
    uid: 1234
    scenario: wind
seed: 42
```

## 5. Запуск

- **Параметры:** `kes-emu [-n 3] [-baud 19200] [-store <каталог>] [-dir /dev]
  [-prefix ttyUSB] [-start 9]`.
  - `-n` — число виртуальных КЭС (по умолчанию `3`);
  - `-baud` — скорость порта, бит/с (по умолчанию `19200`);
  - `-store` — каталог карты памяти `kes-emu.json` (по умолчанию `/malina`, иначе `/settings`,
    иначе `/tmp`);
  - `-dir`/`-prefix`/`-start` — каталог и имена симлинков устройств (по умолчанию `/dev`, `ttyUSB`, старт с `9` → `/dev/ttyUSB9..`).
  Остальное — константы (`FW 0x63`, командная ячейка реле `0x0E3D`, база UID).
- Создаёт **N PTY** и **симлинки-устройства в `/dev`**: `/dev/ttyUSB9..` (их видят
  `kes-reader` через шаблон `/dev/ttyUSB*` и `MAP2Gui` под Wine). Нужны права на запись в
  `/dev` (на `.60` — через `sudo`).
- При старте «битые» симлинки от прошлого запуска удаляются; «живые» (эмулятор уже
  запущен) не дублируются; при остановке симлинки убираются.
- **Постоянный запуск (systemd):** `scripts/` — `install.sh`/`uninstall.sh` и шаблон
  `kes-emu.service.in`; размещение бинарника — `/malina` (`.60`), `/settings` (`.68`),
  `/opt/kes-emu` (прочие); параметры — 3 КЭС, 19200 (см. `scripts/README.md`).
- Подготовка gadget: `modprobe dummy_hcd`, `g_serial`/`acm`, права на `ttyGS*`.

## 6. Резервный режим (PTY)

`socat -d -d pty,raw,echo=0,link=/dev/ttyUSBa pty,raw,echo=0,link=/dev/ttyUSBb`:
`kes-emu` пишет в `ttyUSBa`, `kes-reader` читает `ttyUSBb`. Полностью проверяет протокол и
тайминги; не покрывает USB-слой (дискавери `ttyACM*`/udev).

## 7. Тесты

- **unit (есть):** `lib/microart` — round-trip кадров (`BuildReadRequest`↔`ParseRequestFrame`,
  `BuildReply/BuildErrorReply`↔`ParseReply`), экранирование, CRC; `kes-emu` — чтение
  `_Device`/UID по адресу `+0x1F0`, команда `EEPromWR`, запись реле в командную ячейку,
  неверная команда.
- **e2e (план):** `kes-reader` ↔ `kes-emu` (детект `_Device==5`, окна, UID, реле).

## 8. Связь с `kes-reader`

- `kes-emu` **реализует только сторону устройства** (протокол/регистры). `kes-reader` —
  опрос, публикация в shm/`kes-list`, управление (реле/запись).
- Общий пакет `microart` (кадры/CRC/эскейп) и общий код транспорта — шарить.

## 9. Открытые вопросы

1. Носитель портов: **PTY по умолчанию** (для `kes-reader`/локально) vs **USB-gadget** для
   `MAP2Gui` под Wine — выбрать/совместить.
2. Число эмулируемых КЭС (старт — 3; лимит legacy — 4).
3. Подтвердить командную ячейку реле (`0x0E3D`) на реальном железе (см. `docs/kes-reader.md` §7.7).
4. Версии FW для эмуляции (≥ 6.0; для UID/реле — ≥ 6.3).

## 10. Персистентность (`kes-emu.json`)

Хранилище: если есть `/malina` — там, иначе `/settings`, иначе `/tmp`; файл **`kes-emu.json`**
(коллекция объектов). Объект: `serial` + `mem`.

- `mem` — **вся карта памяти HEX-строкой**, `0x400 + 2048 = 3072` байта = 6144 hex-символа
  (верхний регистр, по 2 символа на байт). Раскладка: `EEPROM 0x000…0x3FF`, затем
  `RAM 0x000…0x7FF` (смещение `0x400+r`). Позиция в строке = байт памяти.
- Константы (`0x00`, подтверждённые `0x01,0x02,0x05,0x0C,0x0D`, серийник `0x2C9/0x2CA`)
  в файле не хранятся (их позиции — `00`), при старте накладываются поверх карты.
- Реле живёт в карте: состояние — RAM-ячейка `0x3E3` (смещение `0x7E3`);
  командная ячейка `0x0E3D` не хранится и не читается.

- Запуск: `kes-emu -n <портов>` → ищет файл; если нет — создаёт. Читает существующие объекты,
  **сначала карту памяти, затем константы**, и инициализирует эмуляторы; если объектов меньше
  `n` — **добавляет новые (серийник генерится только здесь)**, файл дописывается.
- **Запись запрещена** (ответ кадра `e`, код `0x20`) для адреса `0`, подтверждённых EEPROM и любой RAM.
  Исключение — **команда реле** (`0x0E3D`): разрешена, обновляет состояние в RAM-ячейке `0x3E3`
  и сохраняет состояние (`0x3E3`) в карту файла.
- **Все остальные ячейки EEPROM** — запись разрешена: пишем в память процесса и в файл.
- **Чтение всегда из памяти процесса.**

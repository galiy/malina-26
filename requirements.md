# Требования (план развития)

Зафиксированные требования на будущее. Не являются описанием текущего состояния.

## 1. Роль устройства

Устройство работает как сетевой шлюз/логгер (по аналогии с TCP-шлюзами,
логгерами и т.п.).

## 2. Сеть: режимы (финально)

Реализуются **два фиксированных режима** (выбор вручную в админке).
Режим «AP+STA (репитер)» — **не реализуем**.

### 2.1. Режим 1 — «Точка доступа (AP)»
- wlan0 — AP (`hostapd`); `dnsmasq` раздаёт DHCP AP-клиентам
  (подсеть/пул настраиваемые; адрес устройства по умолчанию `10.10.100.254`).
- eth0 активен: DHCP (`dhclient`) или static (IP/маска/шлюз/DNS).
- Тумблер **«Интернет-транзит (NAT через Ethernet)»** (**по умолчанию — вкл**):
  - вкл → `ip_forward=1` + masquerade wlan→eth;
  - выкл → `ip_forward=0`, без NAT (сети изолированы).
- `country=US` (2.4 ГГц, каналы 1–11).

### 2.2. Режим 2 — «Wi-Fi клиент (STA)»
- wlan0 — клиент (`wpa_supplicant`): скан сетей, выбор целевой сети, IP
  (DHCP/static) на wlan0; это **внешний аплинк**.
- eth0 — **НАШ** сегмент: статический адрес из конфига (по умолчанию
  `10.10.100.0/24`, устройство `10.10.100.254`), `dnsmasq` раздаёт адреса, NAT
  eth→wlan. eth0 **никогда не становится клиентом внешней сети**.
- Наличие чужого DHCP на eth0 **выключает только нашу раздачу**; конфигурация
  eth0 (IP/подсеть/NAT) не меняется.
- Без бриджа (см. 2.3).

### 2.3. Прозрачный мост — невозможен
- Проверено на .60: `iw dev wlan0 set 4addr on` → `Operation not supported (-95)`.
  Wi-Fi↔Ethernet только через маршрутизацию/NAT. IP — на интерфейсах, не на мосту.

### 2.4. Хранение настроек
- Настройки **всех** режимов хранятся в `/malina/etc/malina/network/` и при
  переключении **не теряются**; применяется только активный режим.
- На `ro`-корень ничего не пишется; `sysctl` применяется в рантайме из `/malina`.

### 2.5. Ранний сетевой процесс (не Go-сервис)
- `malina-net.service` — **отдельный ранний** systemd-процесс: читает активный
  режим и конфиги из `/malina` (+ транзиентный override из `/run/malina-net/`),
  поднимает сеть (`hostapd`/`wpa_supplicant`/`dnsmasq`/`dhclient`/`nft`/`sysctl`,
  `iw reg set US`, `rfkill unblock wifi`).
- Порядок: `After=local-fs.target`, `Before=network-pre.target network.target
  multi-user.target`. Сеть поднимается **до** Go-сервиса.
- Go-сервис (админка) **не выполняет сетевые команды**: только пишет конфиги и
  запускает `systemctl restart malina-net.service`; сам стартует
  `After=malina-net.service`.

### 2.6. Фолбэк — см. раздел 7.

### 2.7. Защита от конфликта DHCP (режим 2, eth0)
- Наш DHCP-сервер на eth0 выключается при обнаружении чужого DHCP, но
  **конфигурация eth0 не меняется** (свой статический IP/подсеть/NAT остаются).
- **Активный зонд** (`DHCPDISCOVER`, фильтр по `server-id`, ожидание 15 с) —
  **раз в 2 минуты** (сервис `malina-net-monitor`).
- Чужой найден → только `dhcpOff` (остановить нашу раздачу).
- Повторное включение раздачи — после **≥2 подряд «чистых»** проверок.
- Состояние монитора — `/run/malina-net/monitor.state`.

### 2.8. IPv6
- IPv6 **не поднимаем** (ни на одном интерфейсе).

## 3. Наблюдаемость
- Логи — в tmpfs с жёстким лимитом и ротацией.
- Переключение на удалённый syslog инициируется **самим фактом**
  получения/неполучения DHCP-опции 7, а **не из админки**:
  - опция 7 получена (или изменилась) → форвард логов на удалённый сервер по UDP;
  - опция 7 пропала → возврат к локальным логам в tmpfs.
- Изменение опции обрабатывается только при реальном изменении значения
  (без лишних перезапусков syslog при renew с тем же значением).
- Для режима Ethernet **static** (DHCP-опций нет) — позже добавить
  возможность **ручной** настройки удалённого syslog через админку.

## 4. Сетевой стек (технический выбор)

- **NetworkManager не используется** (усложняет логику AP/STA и не отдаёт
  DHCP-опцию 7).
- **Ethernet:** `dhclient` (ISC, standalone, без NM). DHCP/static; опция 7 — из
  lease/enter-hook. `dhcpcd` отвергнут: на ядре 6.12 падает по SIGSYS
  (встроенная seccomp в DHCP-пути).
- **Wi-Fi STA:** `wpa_supplicant`.
- **Wi-Fi AP:** `hostapd` + `dnsmasq` (DHCP для клиентов AP; при Ethernet-аплинке —
  NAT).
- **Сетевой процесс:** ранний `malina-net.service` (см. 2.5) поднимает сеть по
  активному режиму; Go-сервис только пишет конфиги и запускает
  `systemctl restart malina-net.service`.
- **Админка:** правит конфиги Ethernet/STA/AP; переключение remote-syslog по
  опции 7 — автоматическое (п.3), вручную (для static) — позже.

## 5. Immutable-root: что на `/malina`

Перенесено (структура путей от `/`):
- `/root` → `/malina/root`
- `/home` → `/malina/home`
- `/var/spool/cron/crontabs` → `/malina/var/spool/cron/crontabs`
  (`/var/spool/cron` — симлинк на `/malina/var/spool/cron`; создаётся tmpfiles).
- `/etc/wpa_supplicant` → `/malina/etc/wpa_supplicant` (симлинк).

Не переносим (остаётся как есть / tmpfs):
- `/var/lib/dhcp` (lease dhclient) — tmpfs.
- `/etc/systemd/system`, `/etc/passwd|shadow|group` — пока нет рантайм-управления.
- Логи и `/var/lib/systemd` — tmpfs.
- `/etc/fake-hwclock.data` — **сознательно не переносим**: время до синхронизации
  NTP теряется (на старте логи могут иметь неверные метки).

Bluetooth: `/var/lib/bluetooth` — **tmpfs** (BT нужен; пары теряются при
перезагрузке — приемлемо).

machine-id: PID1 читает его **до** монтирования `/malina`, поэтому держать в
`/malina` нельзя (systemd подставляет transient-tmpfs на `/etc/machine-id`).
Решение: **фиксированный `/etc/machine-id`** в образе (ro) +
symlink `/var/lib/dbus/machine-id` → `/etc/machine-id`.

Время (NTP): `systemd-timesyncd`, серверы `ru.pool.ntp.org`
(`/etc/systemd/timesyncd.conf.d/malina.conf`, `PollIntervalMinSec=16`).
Синхронизация форсируется сразу после получения адреса (хук dhclient), поэтому
после ребута время восстанавливается за секунды (fake-hwclock не используем).

## 6. Web/UI стек

- **Один Go-бинарник**: внешняя статика админки + HTTP API. **Сеть не
  оркестрирует** — только пишет конфиги и триггерит `systemctl restart
  malina-net.service` (см. 2.5).
- **Без TLS** (SSL не нужен).
- Авторизация на бэкенде (login + сессии/куки; не basic-auth).
- Сетевые команды Go-сервис не выполняет (это делает ранний `malina-net.service`);
  Go пишет конфиги в `/malina` и запускает перезапуск сети.
- Кросc-компиляция: `GOARCH=arm GOARM=7`, `CGO_ENABLED=0`; компилятор на
  устройстве не нужен.
- Конфиги/состояние — в `/malina`; логи — в journald/rsyslog.
- Оценка ресурсов (Pi 3, 927 МБ): RSS в простое ~10–25 МБ, диск ~8–15 МБ.

Размещение сервиса на rw-разделе `/malina` (структура от `/`):
```
/malina/etc/malina/                    # конфиги сервиса
/malina/usr/local/bin/                 # бинарник malina-web
/malina/usr/local/libexec/             # malina-pamcheck
/malina/usr/local/share/malina/web/    # статика (templates/static/i18n) — внешняя
/malina/var/lib/malina/                # состояние/данные сервиса
```
Статика **не встраивается в бинарник** (по решению): шаблоны/i18n/картинки — на
`/malina`, правятся без пересборки. Статический контент (PAM-сервис, systemd-юнит) — на ro-корне.

## 7. Фолбэк сети (отдельный systemd job)

- Реализуется **отдельным job**: `malina-net-fallback.timer` + `malina-net-fallback.service`.
- **Условие срабатывания** (проверка по таймеру, раз в минуту), при активном
  **персистентном режиме = 2 (STA)** и одновременно:
  - STA не подключён (нет ассоциации: `iw dev wlan0 link` / `wpa_state` ≠ COMPLETED);
  - eth0 без физического линка (`/sys/class/net/eth0/carrier` = 0);
  - оба условия непрерывно **≥ 10 минут** (в любой момент работы, не только при старте).
- **Действие:** транзиентный переход в режим 1 (AP):
  - записать override `/run/malina-net/mode` (`reason=fallback`, tmpfs),
  - `systemctl restart malina-net.service`.
  - **Персистентные настройки не меняются** → после перезагрузки снова режим 2
    (`/run` очищается).
- **После срабатывания job продолжает работу** — следит за возможностью отката:
  - периодически сканирует эфир на предмет **настроенной целевой точки** STA;
  - периодичность: если скан не мешает AP — каждые **2 мин**; если мешает —
    **10 мин** со **снятием AP** на время скана (с последующим возвратом AP);
  - при появлении целевой сети — попытка подключения; при успехе: снять override,
    `systemctl restart malina-net.service` → возврат к **персистентному** режиму и
    возобновление обычного мониторинга.
- Ручной выбор режима 1 пользователем фолбэк не затрагивает (авто-возврат — только
  для override с `reason=fallback`).
- «Мешает ли скан работе AP» определяется на железе при реализации — от этого
  зависит интервал 2 vs 10 мин.

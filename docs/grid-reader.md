# Grid-reader

Модуль опроса сетевых инверторов.

**Статус:** требования и raw-контракт `grid` v1 согласованы 2026-10-18.
Требования доработки (модель опроса, таймауты, классификация «спит vs не
ответил») согласованы и реализованы 2026-10-19. Изменения — в рабочем дереве
(без пуша и деплоя до отдельного решения по ревью).
Реализация: `daemons/grid-reader`, контракт `grid` v1, web-страница
«Сетевые → Настройки», панель статуса из shm, плашки на главной, таблицы,
графики/сравнение, деплой.
Ревью требований — 3 раунда, реализации — 5 раундов; блокеров и major нет.
Задеплоено на дефолтное устройство 2026-10-18; конфиг сгенерирован из
`../sunReceiver/sunReceiver.json` (приватный `.kilo/grid-reader.json`, в git не
попадает).

## Инверторы и настройки

- Инверторы подключены к локальной сети.
- У каждого инвертора есть:
  1. Имя:
     - задаёт оператор;
     - по умолчанию присваивается IP-адрес;
     - при смене IP-адреса имя не меняется.
  2. IP-адрес и порт.
  3. Тип (Sofar/Deye).
  4. Размещение — выбор из списка размещений.
  5. `logger_sn` — серийный номер даталоггера (u32, идёт в запрос); в JSON — число, в UI — десятичное.
- Заводской серийник инвертора (`inverter_sn`) — ключ устройства — читается с
  самого инвертора после подключения (Deye 0x0003–0x0007; Sofar 0x2000–0x200D,
  func 04) и кэшируется. В настройках он не задаётся.
- `inverter_sn` — **строка**, это имя папки/ряда в tsdb. Если инвертор отдаёт
  число — берётся его десятичное представление, как в `sunReceiver`.
  Ограничение ключа tsdb — до 50 байт, без `/`; по факту длиннее и с `/` не
  бывает, отдельная валидация/санитизация не нужна.
- Полный опрос = блок данных + чтение `inverter_sn`, если он ещё не известен.
  SN читается отдельным запросом (Deye 0x0003–0x0007; Sofar 0x2000–0x200D,
  func 04) и кэшируется в памяти. Пока SN не прочитан, результат **не считается
  успешным**: в shm и tsdb ничего не пишется. Ошибка чтения SN — неудачный опрос
  с общим счётчиком и повтором по общим правилам. После успеха SN кэшируется,
  дальнейшие опросы — только блок данных; после рестарта SN читается заново.
- Аналог serial для сетевого инвертора — его уникальный заводской номер.
  Дубли исключены в принципе.
- Лэйбл инвертора в системе — марка (тип) + заводской номер.
- Это **два разных серийника**: `logger_sn` — SN даталоггера, он включается в
  запрос; `inverter_sn` — заводской номер самого инвертора, он читается из
  регистров и служит ключом в tsdb. Без `logger_sn` внятного ответа не будет.
  Deye подтверждено: при запросе с `logger_sn=0` логгер отдаёт heartbeat с кодом
  0x06 и своим реальным SN в кадре — `logger_sn` можно определять автоматически.
  Для Sofar по документации тоже отвечает при SN=0; на живом в момент замера
  проверить не удалось.
- Период опроса: 10, 20 или 30 секунд — на выбор (настраиваемый).
  Один для всех инверторов, по умолчанию 10 секунд.
- Все настройки хранятся в одном файле; раскладка файлов — по аналогии с
  остальными readers.
- Размещение используется только вебом для группировки; ридер его не читает.

## Сервис

- `grid-reader` — сервис на Go, по аналогии с остальными readers.
- Unit: `malina-grid-reader.service`.
- Конфиг: `/malina/etc/malina/grid-reader.json`.
- Control-сокет: `/run/malina-grid/control.sock`, команда `reload`; команды — как
  у остальных сервисов.
- Настройка `log_level` (`debug|info|warn|error`, по умолчанию `info`) — как у
  остальных readers; меняется по `reload`. Код логируется по уровням.
- `reload` сбрасывает баны и таймеры.
- Если устройство удалено из настроек, оно удаляется, независимо от того, активное
  оно или в бане.
- Настройка «Включить»: по умолчанию при первоначальном деплое выключена.
  Если выключена — сервис активен, но спит; публикует пустой список и пустые
  данные, как остальные сервисы.

## Опрос

- Каждый валидный инвертор опрашивается **своей рабочей горутиной**; общий
  оркестратор только запускает их и перезапускает после длинного бана.
  Период (`poll_period`) общий.
- Инверторы не блокируют друг друга: медленный или молчащий Sofar не задерживает
  остальные. Внутри одного инвертора — не более одного запроса в полёте.
- Если инвертор опрошен быстрее периода — его worker спит до следующего
  периода. Если не уложился — сразу начинает следующий цикл.
- Максимум инверторов — 16 (16 слотов).
- Таймаут TCP-подключения — 1 секунда. Это только connect, не чтение.
- Ожидание первого байта — **Deye — 2 с, Sofar — 14 с**.
- Общий лимит приёма ответа — **Deye — 2 с, Sofar — 20 с** (первый байт
  может прийти на 14-й секунде, кадр нельзя обрезать).
- Соединение: **новое TCP-подключение на каждый запрос** для обоих типов
  (connect → запрос → ответ → close). Постоянных соединений нет.
- Из ответа Sofar берётся последний корректный PDU (Sofar не повторяет serial
  запроса и может присылать несколько кадров, включая нулевой/устаревший);
  окончание ответа — короткая тишина 0,4 с.
- Плохой ответ: однократный повтор выполняется, **кроме чистого `no data`**
  (повторяются неполный/битый PDU, ошибки чтения SN, `dial timeout` при
  живом ARP). **Чистый `no data` не повторяется**: тик пропускается, worker
  сразу ждёт следующий период/backoff; другие инверторы не затронуты.
- **Таймаут полного блока — это плохой ответ**, а не отдельный вид бана.
- **Плохой ответ** (включая таймаут полного блока и connect timeout при живом
  ARP) → мягкий backoff для **обоих типов**: в бан не отправляем; после двух
  промахов подряд — пауза 1 минута и статус «плохой ответ», затем попытки
  продолжаются.
- Неудачи прочих ошибок connect считаются подряд единым счётчиком: 2 неудачи —
  бан на 1 минуту. После бана — одна попытка; пока идут неудачи, попытки
  повторяются **раз в минуту**. 5 неудач — бан на 5 минут; все последующие
  баны — по 5 минут.
- Классификация подключения:
  - `no route to host`, `network is unreachable`, `host is unreachable` — штатное
    «нет солнца, инвертор выключен»; **бан 10 минут**, после него снова 10.
  - connect-таймаут (`i/o timeout`) — после него читаем **netlink-таблицу
    соседей** (`RTM_GETNEIGH`, аналог `ip neigh`; connect уже инициировал ARP):
    - `NUD_REACHABLE` → «в сети, но не ответил» → мягкий backoff (как «плохой
      ответ»);
    - всё остальное (нет записи, `INCOMPLETE`, `FAILED`, `lladdr 00:…`,
      неподтверждённые `STALE`/`DELAY`/`PROBE`) → «спит совсем / нет на L2» →
      **бан 10 минут**. Неоднозначность и ошибка ARP трактуются как «нет сети».
    - повторный резолв не делаем: попытка connect только что была.
  - `connection refused`, `connection reset` и прочие ошибки connect — общий
    счётчик неудач (2 → 1 мин, 5 → 5 мин).
- Счётчики неудач сбрасываются после успеха (успешное подключение и корректный
  полный блок).
- Инверторы доступны не всегда: ночью солнца нет, и они засыпают.

### Debug-лог обмена

При `log_level: "debug"` (или флаге `-debug`) демон пишет подробности каждого
обмена с инвертором:

- `connect` и тайминги подключения/ответа;
- `tx` — полный кадр запроса в hex;
- `rx chunk` — каждый принятый фрагмент и `rx total` — весь ответ в hex;
- `кадр[...]` — control code, serial, SN логгера, длина payload, checksum/valid
  и payload в hex;
- `pdu[...]` — Modbus-функция, смещение, число регистров, CRC (фактическая и
  расчётная), значения регистров;
- `ошибка обмена` / `корректных Modbus-PDU нет` — причина «плохого ответа».

Формат предназначен для разбора проблемных ответов (например, коротких или
битых кадров Sofar). Лог объёмный — включать временно; после диагностики
вернуть `info`. Неудачи в журнале содержат классификацию: `плохой ответ`,
`таймаут`, `нет маршрута`, `ошибка связи`.

## shm и tsdb

- Сервис, как и остальные readers, публикует в shm список инверторов и данные
  телеметрии.
- Stale — инвертор, у которого последний успешный опрос был ранее порога:
  3,5 × max(период, длительность последнего опроса этого инвертора).
- 16 слотов; тип устройства — `grid` (в UI — GRID); ключ устройства — серийник; ряды ведутся
  по каждому устройству (серийнику).
- В shm хранится только телеметрия; настройки (имя, размещение и т.п.) там не
  дублируются.
- Запись списка появляется только после первого полного опроса (данные + SN).
  До этого устройства в shm нет; код 0 не публикуется.
- Запись списка — по аналогии с `map`/`bms`: `ID` (индекс слота), `Gen`,
  `Serial`, `Kind`, `Status`, `LastSeen`, `Addr` (IP:порт для диагностики).
- **Один писатель на слот shm.** Слот `i` пишет только worker инвертора `i`;
  список и телеметрию для него не пишет ни оркестратор, ни другой инвертор.
  `reset`/`clear` выполняются только после остановки и ожидания всех worker.
  Имя и размещение не дублируются — веб берёт их из файла настроек.
- `Kind` и `Status` (код опроса 0–7) живут только в списке shm; поле контракта
  `inverter_status` (0–4) — это состояние самого инвертора.
- Бинарная раскладка shm (фиксированная):
  - запись списка — 160 байт: seqlock 16 Б, `Serial[50]` @16, `Addr[64]` @66,
    `Kind` @130, `Status` @131, резерв @132..135, `Gen` u64 @136, `LastSeen` u64
    @144, резерв @152..159;
  - слот телеметрии — 64 байта: payload контракта 50 Б (presence 3 + значения 47),
    затем `energy_today` u16, `energy_total` u24, резерв до 64.
- Инверторы offline/в бане остаются в списке shm (они есть в настройках).
  В raw для них нет строк, поэтому аккумулятор не создаёт точку avg.
- В списке shm есть явный статус-код:

| Код | Статус |
|---|---|
| 0 | зарезервирован (до первого полного опроса в shm не публикуется) |
| 1 | OK |
| 2 | stale (последний успех ранее 3,5 × max(период, последний опрос)) |
| 3 | плохой ответ |
| 4 | нет связи (любая ошибка connect: no route, timeout, refused, reset) |
| 5 | бан 1 минута |
| 6 | бан 5 минут |
| 7 | бан 10 минут |

Приоритет отображения, если совпало несколько состояний: бан (5/6/7) → плохой
ответ (3) → нет связи (4) → stale (2) → OK (1) → не опрашивался (0). После
истечения бана до следующей попытки показывается предыдущий статус.
- Пулер после получения корректной телеметрии складывает её в tsdb raw.
  Плохие/неполные ответы в tsdb не пишутся.
- Набор полей и raw-контракт для обоих типов инверторов идентичен; тип устройства
  у них общий.
- Имя контракта — `grid` v1 (в UI — GRID), ключ — серийник; состав полей — в разделе
  «Raw-контракт `grid` v1».
- В web процесс-аккумулятор, как и по остальным типам устройств, усредняет данные
  с периодичностью как у остальных и по тому же алгоритму, складывает в tsdb avg.
  Отдельного фильтра по shm-статусу нет: в raw попадают только успешные опросы,
  поэтому аккумулятор усредняет имеющиеся raw-строки окна. Фактически это и есть
  «только status=1 на момент записи», но фильтра по статусу в аккумуляторе нет.
  Нет строк за окно — нет точки для устройства.

## Web

- В главном меню «Web» — новый пункт меню «Сетевые».
- В нём подпункт «Настройки» (настройка сетевых инверторов).
- Настраивается список согласно параметрам выше.
- На этой же странице отдельно настраивается список возможных «размещений»
  (только название).
- У каждого инвертора — выбор размещения из этого списка.
- Удаление размещения, на котором есть инверторы, запрещено.
- 17-й инвертор добавить нельзя: веб показывает ошибку. Если добавить руками в
  файл — ридер лишние записи игнорирует.
- Страница очень похожа на страницу настройки Мастер-Узла.
- Вверху страницы — таблица статуса **всех инверторов из настроек** (включая ещё
  не опрошенные — код 0), обновление раз в **1 секунду**.
- Пункт меню виден всегда.
- На странице настроек — инструкция среднего объёма: что такое сетевые
  инверторы, зачем их опрашивать, как заполнять поля (имя, IP и порт, тип,
  размещение, `logger_sn`, период), как работает кнопка «Определить по IP».
- Отдельным заметным блоком — требование к стабильности адресов: IP-адрес
  логгера должен быть постоянным. Простыми словами: либо задать статический
  IP на самом логгере, либо закрепить адрес за ним на DHCP-сервере (static
  lease по MAC). Если адрес сменится, опрос перестанет работать, пока в
  настройках не укажут новый; имя устройства при этом сохраняется.
- Конфиг пишет веб так же, как у остальных readers.
- В настройках есть `log_level` (см. «Сервис»).
- У `logger_sn` есть кнопка «Определить по IP» (Deye подтверждено; Sofar — по
  документации, проверить на живом).
- Страница настроек читает файл настроек. Остальной веб читает shm и tsdb.
- Вебу нужны имена и размещения, поэтому файл настроек он может читать, но:
  1. только on-demand;
  2. с кэшированием; кэш сбрасывается при сохранении настроек этой же страницей.
- Все новые строки (меню, поля, инструкция, блок про IP) локализуются на 8 языков:
  ru, be, zh, en, ka, kk, uz, tg. Источник — русский, дефолт — английский.
- Страница инвертора `/grid?id=<serial>&gen=<gen>`: одна карточка с секциями
  PV, AC, температуры, состояние/аварии, энергия; все параметры из shm,
  обновление 1 с; hex-слова аварий + таблица активных аварий с расшифровкой;
  ниже — графики как у BMS.
- На странице графиков — графики для сетевых инверторов по аналогии с остальными
  устройствами; состав наборов и режим сравнения — в `docs/grid-reader-ui.md`.
- На главной — плашки `grid`, сгруппированные по размещениям; состав и поведение —
  в `docs/grid-reader-ui.md`.

## Реализация

- Код пулеров для Deye и Sofar уже реализован в проекте `sunReceiver`
  (`../sunReceiver`); код авторский, можно копировать и использовать.
- Деплой — по аналогии с остальными readers. Обязательные артефакты
  восстановимости: unit `malina-grid-reader.service`, дефолтный конфиг
  `/malina/etc/malina/grid-reader.json`, запись в `deploy/manifest.tsv` и
  `deploy/local/deploy-local.sh`; короткое rw-окно под `/etc` для unit-файла.
- Эмулятор не нужен, железо есть. Смоуки — на заглушках.
- Тесты: unit-тесты кодека Solarman V5 (15-байтный datafield, повтор/дубли,
  короткий кадр Sofar), encode/decode контракта `grid` и нормализации,
  лестницы банов 1/5/10, состояния «ключ ещё не получен».
- Безопасность: протокол Solarman не имеет шифрования/аутентификации, считается
  доверенной локальной сетью; конфиг с `logger_sn`/IP хранится с правами
  root, в git не попадает.
- В `tscontract` добавить `grid` v1 и фиксированный `FTI16`; в аккумуляторе —
  правило для `grid`: `inverter_status` — последнее, `alarm_w0..w5` — OR,
  остальные — среднее. Иначе дефолт усреднит статус и маски аварий.
- В `docs/telemetry-store.md`/`docs/ui-stat.md` отметить, что raw `grid` пишется
  с периодом 10–30 с, а не 1 с (порог прореживания и оценка объёма — с учётом
  этого).

## Raw-контракт `grid` v1 (согласован 2026-10-18)

Принцип: вместо f64 — масштабированные целые с запасом по диапазону. Все 24 поля
пишутся всегда; если датчика/величины нет — 0 (для температур — фактическое
значение, включая −100 °C у неподключённого IGBT Deye). Энергия (`energy_today`,
`energy_total`) в tsdb **не хранится** — только в shm.

### Оценка объёма raw

Строка raw: Δt varint 2 Б (10–30 с в мс) + version u16 2 Б + payload 50 Б =
**54 Б**. При 16 устройствах и периоде 10 с: 16 × 8640 × 54 Б ≈ **7,1 МиБ/сутки**.
При периоде 30 с — **≈2,4 МиБ/сутки**. Для сравнения: старый контракт 182 Б
значений (17 телеметрических f64 = 136 Б + 4 температурных f64 = 32 Б + status 1 Б
+ kind 1 Б + alarm 12 Б) давал ≈24,0 МиБ/сутки.

## Замеры и ограничения sunReceiver (учтено)

1. **Таймаут подключения и таймаут чтения — разные вещи.** Connect у всех живых
   устройств занял **2–31 мс**, поэтому 1 с на TCP-подключение с запасом
   достаточно. Дольше идёт именно отдача данных: Deye — **0,15–0,33 с**, Sofar —
   **0,75–1,55 с** после подключения. Принято: ожидание первого байта —
   **Deye 2 с, Sofar 14 с**; общий лимит ответа — **Deye 2 с, Sofar 20 с**.
   Для Deye это основано на замере 2026-10-18 (0,15–0,33 с). Для Sofar
   2026-10-20 отдельно проверено при остановленном `grid-reader`: часть
   валидных ответов приходит через **8,8–14,8 с**, поэтому прежние 5 с
   отбрасывали 11 ответов из 114. 14 с ловит 10 из 11 поздних, 15 с — все;
   общий лимит 20 с не даёт обрезать кадр, начавшийся на 14-й секунде.
   Старый `solarman-v5.md` описывает ещё более медленное поведение другого
   парка. Триггер пересмотра: доля таймаутов приёма у устройства > 5 % за
   час → warn и пересмотр таймаута по логам.
2. **Последовательный опрос 16 устройств (историческое решение; с 2026-10-20
   заменено горутиной на инвертор).** По замерам полный ответ — 0,15–1,55 с
   на устройство, то есть круг из 16 устройств — примерно 2,5–25 с. В период 10 с
   при большом числе Sofar можно не уложиться; правило «не уложились — сразу
   новый опрос» это покрывает; тогда stale считался как 3,5 × max(период,
   фактический круг). Сейчас stale — по последнему опросу инвертора.
   В `sunReceiver` каждый инвертор опрашивается своей горутиной независимо.
3. **Два серийника.** `logger_sn` (SN даталоггера) обязателен для запроса:
   Deye без него отвечает 0x06, Sofar отдаёт только heartbeat. Он хранится в
   настройках. `inverter_sn` (заводской номер) — ключ устройства, читается с
   инвертора и кэшируется; в настройках не обязателен. Deye позволяет определить
   `logger_sn` автоматически: на запрос с SN=0 приходит heartbeat 0x06 с реальным
   SN в кадре.
4. **Порт.** В `sunReceiver` порт зашит `8899`; в `grid-reader` порт задаётся в
   настройках — использовать его.
5. **Ключ — серийник инвертора.** `inverter_sn` читается с устройства (Deye
   0x0003–0x0007; Sofar 0x2000–0x200D, func 04) в рамках первого полного опроса
   и кэшируется. Пока SN нет, опрос не считается успешным: ни shm, ни tsdb. В
   запрос идёт не он, а `logger_sn`.
6. **Протокол — Solarman V5.** Оба типа отвечают только на кадр с 15-байтным
   datafield; 12-байтный кадр Sofar даёт лишь heartbeat 0x05.
7. **Замер 2026-10-18 (5 с, локальная сеть).** Из 9 инверторов в конфиге
   ответили 7: пять Deye — стабильно 3/3 полный блок; два Sofar — полный блок в
   1–2 попытках из 3, в остальных приходит короткий/битый кадр. Ещё два Sofar
   недоступны (no route / timeout). Deye иногда присылает полный блок дважды —
   дубль нужно отбрасывать по серийному номеру кадра/времени.

## Доработка 2026-10-19 (реализована)

**Дата постановки и реализации:** 2026-10-19. Причина: после внедрения
постоянного TCP-соединения для Sofar выявлены побочные эффекты — ночью на
спящих инверторах постоянная сессия рвётся и каждая попытка восстановления
даёт `таймаут connect` → бан. Модель опроса вернули к новому подключению на
каждый запрос и уточнили классификацию «спит vs не ответил». Статусы shm и
формат контракта не менялись.

### 1. Убрать постоянное соединение

- Оба типа (Deye и Sofar) — **новое TCP-подключение на каждый запрос**
  (connect → запрос → ответ → close), как изначально было для Deye.
- Удалить из `solarman.Client` режим `Persistent` и связанную логику
  (`exchangePersistent`, а также обработку накопленных байтов/`drain`,
  введённую специально под постоянное соединение).
- Многокадровый ответ Sofar (не повторяет serial запроса, присылает несколько
  кадров) — **свойство протокола, не меняем**: при новом коннекте на запрос
  по-прежнему брать последний корректный PDU (см. п.5 решения).
- Таймауты: connect — 1 с; на 2026-10-19 было **Deye 2 с, Sofar 5 с**.
  С 2026-10-20 для Sofar: первый байт **14 с**, общий лимит **20 с**
  (см. раздел «Доработка 2026-10-20» ниже).

### 2. Разделить Deye и Sofar на два пулера (историческое; с 2026-10-20 — горутина на инвертор)

- Два независимых цикла опроса **внутри одного сервиса `grid-reader`**
  (отдельные сервисы не вводим — проще деплой/восстановимость).
- Разделение по логике протокола (разные времена чтения, разная обработка
  кадров), а не по организационному принципу.
- **Период опроса — общий** (10/20/30 с) для всех, как сейчас.

### 3. Политика банов — уточнение классификации «спит vs не ответил»

**Постановка (2026-10-19):** после `connect timeout` требуется точно определить,
инвертор «спит совсем» (нет в сети, выключен) или «в сети, но не ответил»
(жив на L2, порт молчит). `no route to host` — частный случай «нет в сети»,
но он бывает не всегда; `i/o timeout` покрывает и «нет в сети», и «в сети, но
не ответил». По коду ошибки их не различить — решает **ARP/MAC**.

- **Механизм (вариант 1):** читать **netlink-таблицу соседей** (`RTM_GETNEIGH`,
  `AF_NETLINK`/`NETLINK_ROUTE`, аналог `ip neigh`/`arp`) после неудачного
  connect. Попытка TCP-connect уже инициировала ARP-резолв у ядра — отдельный
  сырой ARP-запрос (arping) не нужен; внешние утилиты (`arping`/`ip`) не
  требуются.
- **Признак «в сети, но не ответил»** → мягкий backoff, как «плохой ответ»:
  **только `NUD_REACHABLE`** (MAC подтверждён живым).
- **Признак «спит совсем / нет на L2»** → бан 10 мин (как `no route`): всё
  остальное — нет записи, `NUD_INCOMPLETE`, `NUD_FAILED`,
  `lladdr = 00:00:00:00:00:00`, а также неподтверждённые
  `STALE`/`DELAY`/`PROBE`.
- **Повторный резолв не делаем** (решение 2026-10-19): попытка connect только
  что была. `STALE`/`DELAY`/`PROBE` не считаем подтверждением жизни: при
  `STALE` ядро может отдавать кэшированный MAC и начать probe только после
  `delay_first_probe_time` (~5 с по умолчанию), а connect-таймаут — 1 с.
  Неоднозначность трактуется как «нет в сети» → бан (см. п. 8 решений).
- **Бан/backoff по результату:** «спит совсем» → бан 10 мин (как `no route`);
  «в сети, но не ответил» → backoff за «плохой ответ». Это сохраняет прежнюю
  логику «нет солнца/выключен — бан», но теперь она определяется по ARP, а не
  по исходу ЭТОЙ ошибки connect.

**История/согласование:** на live-замере ночью (с `.9` и `.253`) у всех
инверторов `INCOMPLETE`/`FAILED` → спят полностью. Кэшированный `STALE` был
застарелым и после принудительного резолва ушёл в `FAILED` — это подтверждает,
что первому `STALE` доверять нельзя. Так как повторный резолв решили не делать,
`STALE` трактуется как «не подтверждён» → «спит совсем» → бан.

### Согласованные решения (2026-10-19)

> **Актуализация 2026-10-20:** решения о «двух пулерах» и последовательном
> опросе внутри группы заменены: теперь один общий оркестратор и отдельная
> рабочая горутина на каждый инвертор (см. «Доработка 2026-10-20: горутина на
> инвертор»).

1. **Постоянное соединение убираем** — новый TCP-коннект на запрос для
   обоих типов.
2. **Два пулера — два независимых цикла опроса внутри одного сервиса
   `grid-reader`.** Отдельные сервисы не вводим.
3. **Классификация «спит vs не ответил»** — после `connect timeout` по
   netlink-таблице соседей (ARP) определять: `NUD_REACHABLE` → «в сети, но не
   ответил» → мягкий backoff (как «плохой ответ»); всё остальное (нет записи,
   `INCOMPLETE`, `FAILED`, `STALE`/`DELAY`/`PROBE`) → «спит совсем/нет на L2»
   → бан 10 мин (как `no route`). Подробно — п.3 выше.
4. **Протокол опроса не меняем:** Solarman V5 как есть; многокадровый ответ
   Sofar — свойство протокола.
5. **Stale и статусы shm — не меняем** (3,5 × max(период, последний опрос),
   коды 0–7).
6. **Период опроса — общий** (10/20/30 с), как сейчас.
7. **Плохой ответ есть плохой ответ** — «в сети, но не ответил» (порт молчит)
   трактуется как мягкий backoff; «спит совсем» — как бан. **Отдельное
   исключение «плохой ответ Sofar не банится» отменяется:** мягкий backoff
   применяется по признаку «жив на L2» (`NUD_REACHABLE`), а не по типу
   инвертора — одинаково для Deye и Sofar. Бан за «спит совсем» — также для
   обоих типов.
8. **Повторный ARP-резолв не делаем** — попытка connect только что была.
   «Жив на L2» = только `NUD_REACHABLE`; `STALE`/`DELAY`/`PROBE`/`INCOMPLETE`/
   `FAILED`/нет записи = «спит совсем» → бан. Неоднозначность трактуется как
   «нет в сети».
9. **Тесты — только unit** с подменяемым источником ARP (fake-таблица соседей);
   отдельный e2e-сценарий «спит vs не ответил» на заглушках не требуется.
10. **Два пулера — независимые тикеры** с общим периодом внутри одного
    сервиса (с 2026-10-20 — горутина на инвертор).

## Доработка 2026-10-20 (реализована)

**Причина:** 10-минутный debug-захват на `.68` и отдельный тест при
остановленном `grid-reader` показали, что часть валидных ответов Sofar
приходит позже 5 с. Прежний таймаут отбрасывал их как `no data`.

### 1. Таймауты Sofar

- ожидание первого байта — **14 с** (было 5 с);
- общий лимит ответа — **20 с** (отдельно от первого байта, чтобы не
  обрезать кадр, начавшийся на 14-й секунде);
- `idle` после первого байта — **0,4 с** без изменений;
- Deye без изменений: первый байт и общий лимит — **2 с**.

Данные теста (114 запросов, `grid-reader` остановлен): поздние валидные
ответы — 11 штук, первый байт через **8,8–14,8 с**. Порог 14 с ловит
10 из 11, 15 с — все; 5 с не ловит ни одного. 17 запросов не ответили
даже за 15 с — это истинное молчание, а не поздний ответ.

### 2. `no data` не повторяем

- чистый `no data` (за таймаут не пришло ни байта) — **без повтора**:
  пропуск тика; worker сразу ждёт следующий период/backoff;
- повтор остаётся для любого плохого ответа, кроме чистого `no data`
  (неполный/битый PDU, ошибки чтения SN, `dial timeout` при живом ARP);
- причина: в 10-минутном окне повтор восстановил лишь **2 из 29**
  завершённых `no data` (≈7 %), но добавлял ещё один таймаут.

### 3. Горутина на инвертор (2026-10-20, реализовано)

- **Один общий оркестратор** (`runInverters`) запускает по одной рабочей
  горутине на каждый валидный инвертор. Отдельного оркестратора на инвертор
  нет.
- Worker (`pollInverter`) держит свой период, свой backoff и не ждёт другие
  инверторы. Внутри worker — не более одного запроса в полёте.
- При длинном бане **5/10 мин** worker публикует статус бана и **завершается**.
  Оркестратор ждёт `banUntil` и запускает новый worker. Бан 1 мин worker
  пережидает сам и продолжает.
- **shm:** слот `i` пишет только worker инвертора `i`. Список и телеметрию для
  слота не пишет ни оркестратор, ни другой worker. `reset`/`clear` выполняются
  только после отмены контекста и ожидания всех worker — иначе была бы гонка
  записи в освобождаемые слоты.
- Stale считается по `3,5 × max(период, длительность последнего опроса этого
  инвертора)`, а не по длительности общего круга.
- Тесты: `TestParallelInverterWritesSeparateSHMSlots` (два слота пишутся
  одновременно), `TestPollInverterExitsOnLongBan` (worker завершается),
  `TestRunInvertersRestartsWorkerAfterLongBan` (оркестратор перезапускает
  worker после бана). Прогон с `-race`.

# Разбор этапа flash (прошивка 4.5 tst3) и сверка с `.map2`

Источник: `usb.pcapng` (166 МБ), разбор `parse-stage.sh`.
Период захвата: 18:57:19–19:04:46 MSK.
TX 410 652 Б / RX 410 661 Б, 821 303 bulk-события, максимальный URB — 6 байт.

## 1. Итог: поток полностью соответствует файлу прошивки

Сверка с `map2gui/mXP1p1v4_5_Titanator_tst3.map2` выполнена побайтово.
Поток TX раскладывается **без остатка**:

```
TX = "lrunU" (5 Б)
   + подпись заголовка (31 Б)
   + тело образа (406 540 Б) с экранированием 4 значений
   + терминатор 0x55 (1 Б)
```

Проверка объёма: `5 + 31 + 406 540 + 4075 + 1 = 410 652` — совпадает с TX
байт в байт. **Покрыто 406 540 / 406 540 байт тела** (100%).

Экранирование (`4B` + код), 4065 замен:

| Байт тела | На линии | Кол-во |
|---|---|---|
| `0x4B` | `4B 4D` | 1099 |
| `0x55` | `4B 4C` | 1158 |
| `0x57` | `4B 43` | 846 |
| `0x5A` | `4B 4E` | 972 |

Итого 4075 лишних байт на линии. Никаких других вставок/кадровых заголовков в
потоке нет; «`l#`» в потоке — просто совпадение байт внутри тела, не команда.

### Зачем экранирование

Это байт-стаффинг бутлоадера: 4 значения тела заменяются парой `4B` + код,
чтобы в потоке не появились служебные байты протокола. Признаки:

- `0x4B` (`'K'`) — сам префикс экранирования, поэтому он тоже экранируется
  (`0x4B → 4B 4D`) — иначе приёмник принял бы его за начало пары;
- `0x55` (`'U'`) — терминатор/подтверждение: поток прошивки заканчивается
  одиночным `0x55`; сырой `0x55` внутри данных оборвал бы передачу;
- `0x57` (`'W'`) и `0x5A` (`'Z'`) — по-видимому, зарезервированные команды
  бутлоадера.

Обратное преобразование — таблица из 4 значений (выше); формулы для кода
второго байта не выведено, таблица эмпирическая и проверена полным
выравниванием. Без снятия экранирования сверка с `.map2` даёт ~4075 ложных
расхождений.

Подпись в заголовке этого файла — **31 байт** (62 hex-символа после `&31#`), и
она передаётся как есть: `0E229853EAAC7FD8034C737202A29B298BF3D7C67D856005B6AF04272833C3`.

### Скорость порта

При открытии порта выставляется **19200 8N1** (`wValue=0x809C`), затем загрузчик
сразу ставит режим бутлоадера: `SET_BAUD wValue=0x8004, wIndex=0x0001`.

Кодирование FT232R: 14-битная целая часть + 3 дробных бита с шагом 1/8, причём
третий дробный бит — это бит 0 `wIndex`. Отсюда
`divisor = 4 + (2 | 4)/8 = 4.75` → **3 000 000 / 4.75 ≈ 631 579 бод**.
Номинал — **625000 бод**: так задано в вендорской ячейке `_RSBAUD_Rasb_Load=0x64`
(верхняя тетрада по умолчанию `6` — «625000 бод для загрузки через PC»,
`disasm/sources/sunReceiver-docs/protocol_MAP_cells_2026_07_15.txt`).
Отклонение +1.05% — предел дробного делителя FT232R; на линии это нормально.

Монитор и меню работают на **19200** (`0x809C`); в этапе `restore-menu` видно
обратное переключение: 705882 → 19200.

## 3. Рукопожатие

- RX начинается с маяка бутлоадера **`Load\r\n`** — МАП уже в режиме прошивки.
- Первые байты TX: `6C 72 75 6E 55` (`l r u n U`).
- Ответ RX после маяка: `4C 39 31 33 31 79 55` (`L 9 1 3 1 y U`).
- Далее TX и RX совпадают (побайтовое эхо) до терминатора.

## 5. Сопоставление с `Titanator_bak_202610291803.cfg`

Блок меню из cfg (256 Б, `0x100…0x1FF`) в теле `.map2` и в потоке прошивки
**не встречается** — cfg это снимок EEPROM, а не образ ПО. Проверка выполнена
поиском блока и отдельных строк cfg в теле и TX: совпадений нет.

Реальная сверка — с этапом `restore-menu` (куда cfg пишется):

- в cfg **288 байт** (меню + одиночные ячейки, включая `0x10`, `0x31`, `0x32`,
  `0x2C…`, `0x53…`, `0xD7…`);
- записано **287 из 288 байт без изменений**;
- единственное расхождение — **`0x124`: cfg `FF` → записано `FE`**
  (контрольное чтение тоже `FE`). `0x124` — «Реле II» (`_LCD_ReleII_Funk`),
  похоже на нормализацию значения программой.

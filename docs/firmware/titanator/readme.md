# Прошивка МАП «Титанатор»

Документ устройства. Общая структура задачи — `docs/firmware/readme.md`.
Рабочий документ задачи. Ведётся по этапам. Источник истины по задаче — этот
файл; методика съёмки и артефакты — в `docs/firmware/tools/` и
`docs/firmware/titanator/logs/`.

**Статус (2026-10-29):** этапы 1–3 выполнены; этап 4 в работе — сняты
монитор, сохранение меню, включение режима прошивки, прошивка 4.5 tst3 и
восстановление меню. Разбор прошивочного этапа отложен (правило оператора).

## 1. Правила работы

- **Сеть и устройства** — только по явному разрешению оператора (конкретный
  хост + цель). На этапах 1–4 сеть не использовалась.
- **Прошивку выполняет оператор.** Агент не нажимает кнопки в `map2gui`, не
  открывает порт и не трогает МАП.
- **Порядок работы:** оператор объявляет «начало» и «конец» этапа. Агент
  включает захват по «начало», выключает и складывает артефакты по «конец».
- **Во время этапов прошивки логи не парсятся** — только складываются. Разбор —
  отдельной командой позже.
- Коммит/пуш — только по явному запросу.
- Приватные данные — только в `.kilo/`.

## 3. Требования оператора

### 3.1. Постановка (дословно, 2026-10-29)

- Новая задача: «Прошивка МАП Титанатор».
- Этап 1. Слушаем оператора, никуда не лезем, ничего не ищем. Собираем
  требования в `docs/firmware/readme.md`.
- Этап 2. Сбор информации, собираем и заносим в документ.
- Этап 3 — подготовка инструментов логирования (зона агента).
- Этап 4. Снятие логов, сохранение всех артефактов в папку `docs/firmware`
  (по факту — `docs/firmware/titanator/logs/`).
- Этап 5. Анализ логов, разработка стратегии.
- Этап 6 планируется после 1–5.

Дополнительно (диалогом):

- прошивальщик — `map2gui` под Wine, запуск через `map2gui/run-map2gui.sh`,
  работает с serial-портом; кабель подключён **к USB-порту МАП**;
- логи нужны **подробные, все данные в обе стороны на всех этапах прошивки**;
- **снифер не должен мешать** программе: не занимать порт, не искажать байты и
  тайминги; поэтому `strace` отклонён — «будет тормозить и мешать прошивке»;
- захват — **отдельный на каждый этап**; внутри этапа вести протокол по меткам
  времени;
- логировать **всё**, включая служебный слой (vendor-запросы FTDI, открытие/
  закрытие порта);
- во время этапов логи **не парсить**, только складывать.

Целевой образ: **`map2gui/mXP1p1v4_5_Titanator_tst3.map2`**.

### 4.4. Подключение и протокол

- Штатная телеметрия проекта: UART Raspberry (GPIO14/15, `/dev/serial0`), 8N1,
  нативный COM Микроарт (приоритет 115200 → 19200 → 57600 → 9600), побайтовое
  эхо, `ErrRS_eco`; МАП теряется при паузе > 5 с.

- Прошивка идёт по serial на 19200 8N1 (это подтверждено съёмкой).
- Для USB-serial FTDI `latency_timer=1` мс — политика проекта.

## 5. Этап 3. Инструменты

Каталог `docs/firmware/tools/` (подробно — `tools/README.md`), логи —
`docs/firmware/titanator/logs/<ГГГГММДД_ЧЧММСС_MSK>_<этап>/`.

| Файл | Назначение |
|---|---|
| `capture-start.sh <этап> ["примечание"]` | находит FTDI `0403:6001` в sysfs, создаёт каталог этапа, пишет `meta.json`, запускает `tshark -i usbmonN` пассивно |
| `capture-stop.sh [--parse]` | останавливает захват, переносит дамп, дописывает `meta.json`; по умолчанию **не разбирает** |
| `parse-stage.sh [каталог]` | разбор сохранённого этапа (по умолчанию — последний) |
| `decode-ftdi.py <каталог>` | восстановление TX/RX из URB, расшифровка CTRL FTDI, `timeline.md`, `summary.md`, hex-дампы |

Технические решения:

- дамп пишется в `/tmp` и переносится на остановке: `tshark` под root сбрасывает
  привилегии и не может писать в каталог пользователя;
- `sudo` нужен только для чтения `/dev/usbmonN` и переноса дампа; пароль — из
  связки ключей (`secret-tool lookup service sudo username sasha`);
- фильтра по USB-адресу нет: FTDI опознаётся по наличию полей диссектора
  `ftdi-ft.*`, иначе смена адреса при ре-энумерации потеряла бы байты;
- полезная нагрузка берётся из `ftdi-ft.if_a_tx_payload` / `if_a_rx_payload`;
  fallback — сырые URB (для IN срезаются 2 байта modem/line status);
- CTRL-запросы FTDI декодируются: `SET_BAUD` (целая + дробная часть divisor),
  `SET_LATENCY`, `SET_DATA`, сброс, flow-control, modem-control;
- самопроверка на пустой шине пройдена: старт → 4 с → стоп, pcap и разбор
  формируются.

### 6.1. Общие наблюдения по обмену

- Открытие порта: `RESET` → `SET_DATA` 8N1 → `SET_BAUD` (`divisor=156.25` →
  19200) → flow-control off → `MODEM_CTRL` DTR/RTS.
- Опрос монитора — пачками с паузами ~301 мс; первая пауза ~3 с после открытия.
- Начало потока стабильно: `72 7F 00 00 0F 0A 6F 03 …` (совпадает с прошлыми
  `strace`-трейсами).
- Обмен побайтовый: bulk-URB в основном по 1 байту, максимум 2; крупных блоков
  нет — «пакетность» видна по плотности событий, а не по размеру URB.
- Скорость бутлоадера при прошивке — **625000 бод** (вендор
  `_RSBAUD_Rasb_Load=0x64`, верхняя тетрада `6`). FT232R кодирует её как
  `wValue=0x8004, wIndex=0x0001` (делитель 4.75 → ≈631 579 бод, +1.05%).
  Монитор/меню — 19200 (`0x809C`).

### 6.3. Включение режима прошивки (`monitor-flashmode`)

Дамп 6.0 МБ, 18:56:22–18:57:04, после перезагрузки ПК FTDI на `bus 5, dev 6`.
Подробно: `logs/20261029_185621_monitor-flashmode/analysis.md`.

Найдена точка перевода — последние три записи перед тем, как МАП замолчал
(18:56:56.252–56.287):

| Время MSK | Адрес | Данные | Роль |
|---|---|---|---|
| 18:56:56.254 | `0x0000` | `A5` | открытие командной транзакции |
| **18:56:56.269** | **`0x0091`** | **`55 AA`** | **магия входа в загрузчик** |
| **18:56:56.287** | **`0x0000`** | **`06`** | **команда «применить/перезагрузиться»** |

`0x0000=A5` → … → `0x0000=06` — общая схема командной транзакции (та же
обрамляет запись ячеек в `restore-menu`), а `0x0091 = 55 AA` встречается только
при входе в режим прошивки. После `06` МАП перестаёт отвечать; далее `flash`
работает уже с бутлоадером. Требуется проверка воспроизводимости.

### 6.4. Прошивка (`flash`)

- Дамп: `usb.pcapng` **166 МБ**, 18:57:19–19:04:46 MSK (~7 мин 27 с).
- Снимок экрана загрузчика на 70%: `loader-70pct.png`; данные — `notes.md`.
- Показания загрузчика: `VerDevice = MAP SIN`, `VerPlatPic = 1`,
  `VerPlatPow = 1.x`, `VerBoot = 9`, **`VerPO = 4.5`**, **`CPU = dsP33MU810`**,
  статус «Загрузка Файла», «Нет ошибок», файл `mXP1p1v4_5_Titanator_tst3.map2`.
- **Фактический ЦПУ — dsP33MU810 (dsPIC33)**, а не PIC18F46K22 из прошлого
  реверса. Прошлый блокер «не та версия процессора» этим объясняется; образ 4.5
  соответствует железу.
- Подробно: `logs/20261029_185719_flash/analysis.md`. Итог разбора:
  - бутлоадер отдаёт `Load\r\n`, загрузчик отвечает `l r u n U`
    (эхо — `L 9 1 3 1 y U`), далее подпись заголовка (31 Б) и тело образа;
  - поток раскладывается без остатка: `5 + 31 + 406 540 + 4075 + 1 = 410 652 Б`;
    **тело покрыто на 100%**; экранируются 4 байта:
    `0x4B→4B4D`, `0x55→4B4C`, `0x57→4B43`, `0x5A→4B4E`;
  - в конце — терминатор `0x55` (19:04:28), после него тишина;
  - скорость линии при прошивке — **625000 бод** (номинал; FT232R: делитель
    4.75 → ≈631 579 бод, `SET_BAUD 0x8004/0x0001`); монитор/меню — 19200;
    фактический темп ~1000 Б/с ограничен побайтовым эхом через USB;
  - передача ~6 мин 54 с; скриншот 70% (19:03:13) соответствует 81.7% объёма;
  - ошибок/повторов в потоке нет;
  - `cfg` (`Titanator_bak_…cfg`) в образе ПО не встречается — это снимок EEPROM;
    сверка с ним идёт по этапу `restore-menu` (6.5): совпало 287 из 288 байт;
  - **итог прошивки (100%, верификация, состояние после сброса) не зафиксирован** —
    уточнить у оператора.

### 6.5. Восстановление настроек ЖКИ (`restore-menu`)

Подробно: `logs/20261029_190829_restore-menu/analysis.md`. Кратко:

| # | Время MSK | Смещение в TX | Перед блоком | Что это |
|---|---|---|---|---|
| 1 | 19:08:56.038–57.007 | 5719 | `0x77` (`w`) | запись блока меню `0x100…0x1F8` |
| 2 | 19:09:01.515–01.814 | 6927 | `0x72` (`r`) | контрольное чтение |
| 3 | 19:09:02.634–02.933 | 8197 | `0x72` (`r`) | повторное контрольное чтение |

- Копии 2 и 3 **побайтово идентичны**; копия 1 отличается на +129 Б (в чтениях
  есть вставка `CA 0A 72 7F 01`) — это разница кадров «эхо записи» vs «ответ на
  чтение», не расхождение данных.
- Сверка с `.cfg` после декодирования кадров MicroArt: **287 из 288 байт
  совпали**; единственное расхождение — **`0x124` (cfg `FF` → записано `FE`)**;
  контрольное чтение тоже возвращает `FE`. `0x124` — «Реле II»
  (`_LCD_ReleII_Funk`).
- Непрерывные серии: 19:08:55.864–57.662 (2156 событий), 19:09:01.338–02.157
  (1956), 19:09:02.458–03.251 (1920).

## 8. Ограничения и что проверить на этапе 5

1. **usbmon** даёт гранулярность USB-транзакции (URB), а не отдельного байта;
   межбайтовые тайминги на линии по нему не восстановить — только пачки и паузы.
2. Логи содержат кадровые байты/экранирование MicroArt; **протокол не декодирован**
   — нужен парсер кадров (`r/w/o/e`, эхо, CRC) для сверки блоков и полей.
3. Скорость бутлоадера 625000 бод подтверждена вендорской докой
   (`_RSBAUD_Rasb_Load=0x64`); FT232R даёт ≈631 579 бод (+1.05%, предел
   делителя). На темп не влияет — ограничение в побайтовом эхе USB.
4. Заголовочная подпись 4.5 tst3 совпадает с 3.6 — проверить тело/структуру.
5. Не зафиксирован итог прошивки (100%, «Загрузка завершена») и поведение после
   сброса — уточнить у оператора.
6. Меню восстановлено из cfg, снятого **до** прошивки; есть ли расхождения после
   обновления — по протоколу на этапе 5.
7. `strace` не использовался (deviation by design) — адреса кода загрузчика в
   этих логах отсутствуют.
8. Команда входа в режим прошивки найдена (`0x0091=55 AA` + `0x06`), но
   воспроизводимость и роль ручных действий (кнопки/питание) не проверены.
9. Образ передан целиком, но финальный статус/верификация не зафиксированы.
10. При восстановлении меню одно расхождение с cfg: `0x124` (`FF→FE`).

# КЭС/MPPT в legacy ПАК «Малина-2» (разбор бэкапа .60)

> **Карта ячеек КЭС живёт в двух документах:** подтверждённое — `docs/kes-memory.md`,
> неподтверждённое/гипотезы — `docs/kes-memory-not-accepted.md`. Ячейки ниже — как их
> видел legacy; источник истины — только `kes-memory.md`.

Анализ боевого образа ПАК «Малина» (192.168.13.60) и человека-читаемых артефактов
внутри него. Источник — бэкап загрузочного диска:

    /u03/archive/solar/microart/malina_backup/titanator_malina_fixed_20261007
    ├─ part1_boot.vfat.img   (63 МиБ, /boot)
    ├─ part2_root.ext4.img   (4 ГиБ, /)         ← /usr/sbin/*, /etc
    └─ part3_settings.ext4.img (534 МиБ, /settings) ← /settings/daemons/*, /settings/html/*

Монтирование (только чтение):

    sudo mount -o loop,ro part2_root.ext4.img   /mnt/root
    sudo mount -o loop,ro part3_settings.ext4.img /mnt/settings

Связано: `docs/kes-reader.md` (§4 — контракт КЭС), `docs/events.md` (§11 — заглушки КЭС),
`docs/map-memory.md`. Общий обзор legacy — `docs/event-manager.md`,
`docs/legacy/master-node.md`.

Внимание: это **legacy-реализация на C/Perl/PHP поверх SysV IPC** — не наш стек.
Ниже фиксируем функциональность и форматы, а не код.

## 1. Как legacy находит и различает устройства (фактический probe)

Цепочка автообнаружения (hotplug):

- `/etc/udev/rules.d/108-usb.rules`: на `ttyUSB[0-9]` (add/change и remove) →
  `systemd` юнит **`add_tty.service` → `/usr/sbin/tty_scan.sh`**.
- `tty_scan.sh`: `sleep 10` (защита от «быстрого перевтыкания»); `find /dev/ttyUSB*`
  → `/var/map/devices_available.txt`; снимает флаги и убивает `mapd/mpptd/batmond/
  dbed/mserver/emd`; запускает **`/usr/sbin/usbscanner`**; затем `fill_shm.pl`;
  по найденным типам стартует нужные демоны (`mapd`/`mpptd`/`chargerd`).
- **`usbscanner`** (ELF ARM, stripped) — собственно определение типа устройства.
  Пишет строки в `/var/map/devices_found` формата **`<порт>D<тип>R<baudIdx>`**.
  Строки бинарника (из `strings`): `Checking device at port %s, and baudrate: %i`,
  `Device type %i found on baudrate: %i`, `%sD%dR%d`; спец-случай порта
  `/dev/serial0`/`/dev/ttyS0` → метка `S0` (= UART, «UART:»).

**Коды типа устройства (`D`):**

| D | Устройство | В нашей теме |
|---|---|---|
| `D0` | не распознано (пропуск) | — |
| `D3` | **MAC** (МАП) | МАП |
| `D5` | **MPPT** | **КЭС** |
| `D7`/`D9` | CHARGER (зарядник) | вне темы |

`get_devices.sh` считает `grep "D3|D5|D7" -c` → `MAC:n`, `MPPT:n`, `CHARGER:n`.
`/usr/sbin/devices_found` — симлинк на `/settings/daemons/devices_found.pl`
(человекочитаемый вывод: `MPPT on USB0:19200 bps, …`).

**Индекс скорости (`R`):** `R0=19200`, `R1=57600`, `R2=115200` (автоскан бодов,
совпадает с `docs/map/map/malina2.pdf`: «автоопределение скорости 19200–115200»).

> **Вывод для нашей задачи:** критерий «КЭС vs МАП» зашит внутри `usbscanner`
> (в скриптах только код `D5`). Точные байты probe оттуда — отдельная задача дизасма.

### 1a. Probe `usbscanner` — РАЗОБРАН (дизасм ARM)

`usbscanner` (ELF ARM, stripped) проанализирован статически (radare2/ARM). Логика:

- `main` (`0x11470`) проверяет кандидатов: `/dev/serial0` (метка «Checking MAC on
  UART...») и порты из `/var/map/devices_available.txt` (это `find /dev/ttyUSB*`).
  Для каждого порта перебирает **3 скорости** из таблицы `.data 0x21c54`:
  `B19200(0x0E)`, `B57600(0x1001)`, `B115200(0x1002)` → индекс `R0/R1/R2`.
- `check_device(port, baud)` (`0x111f0`): `open(port, O_RDWR|O_NOCTTY|O_NONBLOCK)`,
  `tcgetattr`/`cfmakeraw`/`cfsetospeed`/`cfsetispeed`/`tcsetattr`/`tcflush`,
  `isatty`-проверка (не tty → отказ).
- Шлёт **штатный кадр MicroArt-чтения**: `'r'(0x72)`, `P=0x00` (страница 1 байт),
  адрес `A=0x0000`, CRC (сумма mod 256, аккумулятор `0x21cc8`), `\n`. Экранирование —
  как в протоколе: `0x0A → DB DC`, `0xDB → DB DD`; каждый байт с эхо-подтверждением
  (`fn 0x10954` — отправка байта + сверка эха; `fn 0x10a18` — байт с эскейпом).
- Приём ответа (`fn 0x10f0c`): читает поток, эхо-подтверждает, расэкранирует,
  проверяет CRC, кладёт в буфер `.bss 0x21c64`.
- **Тип устройства = байт данных ответа = значение ячейки `0x0000` (`_Device`)**:
  `ldrb r3,[buf,1]` (buf[0]=`'o'`=0x6F, buf[1]=данные). Провал/нет ответа → `0`.

**Коды `_Device` (0x0000) — подтверждено двумя местами** (`usbscanner` возвращает код
как есть; `tty_scan.sh` мапит `D<code>` на демона):

| `_Device` | Буква | Устройство |
|---|---|---|
| `0` | `D0` | не распознано |
| **`3`** | `D3` | **МАП (MAC)** |
| **`5`** | `D5` | **КЭС / MPPT** |
| `7` | `D7` | CHARGER |
| `9` | `D9` | CHARGER (вариант) |

Запись строки: `%sD%dR%d` (порт, код, индекс скорости); провал → `%sD0R0`;
для UART — `/dev/serial0D%dR%d`.

**ИТОГО (снимает GAP §7.6 по маркеру):** **маркер КЭС = значение ячейки `0x0000`
равно `5`**; probe = MicroArt-чтение 1 байта по адресу `0x0000` (маркер МАП — `3`).
Серийник в `usbscanner` не читается (только ячейка 0).

### 1b. `mpptd` — РАЗОБРАН (дизасм ARM): окна чтения и карта ячеек

`mpptd` (ELF ARM, stripped) — один процесс на все КЭС. `main` читает
`/var/map/devices_found`, берёт строки `D5` (КЭС) и опрашивает их штатным
MicroArt-протоколом (в бинарнике — те же функции, что в `usbscanner`: отправка кадра
`0x11290`, приём `0x11610`, байт с эхо/эскейпом `0x1110c`; запись `'w'` — `0x11290`).

**Окна чтения (адрес → длина), функция `0x11984` и `0x11b0c`:**

| Адрес (dev) | Длина | Куда (RAM) | Что там |
|---|---|---|---|
| `0x0000` | 190 | `0x000..0x0BD` | ID/версии/`_Device`/SerialNum (читается как есть) |
| `0x04B2` | 240 | `0x2C2..0x3B1` | измерения + `UID` + `Mode` |
| `0x05A3` | 240 | `0x3B3..0x4A2` | ошибки/реле/знаки/датчики тока |

В снифе `mpptd` (strace) реально наблюдаются: на старте `0x0000`, в цикле `0x04B2` и `0x05A3`
(по 241 Б). Окно `0x02C2` (дизасм) в обмене не поймано (возможно, init-only) → в контракт не берём.

Ключ: **`image_offset == RAM-адрес`**, а **адрес устройства = RAM-адрес + `0x1F0`**
(в точности правило «+0x1F0» из карты `mppdt`!). Образ складывается в буфер (2048 Б на КЭС,
`idx<<11`).

**Отображение ячеек → поля JSON (подтверждено дизасмом `main`):**

| Поле JSON | Ячейка RAM | Примечание |
|---|---|---|
| **`UID`** | **`0x2C9` мл. / `0x2CA` ст.** — в «правде» это **серийник** (`ID = low+high·256`, сырое дес.; EEPROM, см. `docs/kes-memory.md` §2) | legacy брал по модулю, при `0` → `idx+1` |
| **`Mode`** | **`0x2C2`** | ASCII-символ; mapper `fn 0x11d18`: если `0x2A < c ≤ 0x7C` → `c`, иначе `'U'` |
| `Sign` / `MPP` | `0x37A` / `0x379` | через тот же mapper (`'U'` если вне диапазона) |
| `Vc_PV` | 0x2D9 | |
| `Ic_PV` | 0x2DF | (по «правде») |
| `V_Bat` | 0x2E5 | |
| `P_PV` | 0x2EB | |
| `P_Out` (`P_MPPT`) | 0x2ED | |
| `P_Load` | 0x2F5 | |
| `P_curr` | 0x2F9 | |
| `I_Ch` | 0x2FB | |
| `I_Out` | 0x2FF | |
| `Temp_Int` / `Temp_Bat` | 0x31D / 0x31E | |
| `Pwr_kW` | 0x3A1 | + `Pwr_W` 0x39F |
| `Sign_C0` / `Sign_C1` | 0x404 / 0x405 | |
| `I_EXTS0` / `I_EXTS1` | 0x406 / 0x408 | ток датчиков |
| `P_EXTS0` / `P_EXTS1` | 0x40A / 0x40C | мощность датчиков |
| `Relay_C` | **0x3E3** | биты 0/1/2 = реле 1/2/3 |
| `RSErrSis` | **0x3B6** | биты см. §5 |
| **`windspeed`** | **`0x3F8`** (LE, 16 бит) | `65535` = н/д |
| `FW` | `0x02` | подтверждено (кодировка `major=v&0x0F`, `minor=v>>5`; `0xA8`→8.5) |
| `R1`,`R2`,`R3` | производные от `Relay_C (0x3E3)` | **`R1=бит0, R2=бит1, R3=бит2`** (проверено: `Relay_C=0x05` → `1,0,1`) |

**Формат JSON** (строка в `mpptd`, `.rodata`): `{"timestamp","time","UID","Vc_PV","Ic_PV",
"V_Bat","P_PV","P_Out","P_Load","P_curr","I_Ch","I_Out","Temp_Int","Temp_Bat","Pwr_kW",
"Sign_C0","Sign_C1","I_EXTS0","I_EXTS1","P_EXTS0","P_EXTS1","Relay_C","RSErrSis","Mode",
"Sign","MPP","windspeed","FW","R1","R2","R3"}`. Пишется в shm и в
`/settings/logs/mpptN_energy.json` (формат `%d-%02d-%02d:%.3f`), ошибки —
`/settings/logs/mppt_errors.log` (`date:...,time:...,mppt:%d,error:%d`), метка живости —
`/var/map/mpptd_time_label`.

**Вывод для контракта:** карта `sunReceiver/docs/map/mppt` подтверждена и **дополнена**
тремя недокументированными ячейками: `Mode=0x2C2`, `UID=0x2C9`, `windspeed=0x3F8`,
`Sign/MPP=0x37A/0x379`. «Серийник» КЭС в legacy — **`UID` (`0x2C9`/`0x2CA`; = «правда», EEPROM, см. `docs/kes-memory.md`)**;
адреса `0x18/0x19` (буква серийника МАП) к КЭС не применяются.

### 1c. `mpptd` — запись/реле (дизасм)

Запись в КЭС: `mpptd` в хвосте `main` (`0x14dcc` `msgrcv` из очереди **2200**) принимает
строку, `strtok(":")` разбирает **`idx:cell:value:ts`**, проверяет `idx ≤ N-1`, затем:
1. пишет байт **`3` (`ComMAP_EEPromWR`)** в адрес `0` (команда «разрешение записи»);
2. пишет байт `value` страницей 1 по адресу **`cell`** (`uxth(cell)` — **как есть, без
   `+0x1F0`**).

**Реле КЭС:**
- **Чтение состояния** — из образа по смещению **`0x3E3` (`Relay_C`)** (см. §1b), биты
  0/1/2 = реле 1/2/3; это же значение уходит в JSON `"Relay_C"`.
- **Запись (legacy-клиент `write_sec.php`)**: шлёт в очередь 2200 сообщение с ячейкой
  **`0x0E3D`** и новым байтом состояния (после чтения `0x3E3` из shm 1995 и
  пересборки битов). Т.е. legacy пишет состояние реле в **`0x0E3D`**, а читает из
  **`0x3E3`** — это **разные** ячейки.
- `0x0E3D` в карте `mppt/` **не описан** (по карте в районе `0xE30` — `I_Akb_MPPT[16]`).
  **Подтверждено снифом:** `0x0E3D` — командная ячейка реле КЭС (write-регистр), тогда как `0x3E3` —
  их текущее состояние. **Требует подтверждения на железе** (при отсутствии — трактовать
  relay-запись КЭС как «сначала проверить на реальном устройстве», иначе не писать).

> Для нашего `kes-reader`: состояние реле публикуем из `0x3E3`; команду реле формируем
> так же, как откроется на железе (кандидат — запись байта в `0x0E3D`); до подтверждения —
> в событиях/API держать relay-запись как «не реализовано/под вопросом».

## 2. Демоны, флаги, watchdog

- Демоны: `mapd` (МАП), **`mpptd` (КЭС/MPPT)**, `batmond` (BMS/батарейный монитор),
  `dbed`, `mserver`/`mserverups`, `chargerd`, `scd`, `emd` (менеджер событий).
- Флаги-включатели в `/var/map/`: `mapd`, `mpptd`, `batmond`, `dbed`, `mserver`
  (`touch` файла = сервис разрешён).
- Watchdog: `check_daemons.sh` периодически зовёт `check_mapd.pl` / **`check_mpptd.pl`** /
  `check_emd.pl` / `check_ms.pl`. `check_mpptd.pl`: если `/var/map/mpptd_time_label`
  старше **60 с** → `kill -9 mpptd` (перезапуск делает `tty_scan`/сервис-логика).
  `check_daemon.sh <name>` → `pidof` (rc 0 = работает).
- `mpptd_start.sh`: `touch /var/map/mpptd`; если `mpptd` уже есть — выход; иначе старт
  `/usr/sbin/mpptd`; **и убивает `batmond`** (конфликт BMS↔MPPT — учесть при портировании).
- `mpptd_stop.sh`: снимает флаг и гасит `mpptd` и `batmond`.
- `mpptd_restart.sh`: `kill` → `sleep 1` → старт, если не поднялся.

## 3. IPC и shared memory (legacy-контракт)

SysV объекты (ключи и размеры — из `emd.pl`, `read_json.php`, `write_sec.php`,
`read_sec.php`, `read_bms.php`, `shm_init.pl`):

| Ключ | Размер | Назначение |
|---|---|---|
| **2016** | 4096 | **JSON-снимки КЭС**: 4 слота по 1024, разделитель `#EOF` в каждом |
| **1995** | 8192 | **сырой образ ячеек КЭС**: 4 блока по **2048 байт** (по 1 на КЭС) |
| 2015 | 2048 | JSON-снимок МАП |
| 1996 | 2048 | образ ячеек/меню МАП (EEPROM) |
| 2017 | 2048 | JSON батарейного монитора (2 слота × 1024) |
| 2018 | 1024/32768 | CHARGER/BMS (расхождение: `emd.pl` — 1024, `read_bms.php` — 32768) |
| 5000 | 1024 | статус-биты (`fill_shm.pl`: 20 байт = 1) |
| 0x7CE/0x7DF/0x7CC/0x7D2/0x7CA/0x7E0/0x7CB/0xFA0/0x7D1/0x7E1 | — | `shm_init.pl` (старая схема инициализации, часть уже не используется) |

SysV message queues (ключи сообщений):

| Ключ | Направление |
|---|---|
| **2200** | **to-mppt** (команды/запись в КЭС) |
| **2201** | **from-mppt** (ответ) |
| 2100 / 2101 | to-map / from-map |
| 2300 | EMD (события) |

Формат записи (из `write_sec.php`): **`<id>:<cell>:<value>:<timestamp>\0`**,
где `id` — индекс КЭС (0-based), `cell` — адрес ячейки, `value` — значение.
Ответ — эхо `<timestamp>` (проверка доставки), иначе `error`/`unread`.

## 4. Веб/HTTP API КЭС (legacy)

- `GET /read_sec.php?id=N&offset=A&count=C` — чтение ячеек из shm 1995:
  байты `id*2048 + offset` (offset<2048), возврат JSON-массивом (decimal).
  `id` 1..N, где N = число `D5` из `get_devices.sh`.
- `GET /write_sec.php?id=N&relay=R&mode=on|off|1|0` — **реле КЭС**;
  текущее состояние читается из байта `id*2048+0x3E3` (`Relay_C`), биты 0/1/2 = реле 1/2/3.
  Формируется запись ячейки **`0x0E3D` (дес. 3645)** со новым байтом состояния и шлётся в 2200.
- `GET /write_sec.php?id=N&data=[[cell,value],…]` — запись произвольных ячеек КЭС
  (десятичные числа), приоритет у `relay`.
- `GET /read_json.php?device=mppt` — до 4 JSON-объектов КЭС из shm 2016.
- `GET /read_json.php?device=map|bat` — аналогично для МАП/БМ.
- `GET /devices.php` (→ `get_devices.sh`), `GET /find_devices.php`
  (→ `systemctl start add_tty` = пересканировать порты).
- `POST /wind_mppts_set.php` (`numbers`) — список индексов КЭС группы «ветер»
  (0-based, через запятую) в `/settings/web-data/wind_mppts` + `mapd_restart`.
  В JSON поле `T`: `0` = солнце, `1` = ветер.

## 14. `mpptd` (шаг 4): что уточнилось и что осталось

Дополнительные наблюдения по дизасму (полные выгрузки — `./disasm/mpptd`):

- **Окно `devAddr 0x02C2` (RAM `0x0D2..0x1C1`) читается, но НЕ парсится.** Скан обращений
  к image-смещениям в этом диапазоне — пусто; парсятся только ячейки `≥0x2C2`. Значит это
  окно для КЭС-контракта **не используется** → эмулятору достаточно отдавать детерминированные
  значения (нули/константы), а `kes-reader` его может игнорировать.
- **Ячейки `0x0E3D` (команда реле, legacy) в `mpptd` НЕТ.** Демон пишет «как есть» ту ячейку,
  что пришла в сообщении `<id>:<cell>:<value>`; сам `0x0E3D` не упоминается. Т.е. семантика
  команды реле **не подтверждается и внутри `mpptd`** — это решение клиента. Вопрос остаётся
  открытым → шаг 5 (`MAP2Gui_.exe`) либо фиксация гипотезы.
- **Команды `mpptd` не валидирует.** Набор команд КЭС в демоне не перечислен: на запись он
  шлёт pre-команду `3` (`EEPromWR`) и переданный блок. Значит «валидный набор» — вопрос
  уровня устройства, а не демона (для эмулятора: поддерживать `3` + блок; для `8` — отдельно).
- **Энергия.** Состояние — `/var/map/mpptN_energy.bin` (persistent), лог — 
  `/settings/logs/mpptN_energy.json` (формат `date:%d-%02d-%02d,time:%02d:%02d:%02d,...`,
  строки значений). Источник значений — измерения КЭС (`Pwr_W 0x39F` / `Pwr_kW 0x3A1`);
  для контракта достаточно этих ячеек.
- **`FW`.** В JSON `"FW":"%.1f"`. Уточнено по дизасму: значение берётся из **ID-окна**
  (адресная область `0x00…`, вероятнее `_VerPO` `0x02`) и **декодируется по битам**:
  старшие биты (`lsr 5`) + младшие (`and 0x1f`) → float (формат `%.1f`). Т.е. устройство
  хранит версию ПО в ID-окне, а не «магическим» числом. В **`MAP2Gui_` FW выводится прямо
  на форме** (вкладка монитора/после загрузки `.map2`) — источник тот же (поле ID-окна).
  Для эмулятора: задавать `FW` = значение ID-ячейки (напр. `0x63` для «6.3»).
- **Модель** — **опровергнуто** (было «не ячейка»): подтверждено `Вт = 0x05×100`, ячейки
  радио `Модель`/`Версия Модели` в `0x000..0x1FF` (точные адреса **не зафиксированы** —
  см. `docs/kes-memory-not-accepted.md`).

**Итог по шагу 4:** новых RS-ячеек нет; закрыто окно `0x02C2` (не используется) и энергия;
по-прежнему открыты: семантика команды реле `0x0E3D` (подтверждена снифом, не на железе),
набор команд/необходимость post-команды,
кодирование `FW`/модели. Эти три — к шагу 5 (`MAP2Gui_.exe`) или фиксируем как допущения.

«Монитор Ver 26.7» (вкладка MPPT/SUN)**, отображая живые значения эмулятора.

Что показывает монитор (по нашему эмулятору):
- `Версия: SUN Pow0 Pico Net0`, `Модель 0Bv/0B`, `Версия ПО Ver 3.3`, `ID: 0`;
- `Напряжение Солнечной Панели 160.0 В`, `Напряжение АКБ 54.16 В`, `Ток АКБ 100.0 A`;
- Режимы: `Цикл. Заряд "?"`, `Цикл. Дозаряд "v"`, `Буф. Заряд 1 "B"`, `Буф. Заряд 2 "b"`;
- Радио `Модель` (LP 60A / HP 100A / LJ 150W / UP 200A) и `Версия Модели` (165v(200v)/230v(250v));
- Чекбоксы `Ведомый Режим I2C`, `Откл. Корр. EXT датчиков тока`, `Расширенный протокол с МАП`;
- `Сохранить/Загрузить МЕНЮ ЖКИ`, `Сброс Статистики`, `Сбросить`.

**Что это даёт:**
- Протокол Микроарт у КЭС — тот же, что у нас: дамп обмена (`KES_EMU_WIRE`) показал кадры
  `r`, с большими страницами (128 байт: `P=0x7F`), адреса `0x0000,0x0080,0x0100,…`, а также
  `0x02B0,0x04D5,0x05DC,0x0DF0,…` — т.е. `MAP2Gui` читает память страницами по 128 байт.
- «Сразу закрывалось» — не из-за протокола, а из-за конкуренции за порт (`kes-reader` держал
  `/dev/ttyKES0`) и прав на PTY (создан root'ом): после остановки ридера и `chmod 0666` на
  slave-pts монитор подключается и работает.
- `MAP2Gui` — рабочий стенд: `Сохранить/Загрузить МЕНЮ ЖКИ` (=`SUN_MENU_adjustment.cfg`) и
  адресный EEPROM-редактор позволяют уточнить **ячейки настроек и реле** без железа.

**Осталось уточнить по монитору:** коды `Версия ПО`/`Модель` (мы отдаём `FW=0x63`, показано
`Ver 3.3`; модели — из отдельных ячеек), температуры (показаны 77/9 °C при наших 32/…°C —
иные ячейки/масштаб), и наличие/адрес **команды реле** (на вкладке MPPT — пороги `T Вкл/Выкл`,
`М Вкл/Выкл`, а не прямые чекбоксы реле).


## 18. Разбор обмена `MAP2Gui_` ↔ `kes-emu` (снифер, локально)

Дамп обмена (wire) снят при работе монитора и загрузке «МЕНЮ ЖКИ» из
`SUN_5_20230915.cfg`. Кадры — штатный Микроарт.

**Чтение (монитор).** Сначала читается вся EEPROM страницами по **128 байт**
(`P=0x7F`) с адресов `0x0000,0x0080,0x0100,…,0x0380` (полные `0x000..0x3FF`), затем
периодически — точечные поля по адресам (`адрес устройства = RAM + 0x1F0`):

| Чтение | RAM | Поле |
|---|---|---|
| `0x04C9` | 0x2D9 | Vc_PV |
| `0x04CF` | 0x2DF | Ic_PV |
| `0x04D5` | 0x2E5 | V_Bat |
| `0x04EB` | 0x2FB | I_Ch |
| `0x050D` / `0x050E` | 0x31D / 0x31E | Temp_Int / Temp_Bat |
| `0x05A6` | 0x3B6 | RSErrSis |
| `0x0000/0x0001/0x0002/0x0005/0x009B` | ID | идентификация/версии |

**Запись «МЕНЮ ЖКИ» (загрузка `SUN_5_20230915.cfg`).** Последовательность:
1. `w addr=0x0000 data=03` — команда `ComMAP_EEPromWR` (разрешение записи);
2. `w addr=<адрес начала блока EEPROM> ` **208 байт** (page `0xCF`) — блок EEPROM
   `<start>..<start+0xD0>` со значениями из `.cfg` (с экранированием, `0x0A→DB DC`), совпадает с cfg;
3. `w addr=0x0000 data=07` — команда `7` (`load_EEProm`, post).

**Выводы:**
- **Карта настроек КЭС — EEPROM-блок** (адрес начала **не зафиксирован** в контракте;
  второй источник); значения — из `SUN_*_adjustment.cfg`
  и `Карта Памяти_WG.csv`. Реле-настройки — здесь же: `Relay_1/2/3` = `0x8E/0x92/0x96`.
- **Для записи настроек нужна post-команда `7`** (после блока), чего не было в нашем пути
  relay из legacy (`write_sec`); для настроек добавить.
- Прямых «чекбоксов реле» в мониторе нет — реле управляются **настройками** (функция реле в
  EEPROM), а не «живой» ячейкой. Команда реле `0x0E3D` (legacy, FW ≥6.3) — отдельный путь,
  в `MAP2Gui 2023` не используется.
- Монитор читает именно наши поля (`+0x1F0`), т.е. карта подтверждена и с внешней стороны.

## 19. Скрытые формы/функции `MAP2Gui_` (статический разбор DFM)

В exe есть **12 DFM-форм** (бинарные ресурсы `TPF0`). Видимые в UI — `FormMain`(Загрузчик),
`FormMonitor`(Монитор), `Form_CFG_LCD`(Установки ЖКИ), `FormEEProm`, `FormNote`,
`FormOptHard`(Железо), `FormOptSoft`(.soft), `FormFile`. **Не видны в обычном UI:**

- **`FormModBus`** (Caption «ModBus») — скрытая форма отправки ModBus-кадров:
  поля `DevAdr(8)`, `Com(8)`, `Adr(16)`, `Num(16)`, `L_CRC`, `L_Answer`;
  значения по умолчанию `E_AdrModBus=0x88`, `E_Com=0x03`, `E_Adr=0x0001`;
  кнопки `B_SmsSend` и `B_Stop` («Read»). Т.е. ручной ModBus-запросчик.
- **`FormReadPort`** (Caption «Чтение с Порта») — `TRichEdit` только-чтение: **лог приёма порта**.
- **`FormWritePort`** (Caption «Запись в Порт») — `TRichEdit`: **лог передачи порта**.
  → вместе это встроенный «снифер/терминал» (аналог нашего `socat`).
- **`FormOptSoft`** (кнопка «.soft»): скрытые/неактивные опции — `no EEProm`, `MENU`,
  `RS232` (чтение/запись, `Visible=False`), `hex`, `Резерв`.
- **`FormOptHard`** («Железо»): выбор COM и скорости, включая **нестандартные 312500/625000**,
  и `CheckBoxSound`.

**`FormMain` (меню/кнопки):** `ActionMainMenuBar1` с пунктами `&soft`, `&Hex`, `&Help`
(Print Setup, Exit), кнопки `B_Modem`, `B_MAC`. Скрытые формы, вероятно, открываются из этих
веток/по условию (в меню обычного UI их не видно).

**`FormMonitor`:** закладки `TS_MAP`, `TS_MPPT`, `TS_SUN`, `TS_BMS`; среди подписей —
инженерные/скрытые контролы: `Load EEProm`, `SaveEE`, `Set Time`, `Calibr Time`, `TestI2C`,
`DeathTime`, `Corr`, `Soft Prog`, `L_DeathTimeHex` (калибровка/тесты/служебное).

**Итого:** «сюрпризы» — встроенные `ModBus`-запросчик и Read/Write-порт (терминал), скрытые
диагностические опции (`.soft`) и инженерные контролы в мониторе. Прямых «пасхалок»/паролей
в строках не найдено.

## 20. Legacy API КЭС (HTTP, из исходников на живом `.68`)

**Факт `.68` (nginx):** `location ~ \.php$` → `auth_basic "Restricted"` (htpasswd `admin`),
поэтому на `.68` Basic требуется и на чтение, и на запись; `read_json.php` вынесен в
отдельный `location = /read_json.php { allow all }` и доступен без авторизации.

**Наша политика совместимости** (решение, зафиксировано в `docs/legacy/legacy-api.md` §7 и
`docs/api-auth.md` §1): legacy-**чтение** для КЭС (`read_sec.php`, `read_json.php?device=mppt`)
— **открыто** (повторяет МАП-чтение, нужно для внешних потребителей/портала),
legacy-**запись** (`write_sec.php`) — HTTP Basic + PAM. Т.е. Basic на чтение на `.68` —
факт конкретной установки, а не требование к нашему совместимому слою.

### `read_sec.php`
`GET ?id=1..N&offset=A&count=C` (`N` = число MPPT из `get_devices.sh`; `id` — **1-based**;
границы `offset≥0`, `count≥1`, `offset+count ≤ 2048`). Читает shm **1995**, `(id-1)*2048+offset`.
Ответ — PHP-массив `addr→байт`: при `offset=0` это **JSON-массив** `[b0,b1,…]`, при `offset>0`
— **объект** `{"713":0,"714":0}` (`die('error')` при неверных параметрах).

### `write_sec.php`
`GET/POST` `id` (1-based), `data=[[cell,val],…]` или `relay=1..3&mode=on|off|1|0`.
Ответы: **`Ok`** (в т.ч. если состояние уже такое), **`error`**, **`unread`** (в очереди 2200
есть необработанная команда). `relay` имеет приоритет над `data`.

**Правило реле (точно из `write_sec.php`; само поведение устройства — в `docs/kes-memory.md` §3.1):**
1. текущее состояние читается из shm **1995** по `(id-1)*2048 + 0x3E3` (**`Relay_C`, биты 0/1/2
   = реле 1/2/3**);
2. если запрошенное состояние реле уже совпадает — сразу `Ok` (запись не шлётся);
3. иначе собирается **новый байт-маска для ВСЕХ трёх реле** (незатронутые биты сохраняются);
4. в очередь **2200** уходит сообщение **`(id-1):3645:<новый_байт>:<ts>\0`** (формат
   `<id0based>:<cell>:<value>:<ts>`).

**Подтверждено снифом (`write_sec` → `mpptd` → эмулятор):**
- `relay=1&mode=on` → `w 0x0000=03` (`EEPromWR`) → `w 0x0E3D=01`, **без post**;
- мультизапись `data=[[0x200,0x11],[0x201,0x22],[0x2D9,0x01],[0x2DA,0x02]]` → **4 пары
  «`cmd 3` + байт»**, адрес **«как есть»** (без `+0x1F0`), одинаково для EEPROM и RAM.

### Где правда про реле
- **`Relay_C` (`0x3E3`)** — **состояние** реле (только чтение).
- **`0x0E3D`** — **командная ячейка** реле: запись целого байта-маски.
- Это **разные ячейки**: `0x3E3` читаем, `0x0E3D` пишем (оба — для всех 3 реле одновременно,
  т.к. передаётся целый байт).

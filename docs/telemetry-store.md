# Хранилище рядов телеметрии (append-only, SD-safe)

Проект хранилища статистики рядов телеметрии устройств (МАП/КЭС) для ПАК
«Малина» (Raspberry Pi 3, SD-карта смонтирована в `/malina`). Документ —
**дизайн**; реализации ещё нет (см. §12).

## 1. Требования

- Не встроено в приложение — отдельный процесс/сервис (не библиотека в составе
  `malina-web`/демонов).
- Доступ **только с устройства** (loopback) по умолчанию; возможность открыть
  по сети — конфигом (+ аутентификация/`nftables`).
- Индексирование по составному ключу: **идентификатор устройства + время**.
- Быстрый поиск диапазона для вывода графиков.
- **Только накопление (append-only)**: штатных `update`/`delete` нет.
  - «Устройство» — **фиксированный** набор; «Время» — **монотонно возрастает**.
- Данные лежат на диске (`/malina`, SD) — **защита карты от периодической
  фоновой перезаписи блоков**. База **только растёт**.
- Индексация устроена так, что запись идёт **только в конец** индекса. Это должно
  сохраняться и в случае, когда в один момент времени пишутся две строки с
  одинаковым временем, но **сначала устройство с большим id, потом с меньшим**.
- Сервис **не выполняет периодических работ** по оптимизации/уплотнению хранения.
- **Низкое потребление памяти** — задача простая, сервису не следует «жрать» RAM.

## 2. Почему не обычные БД

| Класс | Проблема для задачи |
|---|---|
| РСУБД (Postgres/MariaDB/SQLite) | B-tree вставляет в середину листа (перезапись страницы, split); `autovacuum`, WAL-чекпоинты, `fstrim` → регулярная фоновая запись. Именно случай «равное время, устройство больше→меньше» = вставка в середину упорядоченного индекса. |
| TSDB (InfluxDB/Prometheus/VictoriaMetrics) | Фоновая **компакция/мерж SSTable-ов** и retention → периодическое переписывание файлов; высокий RSS. |
| RRDtool | Round-robin: **перезаписывает** старые слоты (не append-only). |
| LSM (RocksDB/LevelDB/Badger), Cassandra/Scylla | Само по себе append-friendly, но по умолчанию компактит; тяжёлый RSS (memtable, block-cache). Готового лёгкого «сервера» нет. |
| Redis AOF | Append-only лог, но набор данных в RAM (в проекте уже занят под кэш, `docs/redis-cache.md`), не диск-хранилище рядов. |
| Kafka/NATS-лог | Append-only, но не query-БД по диапазону времени без доп. слоя; Java/heavy для Pi3. |

Вывод: под жёсткие ограничения (append-only, индекс в конец, без фона, минимум
памяти) ни один «стандартный сервер» из репозиториев bookworm не подходит
целиком. Выбран **вариант A** — собственный лёгкий append-only сервис.

## 3. Выбранный подход (вариант A)

Отдельный лёгкий сервис (Go, один бинарник), который хранит ряды в
**append-only сегментных файлах, партиционированных по устройству**. Файлы —
только дозапись; по достижении предела сегмент **запечатывается** (immutable),
открывается новый. Никаких компакций, `update`/`delete`, фоновых
оптимизаций.

### Ключевая идея: партиционирование по устройству

Набор устройств фиксирован, время монотонно. Если у каждого устройства **свой
файл**, то «одно время, разные устройства в неправильном порядке» попадает в
**разные файлы** — общего упорядоченного индекса, куда нужно вставлять в
середину, не существует. Запись всегда идёт в конец «своего» сегмента, а значит
и вся индексная структура строится **только приращением в конец**.

Внутри серии время может повторяться — это просто очередной append; порядок не
переставляется. При чтении диапазона сортируется лишь небольшое множество
записей с одинаковой меткой времени.

## 4. Раскладка на диске

```
/malina/var/malina-ts/
  <device>/<metric>/seg-000001.ts      # запечатанный сегмент (immutable)
  <device>/<metric>/seg-000001.idx      # companion-индекс сегмента (append при печати)
  <device>/<metric>/seg-000002.ts      # активный сегмент (растёт)
```

- `device` — идентификатор устройства (фиксированный набор), `metric` — метрика
  (поле) или «снапшот» полей (см. §11, открытый вопрос).
- Имя сегмента монотонно (`seg-NNNNNN`) — сортировка по имени = по времени
  создания.
- Отдельного изменяемого манифеста нет: при старте раскладка и границы сегментов
  **пересобираются однократным последовательным сканом заголовков** (см. §6).

## 5. Формат сегмента и блока

Размер записи может быть переменным — навигация идёт **по блокам**, а блок
самодостаточен (сам описывает размеры и состав полей).

```
segment := hdr block* 
hdr :=
  magic        u32   "MTS1"
  format_ver   u16   # версия формата файла (не схемы)
  schema_ver   u16   # версия схемы полей (см. §8)
  device_id    u32
  metric_id    u16
  time_base    i64   # базовая метка времени сегмента, мс
  flags        u16
  crc32        u32

block :=
  bhdr :=
    rec_count     u16
    first_time    i64   # время первой записи блока, мс
    last_time     i64
    field_bitmap  u64   # какие поля присутствуют в блоке (по стабильным id)
    blen          u32   # длина тела блока
    crc32         u32
  records*
record :=
  time_delta  varint  # неотрицательная дельта от first_time (время монотонно)
  value*              # значения только присутствующих полей
```

- Записи в блоке **отсортированы по времени** и кодируются дельтами (малые числа
  ⇒ компактно).
- `field_bitmap` + стабильные числовые **id полей** обеспечивают эволюцию схемы
  (§8) без перестройки.
- Блок — единица чтения/записи; целевой размер ~16–64 КБ (баланс «индекс/память»
  и «атомарность записи»).

## 6. Индекс (разреженный, per-block)

- Индекс — одна запись **на блок**: `(first_time i64, offset u64, blen u32)`.
  Ориентир ~24 Б на блок.
- У **активного** сегмента индекс держится в памяти по мере роста (несколько
  десятков записей на блок — копейки), в `.idx` не пишется.
- При **запечатывании** индекс сегмента единоразово пишется в
  `<seg>.idx` **последовательной** записью (никаких перезаписей).
- При старте сервиса границы сегментов (`min/max time`, `schema_ver`) собираются
  сканом заголовков сегментов и блока «по цепочке» `blen` — последовательное
  чтение, быстро; **глобальный индекс в памяти не хранится**.
- `.idx` нужного сегмента подгружается лениво — только под конкретный запрос.

Так память не зависит от объёма истории: O(#открытых сегментов + #блоков
текущего активного), а не O(#строк).

## 7. Запись (write path)

1. В append-пришёл сэмпл `(device, metric, time, value)`.
2. Добавляется в **буфер текущего блока** активного сегмента
   (проверка: `time >= last_time` в рамках серии — монотонность; равное время
   допустимо).
3. Блок записывается в конец файла, когда заполнился.
4. **Запечатывание сегмента** по любому из условий: достигнут размер
   (напр. 8–64 МБ), сменилась `schema_ver`, или по таймеру «на всякий случай».
   При печати: сбросить буфер, записать `.idx`, `fsync`, открыть новый сегмент.
5. **`fsync`-политика:** **не** на каждую строку (жалко SD). `fsync` — при
   запечатывании и, опционально, по таймеру (напр. раз в 30–60 с). При потере
   питания теряется только «хвост» незапечатанного сегмента — для телеметрии
   допустимо (настраиваемо).

Никаких перезаписей существующих блоков, никаких фоновых задач.

## 8. Эволюция схемы v1→v2 без перестройки

Поскольку сегменты immutable, а запись — только в конец, схему версионируем:

- В заголовке сегмента — `schema_ver`; сегмент **однороден по схеме**.
- На деплое v2 текущий v1-сегмент **запечатывается**, открывается новый с
  `schema_ver=2`. Старые файлы не трогаются — **перестройки нет by design**.
- Поля адресуются **стабильными числовыми id** (как теги в Protobuf/Parquet), а
  не позицией. Добавление пары полей в v2:
  - старые блоки читаются по v1 (новых полей там просто нет);
  - новые поля появляются только в новых сегментах;
  - id и смысл существующих полей не сдвигаются.
- **Реестр схем** — небольшой статический конфиг в репозитории (`version →
  [ {id, name, type} ]`). Читатель по `schema_ver` сегмента выбирает схему
  декодирования; диапазон, пересекающий v1 и v2, мёржится, отсутствующие поля =
  «нет данных».
- Удаление/переименование поля: id остаётся зарезервированным, неизвестные id
  игнорируются. Несовместимая смена типа — новое поле с новым id.

## 9. Чтение диапазона (графики)

Запрос `(device, metric, t0, t1)`:

1. По каталогу/памяти выбираем сегменты устройства, чьи `[minTime,maxTime]`
   пересекают `[t0,t1]` (сегменты упорядочены — отбрасывание лишних O(log)).
2. В каждом сегменте **binary search по `.idx`** (по `first_time`) → стартовый
   блок.
3. **Последовательно** читаем блоки до выхода за `t1`, декодируем дельты,
   мёржим при необходимости.

Сложность: `O(log #блоков + объём диапазона)`. Размер записи в навигации **не
участвует** — потому переменная длина не мешает.

Ориентир скорости: старт — один seek (~1–5 мс на SD), дальше крупные
последовательные чтения. Сутки одной метрики при интервале 30 с ≈ 2880 точек ×
~8–16 Б ≈ 25–45 КБ ≈ 1–3 блока → единицы–десятки мс на график.

## 10. Память и «только растёт»

- Бюджет RSS: ориентир **~5–10 МБ** (Go-рантайм + буферы). Без block-cache,
  без memtable, без хранения истории в RAM.
- Память O(#устройств + #сегментов + #блоков активного), не O(#строк).
- «Только растёт»: при фиксированном наборе устройств и известной частоте
  записи объём предсказуем. Рано или поздно диск упрётся — вопрос архивации/выноса
  старых сегментов **вне штатной работы БД** (см. §11).

## 11. Открытые вопросы

1. **Гранулярность записи:** ряд = `{device, metric}` (серия на метрику) или
   ряд = снапшот всех полей устройства (одна серия, много полей в блоке через
   `field_bitmap`).
2. **Что храним:** сырые точки или уже статистику (min/max/avg за интервал).
3. **Архивация/ёмкость:** нужен ли ручной вынос старых сегментов (штатно — не
   удаляем).
4. **Протокол доступа:** HTTP/JSON (как у остальных сервисов проекта) vs
   что-то иное.
5. **`fsync`-политика:** допустимая потеря «хвоста» при отключении питания.
6. Набор устройств/метрик и частота — для оценки ёмкости SD.

## 12. Статус

**Дизайн.** Реализация (сервис, формат, реестр схем, юнит, конфиг, доступ по
loopback/сети) — отдельная задача. Смежное: кэш Redis — `docs/redis-cache.md`.

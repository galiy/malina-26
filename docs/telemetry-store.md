# Хранилище рядов телеметрии (append-only, SD-safe)

Проект хранилища рядов телеметрии устройств (МАП/КЭС) для ПАК «Малина»
(Raspberry Pi 3, SD-карта смонтирована в `/malina`). Документ — **дизайн**;
статус реализации — §13.

## 1. Требования

Требования — внешние, наблюдаемые. Внутренние решения — §3–§11; числовые пороги
(§1.7) уточняются под входные данные.

### 1.1. Функциональные

- Отдельный процесс/сервис — не библиотека в составе `malina-web`/демонов.
- Хранение телеметрии по ключу **(тип устройства, идентификатор устройства,
  время)**.
- На узле — **до 10 устройств** (обычно 1, редко до 5, 10 — предел).
- Хранятся **усреднённые за интервал** данные (усреднение делает
  продюсер/приложение, не хранилище). Частота записи — по умолчанию **1 раз в
  5 мин**; регулируется настройкой гранулярности **1–5 мин** в приложении.
- Штатно — **только накопление**: операций `update`/`delete` нет.
- Доступ **только с устройства** — Unix domain socket; сервис **не слушает сеть**
  (TCP нет).
- Сервис **не выполняет периодических работ** по оптимизации/уплотнению данных.
- Запись **не изменяет ранее записанные данные** (write-once на уровне носителя).
- **Низкое потребление памяти**, не зависящее от объёма истории.

### 1.2. Данные и версионность контракта

- Хранятся **только двоичные данные**; структуру полей определяет **контракт**,
  а не хранилище. Хранилище знает структуру полей контракта (встроенный реестр
  версий) для колоночной раскладки и проекции (§5, §8), но не их семантику и не
  изобретает собственную схему.
- Строка — **усреднённые значения за интервал гранулярности** (1–5 мин);
  агрегацию выполняет продюсер, хранилище получает готовый двоичный payload.
- Одна строка = **снапшот всех полей устройства** за интервал (одна серия на
  устройство); отдельных серий/файлов на метрику нет.
- **Версия контракта хранится на блок** (`u16`); все строки блока — одной версии
  и наследуют её (§5). В одном ответе (и в разных блоках/сегментах) могут быть
  строки **разных версий** — их согласование на стороне клиента (напр. для
  непрерывного графика).
- С ростом версии поля могут **добавляться и удаляться**.
- **Контракты — по типам устройств**: у каждого типа **своя нумерация версий**
  (`map`: v1…, `kes`: v1…), независимо. Все версии каждого типа, начиная с v1,
  **известны и клиенту, и серверу БД** (встроены в код обеих сторон; отдельных
  файлов нет, см. §1.6). Реестр версий ключуется парой `(device_type, version)`.

### 1.3. API (двоичный)

- **Запись:** клиент передаёт `тип устройства`, `идентификатор`, `время`,
  `версию`, `двоичное содержимое`.
- **Чтение:** возвращается `двоичное содержимое` строк (и их версия), **без
  JSON** — не раздувать канал.
- Поддерживается запрос **ряда целиком** и запрос **отдельных метрик**.
- **Продюсер** — горутина в составе `malina-web`; **потребитель** (графики) —
  страница в веб-админке (§12.11).

### 1.4. Режимы запросов

- **4.1.** Ряд целиком по одному устройству.
- **4.2.** Выбранные метрики по одному устройству.
- **4.3.** Выбранные метрики по нескольким устройствам.
- **4.4.** Ряд целиком по нескольким устройствам.
- В любом режиме **за один запрос данные отбираются за один и тот же период**
  `[from, to]` (единый интервал для всех выбранных устройств/метрик).
- **Валидация режима** (иначе отказ, §10 `status=1`): 4.1/4.2 — ровно одно
  устройство; 4.3/4.4 — одно и более; 4.2/4.3 — непустой список метрик; 4.1/4.4 —
  метрики не задаются. Пустой список устройств — ошибка (не «все устройства»).
- **Лимит выборки:** период `[from,to]` ограничен (`-maxrange`, дефолт ~400 суток)
  и число строк в ответе — (`-maxrows`, дефолт 300 000). При превышении —
  **отказ** (код статуса, §10), а не частичный ответ: это держит пиковую память
  чтения в бюджете RSS (§1.7) и отсекает запросы «за годы».

### 1.5. Идентификация устройств и раскладка

- Устройство идентифицируется **типом** и **идентификатором** — оба строки **до 10
  символов** (§5); запрещены `/`, NUL и значения `.`/`..` (защита от выхода за
  каталог данных). **Набор типов открыт**: могут появляться новые типы (`map`,
  `kes`, `mbms` и др.). Новый тип = новая папка + зарегистрированные контракты
  `(type, version)`; формат хранилища и код при этом не меняются.
- Устройства разных типов хранятся **в разных папках**; устройство — отдельная
  папка внутри папки своего типа.
- **Никаких отдельных файлов конфигурации БД, кроме самих данных.** Достаточно
  структуры папок и лежащих в них файлов (см. §1.6).

### 1.6. Эксплуатация данных

- Удаление **части** файлов допустимо: в рядах образуются **пропуски**; сервис
  это переносит и продолжает работу.
- Удаление **всей** БД: сервис **автоматически инициализируется** (создаёт
  структуру заново при первой записи; на чтение отдаёт пусто).
- Служебные параметры сервиса (путь, лимиты) задаются unit-файлом/CLI, **не**
  файлами внутри каталога данных.
- Не допускать перегрузку ФС папками с огромным количеством содержимого:
  раскладка ограничивает число записей в каталоге (§4).

### 1.7. Производительность (измеримые пороги)

- Запись: ≥ 100 строк/с (запас к пику 10 устройств × 1/мин ≈ 0,17 стр/с);
  задержка ответа (p99) ≤ 50 мс — клиент **не блокируется** на запись на диск
  (ответ после постановки в очередь единому writer'у, §7).
- Чтение диапазона за сутки по одному устройству — p95 ≤ 50 мс; за 30 суток —
  p95 ≤ 300 мс.
- Память: RSS сервиса ≤ 16 МиБ и **не зависит от объёма истории**
  (O(#устройств + #сегментов + #блоков активного), не O(#строк)). Лимиты выборки
  (§1.4) ограничивают пиковую память ответа чтения.

### 1.8. Целостность и восстановление

- Каждый блок/сегмент защищён контрольной суммой (CRC); при чтении — проверка.
- Повреждённый блок/сегмент **обнаруживается** и не используется молча (пропуск +
  явная отметка в логе/ответе).
- После сбоя питания: запечатанные сегменты не теряются; незавершённый «хвост»
  активного сегмента отбрасывается/обрезается по целостности, без порчи
  остального.
- Запечатанный сегмент — **write-once**.

### 1.9. Безопасность

- Доступ — **только через Unix domain socket** (`/run/malina-ts/tsdb.sock`,
  права `0600`, владелец — сервис).
- **Сетевого доступа нет:** сервис не слушает TCP; аутентификация не требуется
  (изоляция обеспечивается правами сокета и локальностью).

### 1.10. Жизненный цикл данных

- Штатно данные **не удаляются**; хранилище только растёт.
- Исчерпание ёмкости **сервис не отслеживает** — контроль внешний (внешний
  мониторинг раздела), вне рамок сервиса.
- Вынос/архивация старых сегментов — отдельный ручной процесс, вне штатной работы
  сервиса.
- **Глубина хранения** зависит от свободного места на разделе. Ориентир:
  `bytes/год/устройство ≈ (525600 / интервал_мин) × (payload + ~8 Б overhead)`.
  При payload ≈ 50 Б: 5 мин → ~6 МБ/год, 1 мин → ~30 МБ/год на устройство;
  10 устройств при 1 мин → ~0,3 ГБ/год. Объёмы малы — место на разделе
  покрывает годы; ограничение при необходимости — ручным удалением старых
  сегментов (пропуски допустимы, §1.6).

### 1.11. Ограничения и допущения (не требования)

- Время в ряду **неубывает**; равные метки **допустимы**.
- Для записей с равной меткой времени порядок = порядок поступления; порядок при
  чтении такого множества **не гарантирован** (допускается сортировка на клиенте).
- Построение файлов/индекса только дозаписью в конец — **следствие** выбранной
  раскладки (§3), а не внешнее требование.
- Состав устройств задаётся продюсером/клиентом; сервис допускает отсутствие или
  появление папок устройств (пропуски, §1.6).
- Запись в хранилище — **единая writer-горутина сервиса**: клиенты кладут строки
  в очередь и не блокируются; writer раскладывает их по сегментам/блокам.

## 2. Почему не обычные БД

| Класс | Проблема для задачи |
|---|---|
| РСУБД (Postgres/MariaDB/SQLite) | B-tree вставляет в середину листа (перезапись страницы, split); `autovacuum`, WAL-чекпоинты, `fstrim` → регулярная фоновая запись. Случай «равное время, устройство больше→меньше» = вставка в середину индекса. |
| TSDB (InfluxDB/Prometheus/VictoriaMetrics) | Фоновая **компакция/мерж SSTable-ов** и retention → периодическое переписывание файлов; высокий RSS; собственный формат вместо бинарного контракта проекта. |
| RRDtool | Round-robin: **перезаписывает** старые слоты (не append-only). |
| LSM (RocksDB/LevelDB/Badger), Cassandra/Scylla | Append-friendly, но по умолчанию компактит; тяжёлый RSS (memtable, block-cache); свои схемы/файлы конфигурации. |
| Kafka/NATS-лог | Append-only, но не query-БД по диапазону и метрикам без доп. слоя; Java/heavy для Pi3. |

Вывод: под жёсткие ограничения (append-only, индекс в конец, без фона, минимум
памяти, бинарный контракт, никаких доп. файлов) не подходит ни один штатный
сервер. Выбран **вариант A** — собственный лёгкий append-only сервис.

## 3. Выбранный подход (вариант A)

Отдельный лёгкий сервис (Go, один бинарник): **append-only сегментные файлы,
партиционированные по типу и устройству**. Файлы только дописываются; по
достижении предела сегмент **запечатывается** (immutable), открывается новый.
Никаких компакций, `update`/`delete`, фоновых задач.

### Ключевая идея: партиционирование по устройству

Набор устройств фиксирован в пределах узла, время в ряду неубывает. Если у
каждого устройства **свой файл**, то «одно время, разные устройства в неправильном
порядке» попадает в **разные файлы** — общего упорядоченного индекса, куда надо
вставлять в середину, не существует. Запись всегда идёт в конец «своего»
сегмента, и вся индексная структура строится **только приращением в конец**.

Внутри одного устройства время может повторяться — это очередной append; порядок
не переставляется, при чтении множества с равной меткой допускается сортировка на
клиенте.

### Ключ ряда и индекса

- **Ключ ряда** = `(device_type, device_id, time)` — ровно два логических поля
  идентификации + время (§1.1).
- `device_type` и `device_id` **фиксированы для сегмента** — лежат в заголовке
  сегмента и в пути (`<type>/<device_id>/...`), поэтому **в каждой записи не
  дублируются** (экономия на 50-байтных строках). В записи хранится только
  `time` (дельтой от `first_time`).
- **Ключ индекса** внутри сегмента — `time`: блоки упорядочены по времени,
  разреженный индекс навигации строится по `first_time` (§6). Полный ключ
  восстанавливается как `(заголовок сегмента, time)`.
- В **ответах** каждый ряд отдаёт ключ целиком — `device_type, device_id, time`
  (§10), — чтобы мультиустройственные запросы (4.3–4.4) были однозначны.
- При **проекции метрик** (§8) ключ ряда не меняется: тот же
  `(device_type, device_id, time)`, меняется только набор полей в payload.

## 4. Раскладка на диске

```
/malina/var/malina-ts/
  <type>/<device_id>/<bucket>/seg-NNNNNN.ts
```

- `<type>` — тип устройства: `map` (МАП), `kes` (КЭС), `mbms` (BMS — отдельный ряд
  с тем же `device_id`, см. `docs/stat.md`). Типы — разные папки (§1.5).
- `<device_id>` — серийник устройства (строка; сейчас числовой, но заложена строка).
- `<bucket>` — подкаталог для ограничения числа файлов в каталоге (§1.6):
  номер бакета = `seg_seq / K` (напр. `K = 1024`), где `seg_seq` — счётчик
  сегментов **данного устройства**. Имя — числовое; сортировка бакетов и
  сегментов **числовая** = порядок по времени.
- `seg-NNNNNN.ts` — сегмент; `NNNNNN` монотонно (**счётчик сегментов устройства**),
  сортировка по имени = по времени.
- Никаких отдельно лежащих индексов/конфигов: индекс запечатанного сегмента —
  **в хвосте того же файла** (§5), состояние пересобирается сканом дерева.
- Удаление части файлов → пропуски; отсутствие всего дерева → инициализация при
  первой записи (§1.6).

## 5. Формат сегмента и блока

Данные — двоичный контракт; хранилище знает структуру полей контракта (§1.2),
строки переменной длины, поэтому навигация — **по блокам**, блок самодостаточен.

```
segment := hdr block* [index_footer]
hdr :=
  magic        u32   "MTS1"
  format_ver   u16   # версия формата файла (не контракта); текущая = 2
  device_type  str   # тип устройства (map, kes, …; набор открыт, §1.5)
  device_id    str   # len u8 + байты UTF-8 (серийник; сейчас числовой, заложена строка)
  time_base    i64   # базовая метка времени сегмента, мс
  flags        u16
  crc32        u32

block :=
  bhdr :=
    rec_count    u16
    first_time   i64   # время первой записи блока, мс
    last_time    i64
    version      u16   # версия контракта БЛОКА в нумерации своего типа устройства (§1.2)
    col_count    u16   # число колонок (время + поля контракта)
    blen         u32   # длина тела блока
    crc32        u32
  col_offsets*        # на колонку: field_id u16 | offset u32 | len u32
                      #   field_id=0 — колонка времени; остальные — поля контракта;
                      #   offset — смещение от начала тела блока (после bhdr + col_offsets)
  col_time            # rec_count дельт varint (неотрицательные; время неубывает)
  col_<field_id>*     # значения каждого поля подряд (все строки блока)

index_footer :=                # только у запечатанного сегмента, в конце того же файла
  entries*: first_time i64 | offset u64 | blen u32   # сначала записи
  entry_count  u32            # затем — хвост (читается с конца)
  magic        u32   "MTSX"
  crc32        u32            # по entries (без entry_count/magic)
```

- Строки в блоке упорядочены по времени; время — колонка дельт (varint).
- Поля снапшота раскладываются **по колонкам** (§8): колонка на поле контракта.
  Все строки блока — **одной версии контракта** (иначе колонки неоднородны);
  версия лежит в `bhdr.version`, строка её наследует.
- `col_offsets` задаёт смещение/длину каждой колонки: чтение подмножества метрик
  декодирует **только нужные колонки**, а не весь снапшот.
- `field_id` (в `col_offsets`) = идентификатор метрики; `metric_ids` в запросах
  (§9) — те же `field_id` контракта.
- Формат значения поля задаётся типом поля из реестра контракта (varint/fixed/
  bytes); хранилище кодирует/декодирует по реестру, семантику не знает.
- Сжатия нет: компактность дают дельта-кодирование времени (varint) и колоночная
  раскладка; значения полей хранятся как есть (без gzip/zstd).
- **Ключ `(device_type, device_id)`** берётся из заголовка сегмента, `time` — из
  колонки времени (`first_time + Σ delta`); в записи ключ не дублируется (§3).
- Блок — единица чтения/записи; размер зависит от потока: при частых записях
  накапливается до ~16–64 КБ, при редких (наш случай) блок может быть мал —
  вплоть до одной строки.

## 6. Индекс (без отдельных файлов)

- Ключ индекса — **время** (`first_time` блока); навигация по диапазону
  `[from,to]` внутри сегмента.
- Индекс — запись **на блок**: `(first_time, offset, blen)`.
- **Активный** сегмент: индекс держится в памяти по мере роста; после сбоя
  питания полный per-block индекс восстанавливается сканом заголовков блоков по
  цепочке `blen` (теряется только хвост недописанного блока, §1.8).
- При **запечатывании**: индекс один раз дописывается в **хвост того же файла**
  (`index_footer`), не в отдельный файл (§1.6). Перезаписей нет.
- При старте состояние пересобирается **обходом дерева**: читаются заголовки
  сегментов (`time_base` = minTime, `device_type`, `device_id`); maxTime
  запечатанного сегмента — из `index_footer` (последняя entry), активного —
  «растёт» (ведётся в памяти). Если footer отсутствует/повреждён (обрезанный
  хвост, ручное удаление), индекс пересобирается сканом блоков по цепочке `blen`
  **с проверкой CRC тела**: недописанный/битый блок (в т.ч. обрыв внутри строки)
  отбрасывается, файл обрезается до последнего целого блока.
- Глобальный индекс в памяти не хранится; footer нужного сегмента читается
  лениво под конкретный запрос.

Память не зависит от объёма истории: O(#устройств + #сегментов + #блоков
активного).

## 7. Запись (write path)

Продюсер — **горутина в составе `malina-web`**; транспорт — Unix-сокет (§10).

1. Клиент (продюсер) шлёт батч — одну или несколько строк
   `(device_type, device_id, time, version, payload)` (§1.3).
2. Сервис принимает кадр, кладёт строки в **очередь единому writer'у** и сразу
   отвечает `ack` — клиент **не блокируется** на запись на диск (§1.7).
3. **Единственная writer-горутина сервиса** сериализует записи всех устройств:
   раскладывает строки по блокам (все строки блока — одной версии контракта; при
   смене `version` блок закрывается, §5). Проверка `time >= last_time` —
   неубывание; равное время допустимо; при `time < last_time` строка отклоняется
   (ошибка/лог, не пишется).
4. **Flush — сразу при получении записи** (без таймера): блок немедленно
   дописывается в конец файла активного сегмента (обычная `write`, без fsync).
   При низкой частоте блок может содержать одну строку — это допустимо.
5. **Запечатывание** при достижении размера (напр. 8–64 МБ) или границы бакета;
   при печати: дописать `index_footer`, `fsync`, открыть новый сегмент.
6. **Периодического fsync/таймера нет**; `fsync` — при запечатывании и при
   аккуратном завершении. Потеря при отключении питания — окно kernel-writeback.

Никаких перезаписей существующих блоков, никаких фоновых задач.

## 8. Версии контракта и проекция метрик

- Контракт определяет поля снапшота; хранилище раскладывает снапшот на колонки
  при записи и собирает обратно при чтении, используя **встроенный реестр версий**
  `(device_type, version) → схема` (у каждого типа устройств — своя нумерация
  версий, §1.2). Семантику полей хранилище не знает.
- Для режимов с **выбором метрик** (§1.4.2–4.3) сервер **декодирует только
  выбранные колонки** (по `col_offsets`, §5) и сериализует их в той же версии
  контракта (контракт описывает необязательность полей). Версия строки — из
  блока, сохраняется.
- Схемы версий живут **в коде** клиента и сервера (никаких файлов, §1.6). Поля
  могут добавляться/удаляться между версиями; неизвестные/удалённые метрики
  игнорируются.
- Один ответ может смешивать версии; клиент сам решает, как их согласовать
  (§1.2).
- **Зарегистрированные схемы** (в коде, пакет `daemons/lib/tscontract`; состав —
  `docs/stat.md`): `payload = presence[ceil(n/8)] | значения присутствующих полей
  в порядке схемы`. Типы значений: `FTInt` (zigzag-varint), `FTU8`, `FTU16` (LE),
  `FTFloat` (IEEE-754 LE), `FTBytes` (len-varint + байты).
  - `map` v1 — 26 колонок (регистры МАП);
  - `kes` v1 — 15 колонок (ячейки КЭС);
  - `mbms` v1..v32 — BMS отдельным рядом (`device_id` — тот же, что у МАП):
    `Vn` = `n` ячеек × (u16+u8+u8).
  Хранилище раскладывает поля по колонкам, семантику не интерпретирует.

## 9. Чтение (режимы запросов)

Единая модель: запрос `(mode, device_type, device_ids[], metric_ids[], from, to)`
— период **один на запрос** (§1.4). Ответ — поток двоичных строк
(§1.3), каждая: `device_type, device_id, time, version, payload`.

1. По дереву выбираем сегменты нужных `(type, device_id)`, чьи
   `[minTime,maxTime]` пересекают `[from,to]`.
2. В каждом сегменте — binary search по индексу → стартовый блок.
3. Последовательно читаем блоки до выхода за `to`; декодируем дельты; для
   выбранных метрик — проекция (§8); для «ряда целиком» — собираем все колонки
   блока в снапшот (§8).

Сложность: `O(log #блоков + объём диапазона)`. Размер строки в навигации не
участвует — переменная длина не мешает.

Режимы (соответствуют §1.4): 4.1 all-metrics/один device; 4.2 selected/один;
4.3 selected/несколько; 4.4 all/несколько.

## 10. Транспорт (двоичный, локальный)

- **Только Unix domain socket** `/run/malina-ts/tsdb.sock` (права `0600`).
  Сервис **не слушает TCP** — сетевого доступа нет (§1.9).

Бинарные кадры (little-endian; `str` = длина `u8` + байты UTF-8; varint — LEB128):

```
write_frame :=                 # кадр записи (батч)
  magic        u32   "MTSW"
  count        u16             # число строк
  rows*:
    device_type str            # тип устройства (map, kes, …; набор открыт)
    device_id   str
    time        i64            # мс, UTC
    version     u16            # версия контракта (нумерация своего типа устройства)
    payload_len varint
    payload     bytes          # снапшот полей (сериализация контракта)
  crc32        u32

write_reply :=                 # ответ на запись
  magic        u32   "MTSK"
  code         u8             # 0 = ok
  written      u32            # принято в очередь (не факт записи на диск, §7)
  crc32        u32

read_frame :=                  # кадр чтения
  magic         u32   "MTSR"
  mode          u8             # 1..4 (§1.4)
  device_type   str            # тип устройства (набор открыт)
  device_ids_len u8
  device_ids*   str
  metric_ids_len u8            # 0 = все метрики (ряд целиком)
  metric_ids*   u16            # field_id контракта (§5)
  from          i64
  to            i64
  crc32         u32

read_reply :=                  # поток ответа
  magic        u32   "MTSA"
  status       u8             # 0 = ok; 1 = неверные параметры/режим;
                              # 2 = период > лимита; 3 = слишком много строк (§1.4)
  rows*:                      # при status != 0 строк нет
    device_type str
    device_id   str
    time        i64
    version     u16
    payload_len varint
    payload     bytes          # снапшот (ряд целиком) или проекция метрик (§8)
  magic        u32   "MTSE"    # маркер конца
  crc32        u32
```

## 11. Память и «только растёт»

- Бюджет RSS: ориентир **~5–10 МБ** (Go-рантайм + буферы). Без block-cache, без
  memtable, без истории в RAM.
- Память O(#устройств + #сегментов + #блоков активного), не O(#строк).
- «Только растёт»: при известной частоте объём предсказуем. Исчерпание ёмкости —
  сигнал/алерт; архивация старых сегментов — вне штатной работы сервиса (§1.10).

## 12. Решения по открытым вопросам (закрыты)

1. **Модель:** строка = `(device_type, device_id, time, version, binary_payload)`;
   ключ/индекс `(device_type, device_id, time)`.
2. **Модель хранения:** одна серия на устройство — строка = **снапшот всех
   полей** за интервал; отдельных серий/файлов на метрику нет (не плодим иноды).
   Поля снапшота в блоке — **колонками** (§5): запрос выбранных метрик читает
   только нужные колонки, не весь снапшот. Агрегация — у продюсера; хранилище
   раскладывает/собирает поля через встроенный реестр версий (§8); контракт
   допускает частичную сериализацию.
3. **Транспорт:** двоичные кадры по **Unix domain socket** (локально; сервис не
   слушает сеть); запись — **батчем** (одна или несколько строк в запросе),
   чтение — поток строк.
4. **Запись/`fsync`:** **единая writer-горутина** сервиса, клиент **не
   блокируется** (ответ после постановки в очередь); **flush сразу при получении
   записи** (без таймера); периодического fsync нет; fsync — на запечатывании и
   при завершении (§7).
5. **Входные данные:** до 10 устройств (обычно 1, редко до 5); запись раз в
   5 мин по умолчанию, гранулярность 1–5 мин (настройка приложения); данные —
   усреднённые (§1.1); payload ≈ **50 Б** в среднем. Ёмкость:
   `bytes/год/устройство ≈ (525600 / интервал_мин) × (payload + ~8 Б)`
   (50 Б: 5 мин → ~6 МБ/год, 1 мин → ~30 МБ/год; 10 уст. при 1 мин → ~0,3 ГБ/год).
   Глубину задаёт свободное место; «хранить всё» реалистично.
6. **Раскладка:** `<type>/<device_id>/<bucket>/seg-NNNNNN.ts`; бакеты ограничивают
   число файлов в каталоге (§4).
7. **Файлы-конфиги отсутствуют:** всё — дерево папок и файлы данных; индекс — в
   хвосте сегмента (§6).
8. **Время:** Unix-время в **миллисекундах** (int64, UTC); монотонность и
   гранулярность обеспечивает продюсер.
9. **Глубина хранения:** штатно храним всё (объёмы малы, см. п.5); при исчерпании
   — алерт; при необходимости старое удаляется вручную (пропуски).
10. **Контракты:** отдельные для **каждого типа устройства**, независимая
    нумерация версий; реестр ключуется парой `(device_type, version)` (§1.2, §8).
    **Набор типов открыт** — новый тип добавляется папкой + его контрактами, без
    изменения формата хранилища (§1.5).
11. **Продюсер** — горутина в составе `malina-web`; **потребитель** — страница в
    веб-админке (§1.3, §9).

## 13. Статус

**Реализовано** — демон `daemons/tsdb` (бинарник `malina-tsdb`) соответствует
§5/§8/§10:

- колоночный блок (`bhdr` + `col_offsets` + колонки) — `daemons/tsdb/format.go`;
- хранилище: строковые `type`/`id`, серии, бакеты, запечатывание, скан/каталог,
  пропуски, авто-инициализация; **единая writer-горутина**, клиент не блокируется,
  flush сразу — `daemons/tsdb/store.go`;
- реестр контрактов `(device_type, version)`, проекция метрик, реальные схемы
  `map` v1 / `kes` v1 / `mbms` v1..v32 (`docs/stat.md`) — `daemons/lib/tscontract`;
- двоичные кадры `MTSW/MTSR/MTSA/MTSE` (+ ответ `MTSK`), crc32, varint, `str` —
  `daemons/tsdb/wire.go`;
- транспорт — только Unix-сокет (локально, без сети) — `daemons/tsdb/api.go`,
  `daemons/tsdb/main.go`;
- тесты — `daemons/tsdb/*_test.go`.

Юнит `daemons/tsdb/tsdb.service` → `/etc/systemd/system/malina-tsdb.service`,
бинарник `/malina/usr/local/sbin/malina-tsdb`, данные — `/malina/var/malina-ts`;
ставится `deploy/update.sh` / `stage2.sh` / `install.sh`.

Осталось (вне сервиса): **продюсер-горутина** в `malina-web` (пишет контракты
`map`/`kes`/`mbms` в tsdb); страница графиков; развёртывание на устройстве —
после подключения продюсера.

Смежное: кэш Redis — `docs/redis-cache.md`.

# Тип BMS: AntBMS-DSP (дисплейный порт, пассивный)

**Режим:** пассивное прослушивание. **Протокол:** классический ANT live-кадр 140 Б
(`AA 55 AA FF`). **Скорость:** **19200 8N1, фиксированная** (как в `bmslistener`).

**Область типа:** это **дисплейный порт** ANT BMS (DSP). Прочие интерфейсы ANT BMS
(RS485/CAN) — **отдельный тип** (другая шина), здесь не рассматриваются.

## 1. Проект-источник

Референс — `../sunReceiver`:
- `daemons/bmslistener/bmslistener.c` — пассивный слушатель ANT BMS (C, arm);
- `docs/antbms.md` — распиновка/подключение, скорость;
- `docs/antbms/antbms-protocol-status-frame.md` — формат 140-байтного кадра;
- `docs/antbms/antbms-live-frame-decoded.md` — разбор живого кадра;
- `docs/modules/bms-listener.md` — демон на ПАК «Малина» (shm 2018).

Что берём как референс: пассивное чтение, marker+CRC валидация, offsets полей,
способ именования по ёмкости.

## 2. Транспорт и сигнатура

- Serial, raw **8N1**, приём включён; TX не используется (только чтение).
- Пассивный поток: 140-байтные кадры, шаг 140 байт, ~4–7 кадр/с.
- Заголовок `AA 55 AA FF`; **CRC**: `sum(f[4..137]) & 0xFFFF == BE16(f[138..139])`.
- Ограничение приёмного буфера и выделение кадров по маркеру (как `bms_feed`).
- **Серийного номера в кадре нет.**

## 3. Нюанс пассива (keep-alive)

BMS начинает вещать только после keep-alive **`5A 5A 00 00 01 01`** каждые ~250 мс,
который шлёт **родной дисплей** (линия RXD BMS). `bmslistener` работает read-only
именно потому, что дисплей остаётся подключён (адаптер слушает линию TXD BMS).
→ Наш тип — тоже **только приём**; требуется, чтобы источник keep-alive (дисплей) был
подключён. Сами keep-alive **не шлём** (правило RO). Подтверждено: стабильно работает.

## 4. Probe: критерии и сценарий

**Вход — открытый источник** (serial, raw 8N1); скорость (**19200**) задаёт
**оркестратор**. Probe порт не открывает и скорость не меняет.

1. **Пассивно** слушать окно **500 мс**.
2. Найти маркер `AA 55 AA FF`, собрать 140 байт, проверить CRC.
3. **Признание своим:** CRC валидна **и** `1 ≤ cell_count(f[123]) ≤ 16` (контракт —
   макс. 16 ячеек) **и** напряжения ячеек правдоподобны (напр. 1.0–5.0 В) **и**
   `soc(f[74]) ≤ 100`.
4. Валидный кадр → **Found** (BASE, §7). Нет в окне → **NoAnswer**.

> Сразу после подключения, пока дисплей keep-alive'ом не «раскачал» вещание, первые окна
> могут дать `NoAnswer`; первичное обнаружение может занять несколько раундов отстойника
> (окно **500 мс** не расширяем — осознанно).

## 5. Опрос: сценарий (модуль опроса)

- Порт — **«нулевой»** (одно вещающее устройство, без адресации).
- Блокирующее чтение с таймаутом окна → вычленить целостный 140-байтный кадр по
  маркеру → CRC → разобрать → смапить в контракт → вернуть.
- Нет валидного кадра за окно → источник потерян.

## 6. Мэппинг на общий контракт (`docs/bms-reader.md` §1)

Контракт — бинарный фиксированной длины, макс. 16 ячеек (§1). Многобайтовые — BE.
**Полный мэппинг** (все поля §1; у Ant отсутствующие → `0`):

| Поле §1 | Источник AntBMS (offset, BE) |
|---|---|
| `cell_count` | u8 `123` (ограничить 16) |
| `temp_count` | `6` (в кадре фиксировано 6 каналов) |
| `flags` | b0=f`103` charge_mos, b1=f`104` discharge_mos, b2=f`105` balancer |
| `cells_mv[0..15]` | BE16 `6+2i`, мВ, i < `cell_count`; остальные `0` |
| `temps_dc[0..7]` | s16 `91+2i` (°C) ×10, i < 6; 6..7 → `0` |
| `current_da` | s32 `70` (0.1 А) ×10 — знак как есть: разряд «+», заряд «−» |
| `power_w` | s32 `111` (прямое поле; у EnBMS — производное U·I) |
| `soc_dp` | u8 `74` (%) ×10 |
| `soh_dp` | — → `0` |
| `cap_mah` | u32 `75` (µА·ч) /1000 |
| `remaining_mah` | u32 `79` (µА·ч) /1000 |
| `rated_mah` | — → `0` |
| `cycles` | — → `0` |
| `total_cv` | Σ `cells_mv` / 10 (мВ → 0.01 В) — производное (у EnBMS поле прямое) |
| `port_cv` | — → `0` |
| `balance_mask` | u32 `132` |
| `mode` | по знаку `current_da` (см. ниже) |
| `alarm` | см. «Раскладка `alarm`» ниже |

### Определение `mode`

Прямого поля режима в кадре нет; режим — по **току** (конвенция: разряд «+», заряд «−»):

| Условие | Код `mode` (канон, `docs/bms-reader.md` §1) |
|---|---|
| `current_da` > 0 | `0x01` Разряд |
| `current_da` < 0 | `0x02` Заряд |
| `current_da` == 0 | `0x00` Ожидание / standby |

Порог не применяется: standby — **только при точном нуле** тока. Старший байт `mode` —
резерв (`0`). Вне контракта: `cycle_ah` (u32 `83`), `uptime_s` (u32 `87`), MOS-напряжения
(BE16 `124–129`) — отказ.

### Раскладка `alarm` (AntBMS)

Поле `alarm` — 19 Б (152 бита); значимо **28 бит**, остальное `0`.

| Биты | Поле | Ед. |
|---|---|---|
| 0..3 | `charge_mos` — код состояния (f`103`) | код 0..15 |
| 4..7 | `discharge_mos` — код состояния (f`104`) | код 0..15 |
| 8..11 | `balancer` — код состояния (f`105`) | код 0..10 |
| 12..27 | `system log` (u16, f`136`): 0–4 Status, 5–9 battery#, 10–14 order, 15 chg/dis | — |
| 28..151 | — (не используется, `0`) | — |

Коды MOS — таблицы в `../sunReceiver/docs/antbms/antbms-protocol-status-frame.md`.

## 7. Идентификатор

Серийника нет → BASE от **ёмкости** (как `bmslistener`: `AntBms <ёмкость> A/h`).
Идентификатор: **`AntBMS-DSP-<capacity_ah>`** (напр. `AntBMS-DSP-320`), при
необходимости `+` число ячеек (`AntBMS-DSP-<Ah>-<cells>`).

**ID = BASE**, без суффикса `-NNNNN` и без реестра. Две AntBMS одной ёмкости
получат одинаковый ID; их телеметрия попадёт в один ряд tsdb. Это принятый риск:
уникальность BASE обеспечивает пользователь.

**Транспорт/нагрузка USB.** AntBMS-DSP отдаёт пассивный поток. Чтение —
пакетное (`Port.Read` до 256 Б за `syscall.Read`), а не побайтовое. Это снижает
число `syscall.Read`; на `.68` замер показал, что bulk-IN/IRQ при этом не
снизились (нужен `latency_timer`). Кадр и период опроса не меняются.

# БМС-Прокси: требования

> Статус: **реализовано**; документ описывает фактическое поведение демона и
> контракт отдачи (стабильный слот, молчание при отсутствии данных).

## 1. Назначение

`bms-proxy` — компонент, работающий **последовательным портом (RS485)** и
отдающий инвертору телеметрию конкретной BMS. Инвертор запрашивает номера
последовательно, в цикле; диапазон зависит от его настройки — **`0..15`** или
**`1..16`** (`addr_mode`, §8; на проде — `1..16`).

Номер запроса (ADR) мапится на **стабильный слот shm `bms-reader`** согласно
`addr_mode`: `"1-16"` → `slot = ADR-1`, `"0-15"` → `slot = ADR`. Слот не
перенумеровывается при выпадении других BMS, поэтому инвертор всегда получает
ту батарею, которую запросил, либо молчание.

Прокси не опрашивает BMS сам, не знает протоколов типов и не пишет в
телеметрию — он читает уже подготовленный бинарный контракт `bms-reader` из
POSIX shared memory и транслирует его в ответ на порту.

Цель — дать инвертору простой доступ «номер → телеметрия» через живые BMS, не
заставляя его разбираться в раскладке shm, генерациях и диагностике живости.

## 2. Источник данных

- Сегмент: `/dev/shm/malina-bms-state`.
- Магия: `0x424D5342` (`"BSMB"`), версия `1`.
- Раскладка (синхронизирована с `daemons/bms-reader/shm.go` и
  `web/internal/web/bmsstate.go`):

  ```
  [header 64 Б][list: 16 записей × 200 Б][slots: 16 × (32 + 112 Б)]
  ```

- Список (`Items`) — по одному на слот: метаданные устройства
  (`id`/логический ID `BASE`, `base`, `source`, `type_id`, `state`, `framing`,
  `gen`, `last_seen`).
- **ID = `BASE`**, без суффикса и реестра. У нескольких BMS может быть одинаковый
  `id`/`base`; записи различаются слотом и `gen`. Это принятый риск; прокси
  обязан публиковать все живые слоты, включая дубли BASE.
- Телеметрия (`Slots`) — бинарный payload `bmscontract.Size` (107 Б), доступен
  по индексу слота при `state==1` и совпадении `gen`.

Список пишется **только** оркестратором `bms-reader` (архитектура §12), телеметрия
— пулером. Прокси — сторонний читатель, на запись не претендует.

## 3. Смещения записей списка (200 Б)

| Поле | Смещение | Размер | Тип |
|---|---|---|---|
| `seqlock.state` | 0 | 4 | uint32 (1 = занят) |
| `seqlock.seq` | 8 | 8 | uint64 (bit0 = идёт запись) |
| `id` / логический ID | 16 | 50 | строка, `BASE` |
| `base` | 66 | 50 | строка |
| `source` | 116 | 64 | строка |
| `type_id` | 180 | 1 | uint8 |
| `state` | 181 | 1 | uint8 (0 = lost, 1 = ok) |
| `framing` | 182 | 1 | uint8 |
| `gen` | 184 | 8 | uint64 LE |
| `last_seen` | 192 | 8 | uint64 LE (unix, секунды) |

## 4. Определение «живой» BMS

Слот отдаётся, если он занят и данные не протухли:

```
отдаём ⇔ (state == 1) И (now − last_seen ≤ 4 с)
```

Пояснение:

- `state == 1` — основной признак: `bms-reader` снимает запись по
  `MissThreshold` (см. `loseDevice` в `daemons/bms-reader/orchestrator.go`).
- `last_seen` — страховка от зависшего `bms-reader`: пулер обновляет его сразу
  после каждого успешного опроса, штатно раз в секунду.
- Порог **4 с** покрывает один медленный цикл опроса (`0x42` с ретраем + `0x44`)
  и при этом гарантированно перекрывает паузу рескана (≤ 200 мс, arch §6.4).
  Данные старше порога не отдаются — прокси молчит.

## 5. Алгоритм ответа слушателя на запрос инвертора

Слушателю **нельзя** шариться по shm-листу и вычислять, кто жив — на запрос
надо отвечать максимально быстро. Поэтому слушатель на каждый запрос читает
слот напрямую из shm (фонового списка и его обновления нет, см. §7).

Обработчик запроса `onRequest(adr)` мапит адрес инвертора на стабильный слот
по виду адресации `addr_mode` (§8), затем отвечает:

```text
# slot — стабильный слот shm
если addr_mode == "1-16": slot = adr - 1   # инвертор адресует 1..16
иначе:                   slot = adr       # инвертор адресует 0..15
если slot < 0 или slot >= 16: вернуть МОЛЧАТЬ

item = read(shmPath, 64 + slot*200, 200)  # запись списка
если item.state != 1: вернуть МОЛЧАТЬ
если item.last_seen старше 4 с: вернуть МОЛЧАТЬ
если item.seqlock & 1: вернуть МОЛЧАТЬ    # идёт запись

payloadSlot = read(shmPath, 64 + 16*200 + slot*slotSize, bmsSlotSize)
если payloadSlot.seqlock.state != 1: вернуть МОЛЧАТЬ
если payloadSlot.seqlock.seq & 1: вернуть МОЛЧАТЬ
если payloadSlot.gen != item.gen: вернуть МОЛЧАТЬ
тело = payloadSlot.payload[0:payloadSlot.len]  # контракт 107 Б
info = buildSeplosInfo(тело)                   # SEPLOS INFO (75 Б)
вернуть info
```

Свойства:

- **Вид адресации `addr_mode`** — как инвертор нумерует BMS: `"1-16"` (по
  умолчанию) или `"0-15"` (§8). При `"1-16"` адрес инвертора `ADR` соответствует
  слоту `ADR-1`; при `"0-15"` — слоту `ADR`. Вне диапазона — молчим.
- **Адресация стабильна:** выпадение одной BMS не сдвигает номера остальных.
  Если батарея в запрошенном слоте потеряна, прокси молчит, а не отдаёт данные
  соседней.
- **Слот — логический номер батареи**, который `bms-reader` назначает при
  обнаружении (первый свободный). В пределах работы сервиса он не меняется;
  после перезапуска `bms-reader` нумерация слотов определяется порядком
  обнаружения устройств. Шинный адрес в записи shm не хранится — это отдельное
  ограничение контракта (при необходимости добавляется полем `addr`).
- **Ответный кадр** отдаётся с тем же номером `ADR`, что запросил инвертор
  (мапинг затрагивает только выбор BMS, не поле `ADR` в ответе).
- **Отсутствующая/мёртвая BMS → молчим.** Слушатель ничего не отвечает, ждёт
  следующий запрос (никакой ошибки/таймаута не шлёт).
- **Отдаём SEPLOS-блок телеметрии** (75 Б: 67 ядра + 8 хвоста) по протоколу
  SEPLOS (референс §10) — не сырой `bmscontract`. `buildSeplosInfo` раскладывает
  поля 107-Б контракта по полям SEPLOS (ячейки мВ, температуры 0.1 K, ток s16,
  напряжения 0.01 В, ёмкости, SOC/SOH, циклы). Число температур ограничиваем
  **6** (карта `16S_V20`), `field count = 0x00` — ядро ровно 67 Б, блок 75 Б
  (подробнее §10).
- **Ничего не кэшируем:** каждый ответ собирается заново из shm по слоту.
- **Целостность** — `seqlock` (bit0) и сверка `gen`: запись списка хранит `gen` для
  каждого номера (`list_gen`), слушатель сверяет с `gen` telem-слота, чтобы не
  отдать чужие данные, если слот переписан под другое устройство.

## 5.1. Протокол BMS: Seplos(Pylon) / Vektor(Growatt)

Настройка **«Протокол BMS»** (`protocol` в `bms-proxy.json`, §8) задаёт протокол
обмена с инвертором:

- **`seplos`** — текущий **Seplos(Pylon)** (PACE/ASCII, §5); поведение не меняется;
- **`vektor`** — **Vektor(Growatt)** (Modbus RTU): блок состояния
  `0x0015..0x0029` и напряжения 16 ячеек синтетическим пакетом из активных BMS
  (§5.1).

Настройка **глобальна для прокси** и применяется к обоим каналам: serial и UDP
(§7а). Смена протокола по `reload` перезапускает слушатель и поиск порта (A→B).

### Vektor(Growatt) — блок состояния и напряжения ячеек

Режим инвертора — **«1 устройство»**. Прокси отвечает на **два** известных
блока Modbus RTU (и только на них):

| Запрос | Что это | Ответ |
|---|---|---|
| `01 03 00 15 00 15` | блок состояния `0x0015..0x0029`, 21 регистр | `01 03 2A …` (47 байт) |
| `01 03 00 71 00 10` | напряжения ячеек `0x0071..0x0080`, 16 регистров | `01 03 20 …` (37 байт) |

Старт/функция/количество должны совпадать. Другие запросы (другой старт,
включая второй пакет `0x0081`, другая функция, другой адрес) **логируются и
остаются без ответа**; Modbus-exception не шлётся. Инвертор опрашивает блоки
примерно раз в секунду.

**Формат ответа.** `[slave][0x03][2n][n×u16 BE][CRC lo][CRC hi]`, где `slave` —
адрес из запроса; CRC16 Modbus, младший байт вперёд.

#### Блок состояния `0x0015..0x0029`

Источник — shm `bms-reader`, только `state=1` и `last_seen` не старше **4 с**.
BMS с `cell_count = 0`, `> 16` или нулевыми/неполными ячейками не учитываются.
Данные читаются заново на каждый запрос, ничего не кэшируется.

| Рег. | Поле | Ед. | Правило |
|---|---|---|---|
| `0x0015` | SOC | % | среднее `soc_dp/10`, округление до %, 0..100 |
| `0x0016` | Напряжение пакета | 10 мВ | `PAvg` (среднее сумм ячеек), `/10` |
| `0x0017` | Ток | 10 мА, signed | **сумма** `current_da`; разряд «+», заряд «−»; клэмп ±32767 |
| `0x0018` | Температура | °C, signed | **максимум** по всем датчикам, `/10`, клэмп -127..127 |
| `0x0019` | Max charge/discharge current | 10 мА | **327 А** (`32700`) |
| `0x001A` | Gauge RM (остаток) | 10 мА·ч | **сумма** `remaining_mah/10`, клэмп `65535` |
| `0x001B` | Gauge FCC (полная) | 10 мА·ч | **сумма** `cap_mah/10`, клэмп `65535` |
| `0x001C` | YW/FW | — | 0 |
| `0x001D` | Delta (разброс) | 1 мВ | `max_cell − min_cell` |
| `0x001E` | Cycle Count | — | **максимум**, клэмп `65535` |
| `0x001F` | Box ID | — | 0 |
| `0x0020` | SOH | % | среднее `soh_dp/10` по BMS с `soh_dp > 0`; нет данных → 100 |
| `0x0021` | CV Voltage (цель заряда) | 10 мВ | **57.6 В** (`5760`) для LFP 16S |
| `0x0022` | Warning + тип АКБ | биты | биты 0..13 — тревоги (ниже), 14..15 — тип |
| `0x0023` | Max discharge current | 10 мА | **327 А** (`32700`) |
| `0x0024` | Extended Error | — | 0 |
| `0x0025` | Maximum cell voltage | 1 мВ | синтетический max (ячейка 2) |
| `0x0026` | Minimum cell voltage | 1 мВ | синтетический min (ячейка 1) |
| `0x0027` | Maximum cell number | — | **2** (1-based) |
| `0x0028` | Minimum cell number | — | **1** (1-based) |
| `0x0029` | Cell Series | — | **16** |

**Ограничения регистров.** `0x0017` signed 16-bit: максимум 327.67 А, поэтому
лимит снижен до 327 А, а отдаваемый ток дополнительно клэмпится в ±32767.
`0x001A`/`0x001B` u16 в 10 мА·ч: максимум 655.35 А·ч; суммарная ёмкость банка
(794 А·ч) клампится в `65535`.

**Тип батареи** (биты 14..15 `0x0022`): `0 = LFP`, `1 = NMC`, `2 = LTO`.
Определяется эвристикой по среднему напряжению **фактической** ячейки `Vc`
(не `PAvg/16`) и среднему SOC:

- `Vc < 2900` → LTO;
- `Vc > 3900` → NMC;
- `SOC < 85 && Vc > 3550` → NMC;
- `SOC < 10 && Vc > 3400` → NMC;
- `SOC >= 85 && Vc <= 3650` → LFP;
- `SOC >= 10 && Vc <= 3500` → LFP;
- иначе — не менять текущий тип.

Тип хранится **только в памяти**, на диск не пишется; холодный старт — LFP.

#### Блок напряжений ячеек `0x0071..0x0080`

Синтез 16 ячеек из **всех активных** BMS (те же 4 с):

1. для каждой BMS суммируются все её ячейки — напряжение пакета `P` (поле
   `total_cv` **не используется**);
2. `PAvg` — среднее `P` по активным BMS, округлённое до целого мВ;
3. по всем ячейкам всех пакетов находятся глобальные `min` и `max`;
4. ячейка 1 = `min`, ячейка 2 = `max`, остальные 14 делят
   `PAvg - min - max` поровну; остаток (+1 мВ) добавляется первым ячейкам,
   чтобы сумма всех 16 точно равнялась `PAvg`.

Нет активных BMS (или `min + max > PAvg`) — прокси молчит. Синтетический
min/max используются и в `0x0025`/`0x0026`, индексы — `1`/`2` (1-based).

#### Warning (`0x0022`, биты 0..13)

Маппинг `alarm` тип-специфичный. Для **EnBMS** (typeId 2):

| Бит | Источник |
|---|---|
| 0 | любой `alarm[4i+0]`/`[4i+1]`, плюс 108/109 |
| 1 | любой `alarm[4i+2]`/`[4i+3]`, плюс 110/111 |
| 2 | 112/113 (pack OV), 140 |
| 3 | 114/115 (pack UV) |
| 4 | 134/135 (discharge OC), 137/139 (short/block) |
| 5 | 132/133 (charge OC), одиночный 98 |
| 6 | 120/121 (discharge overtemp) |
| 7 | 122/123 (discharge undertemp) |
| 8 | 116/117 (charge overtemp) |
| 9 | 118/119 (charge undertemp) |
| 10 | 128/129 (power part), одиночный 97 |
| 11 | 124/125 (env overtemp) |
| 12 | 126/127 (env undertemp) |
| 13 | 142/143 (remaining capacity), 144 (charge at low U) |

Для **AntBMS** (typeId 1) в контракте есть только MOS-коды, поэтому:

| Бит | Источник |
|---|---|
| 2 | charge MOS: код 2 или 5 |
| 3 | discharge MOS: код 2 или 5 |
| 4 | discharge MOS: код 3, 8, 12 |
| 5 | charge MOS: код 3, 8 |
| 6 | discharge MOS: код 6 |
| 8 | charge MOS: код 6 |
| 10 | charge/discharge MOS: код 7 или 10; balancer: 3 или 10 |

Биты `0,1,7,9,11,12,13` от AntBMS не приходят: ячеечных и температурных
warn/protect в контракте AntBMS нет. По всем активным BMS биты объединяются
через **OR**; `typeId` берётся из списка shm.

#### Probe и каналы

- **Probe (пассивный).** Ждём до **10 с** один из известных запросов:
  `0x03 0x0015 ×21` или `0x03 0x0071 ×16` (адрес 1..16, корректный CRC16,
  длина 8 байт). Прочие валидные Modbus-кадры отбрасываются; ожидание
  продолжается. Весь принятый поток пишется burst-логгером.
- **Слушатель serial.** Отвечает на оба известных блока; остальные запросы
  логирует. Поток режется по паузам **50 мс**, каждый «всплеск» пишется
  целиком (время, RX/TX, длина, raw/hex).
- **Время жизни.** 5 с без валидных запросов → завершение, возврат к поиску
  порта (§7).
- **UDP.** Тот же обработчик, что и на serial; probe по UDP не выполняется.
- **shm / `bms-reader`.** Только чтение — для синтеза; прокси ничего не
  публикует.

### Логирование probe и слушателя

Для **обоих** протоколов probe и слушатель используют общий **burst-логгер**:
сырые байты чтения и записи, разбитые по паузам **50 мс**, с точным временем
(`t=<µs>`), направлением и длиной. В probe логируется весь принятый поток,
включая невалидные кадры; отдельный разбор причины (CRC/длина/адрес) не
делается. Поля телеметрии в лог не дублируются. Режим Seplos по
поведению не меняется — меняется только формат debug-логов.

## 6. Основной каркас и поиск своего порта

Каркас — как у `map-reader` / `bms-reader` / `kes-reader`: общий раннер
сканирования портов (`daemons/lib/scanner/runner.go`), где проба и регистрация —
колбэки демона. Отличие: у МАП/КЭС/BMS проба **активная** (демон шлёт запрос и
ждёт ответ), у прокси — **пассивная**: инвертор сам вещает запрос, а мы просто
слушаем порт.

Логика определения «наш порт»:

1. **Перебираем кандидатов** — свободные последовательные порты (те же шаблоны,
   что у остальных: `/dev/ttyUSB*`, `/dev/ttyACM*`, `/dev/ttyAMA*`, `/dev/ttyS*`,
   `/dev/serial/by-id/*`, `/dev/serial0`, `/dev/serial1`). Кандидат пропускается,
   если занят другим процессом (flock/rdev) или в бане.
2. **Слушаем порт** (Seplos — **2 с**, `probeDeadline = 2 s`; Vektor — до
   **10 с**, §5.1): ждём входящий **правильный** запрос инвертора. Для Seplos это
   валидный PACE-кадр `~ … CR` с `CID2=0x42`; для Vektor — один из известных
   блоков: `0x03 0x0015×21` или `0x03 0x0071×16`, адрес 1..16, корректный CRC16
   (§5.1).
3. **Услышал правильный запрос → порт наш.** Регистрируем, **закрепляем** (не
   отпускаем), на этом **прекращаем поиск** остальных портов и запускаем
   основной сценарий (слушаем и отвечаем — §5).
4. **Не услышал за отведённое время → бан порта на 10 с.** В Vektor невалидные
   кадры не прерывают ожидание: ждём валидный до 10 с.
5. Цикл перебора повторяется (интервал сканирования) до тех пор, пока порт не
   найден; после закрепления поиск больше не идёт.

Требуемые параметры (удерживаются как константы/конфиг, по умолчанию):

| Параметр | Значение | Смысл |
|---|---|---|
| проба/прослушивание | **2 с** Seplos / **10 с** Vektor | бюджет на ожидание валидного запроса на порту |
| бан порта | **10 с** | пауза для порта, где правильного запроса нет |
| после закрепления | — | порт не отпускается, другие порты не сканируются |

Замечания:

- **Последний рабочий порт пробуется первым** (`prefer`): после потери/смены
  скорости прокси не перебирает все `ttyUSB*` заново, а сразу проверяет известный
  порт. При смене `baud` баны портов сбрасываются — промахи на старой скорости
  недействительны, поэтому новая скорость применяется примерно за один probe (2 с).
- **Скорость не перебираем.** Набор скоростей у прокси свой и **задаётся явно
  в настройке** (2400/9600/19200/57600/115200/230400, умолчание 19200 — §8), никакого
  перебора, как у map/kes, нет. Порт открывается сразу на заданной скорости.
- В самом переиспользуемом `scanner.Runner` проба активная, а у нас ожидание
  входящего кадра — поэтому либо добавить пассивный режим пробы в `scanner`
  (колбэк уже возвращает `(Result, error)`), либо выполнять перебор своим циклом
  на тех же принципах (дедуп по rdev, flock, backoff-карта один к одному).
- Поскольку «наш» порт один и после закрепления другие не нужны, `MaxDevices=1`,
  а `Foreign`-ветка не требуется (чужих MicroArt-устройств порт «наш порт»
  не принимает — при заглушке ток на кадр `~` просто бан).
- Критерий «правильного запроса»: для Seplos — строго по §5 (`~`, `CID1=0x46`,
  `CID2=0x42`, валидный `CHK`); для Vektor — один из известных блоков
  (`0x03 0x0015×21` или `0x03 0x0071×16`, корректный CRC16) по §5.1. Всё прочее
  → не наш порт (в Vektor — продолжаем ждать до 10 с).

## 7. Состояния основного процесса и горутина-слушатель

Основной процесс находится ровно в одном из трёх состояний:
**A — поиск порта** (§6), **B — приём запросов и ответ по слоту** (ниже),
**C — остановлен** (§8). В этом разделе — A и B.

**Состояние A — «Поиск порта»** (см. §6): перебор свободных портов, слушаем по
2 с, бан 10 с. Устройств/данных не отдаёт.

**Состояние B — «Слушаем порт»**:
- **Seplos:** слушатель на каждый запрос читает shm и проверяет слот, `state`,
  свежесть `last_seen` и `gen` (§5); отвечает по стабильному слоту, без
  компактной перенумерации;
- **Vektor:** слушатель отвечает на блок состояния (`0x03 0x0015×21`) и блок
  ячеек (`0x03 0x0071×16`), остальные запросы только логирует (burst 50 мс);
  shm читает для синтеза (§5.1).

Переходы:
- **A → B**: найден наш порт (слышим валидный запрос) → запускается
  горутина-слушатель.
- **B → A**: слушатель **5 с** не слышал запросов (в норме инвертор опрашивает
  ≥ 1 раз/с хотя бы одну BMS, так что 5 с = инвертор отвалился) → завершается,
  основной возвращается в состояние поиска порта. При EOF/hangup (USB отключён)
  или не-timeout ошибке чтения слушатель завершается сразу, без ожидания 5 с;
  основной уходит в пересканирование с backoff.

### Горутина-слушатель

Запускается из состояния B (после нахождения порта) и обслуживает порт
(циклически):

1. Читает запрос инвертора, извлекает **номер BMS (ADR)** и мапит его на слот
   по `addr_mode` (§5): `1-16` → `slot=ADR-1`, `0-15` → `slot=ADR`.
2. Читает запись списка и payload слота **напрямую из shm** (с проверкой
   `state`, свежести `last_seen`, seqlock и `gen` — §5).
3. Данные есть → **отдаёт** ответ с исходным `ADR` инвертора; нет → **молчит**,
   ждёт следующий запрос.
4. Каждый запрос сбрасывает таймер бездействия.

Таймаут бездействия **5 с**: если за это время не пришло ни одного запроса —
горутина завершается, освобождает порт, основной процесс уходит в состояние
поиска.

**Пауза ответа.** Перед отправкой ответа слушатель ждёт ~**30 мс** — столько же,
сколько реальный EnBMS (замер: первый байт через 32–34 мс после запроса). Это время
нужно инвертору на переключение RS485 в приём; ответ через 0.7 мс приводил к потере
первого байта кадра и повторному запросу через 2 с.

Замечания:

- Фонового списка и его обновления раз в секунду **нет**: снимок читается на
  каждый запрос, поэтому данные всегда актуальны.
- Если батарея потеряна (слот освобождён или `last_seen` протух) — молчим.
  Данные соседнего слота не подставляются: адресация стабильна.
- **Ничего не кэшируем** (§5).

### UDP-слушатель (§7а)

Помимо COM-порта, у демона есть **второй (UDP) слушатель** для случая, когда
инвертор подключён через прозрачный UDP-шлюз (RS485↔UDP). Он принимает те же
PACE-запросы `CID2 0x42` и отвечает **тем же форматом и теми же данными наших BMS**,
что и COM-порт:

- мапинг `ADR → стабильный слот` по `addr_mode` (§5);
- данные читаются **напрямую из shm `bms-reader`** на каждый запрос (свежий снимок,
  без кэша), с проверкой seqlock/`gen`; нет BMS → **молчим**;
- ADR в ответе = ADR запроса.

В режиме **`vektor`** UDP-слушатель принимает те же два Modbus-блока
(`0x0015×21` и `0x0071×16`) и отвечает тем же синтетическим блоком
состояния/ячеек, что и COM-порт; PACE-кадры в этом режиме не обрабатываются.
Перед ответом UDP-слушатель Vektor выдерживает `responseDelay` (~30 мс), как и
COM-порт.

**Управление — открытая настройка** в рамке «БМС-Прокси» на странице
`/bms/settings`: **явный переключатель «Включено»** (`udp_enabled`) + поле адреса
(`udp_listen`). Слушатель запускается только при `udp_enabled=true` **и** непустом
адресе. **По умолчанию выключен.**

| Ключ `bms-proxy.json` | Значение | Смысл |
|---|---|---|
| `udp_enabled` | `false` (по умолчанию) | UDP-слушатель выключен |
| `udp_enabled` | `true` + `udp_listen: "0.0.0.0:502"` | слушать этот UDP-адрес |

Адрес применяется **на старте и по `reload`** (смена значения запускает/останавливает
слушателя). UDP-слушатель **независим от состояний COM-процесса** (A/B/C) и от
`enabled`. Завершение — корректное: по `stop` сокет закрывается, `serve()` дожидается
выхода.

**Зачем и как настроить шлюз.** Нужно, когда инвертор физически не на COM-порту
ПАК, а подключён через сетевой **прозрачный шлюз RS485↔UDP** (инвертор шлёт
RS485-запросы, шлюз инкапсулирует их в UDP-датаграммы). Настройте шлюз пересылать
эти датаграммы на **адрес:порт ПАК**, указанный в `udp_listen` (например
`0.0.0.0:502` — слушать на всех интерфейсах, порт 502). Демон примет запрос, ответит
кадром SEPLOS, шлюз вернёт его в RS485. Пустое поле — UDP-путь выключен, работает
только COM.

## 8. Сервис, настройки и третье состояние (остановлен)

### Systemd и reload

- Прокси ставится как отдельный systemd-сервис (по образцу `bms-reader`-unit).
- У сервиса **свой Unix control-socket** (общий каркас `daemons/lib/control`:
  запрос — одна JSON-строка, ответ — одна JSON-строка), например
  `/run/malina-bms-proxy/control.sock`.
- Команда **`reload`** по сокету → демон **перечитывает настройки** (аналог
  `SIGHUP`). Также как у `bms-reader`: `ping`, `reload`.
- Настройки хранятся в отдельном конфиг-файле (например
  `/malina/etc/malina/bms-proxy.json`) рядом с `bms-reader.json`; запись —
  атомарная (temp + rename), как у остальных конфигов.

### Настройки на странице настроек БМС

Отдельная **рамка «БМС-Прокси»** на странице настроек БМС (`/bms/settings`,
`handleBmsSettings`). Поля:

| Параметр | Тип | По умолчанию | Допустимые значения |
|---|---|---|---|
| **Включено** | bool | **выключено** | да/нет |
| **Протокол BMS** | string | **seplos** (Seplos(Pylon)) | `seplos`, `vektor` (Vektor(Growatt): блок состояния и 16 ячеек) |
| **Скорость порта** | int | **19200** | 2400, 9600, 19200, 57600, 115200, 230400 |
| **Уровень логирования** | string | **info** | debug, info, warn, error |
| **Адресация инвертора** | string | **1–16** | `1-16`, `0-15` |
| **UDP-слушатель** | bool + string | **выключен** | «Включено» (`udp_enabled`) + `host:port` (`udp_listen`, напр. `0.0.0.0:502`, §7а) |

Сохранение → запись конфига + `controlCall(sock, {cmd:"reload"})` (как у
`bms-reader.json` → демон `bms-reader`).

В поставляемом конфиге `system/bms/bms-proxy.json` уровень выставлен в **error**
(минимальный, только ошибки); встроенное умолчание кода (нет файла/невалидно) —
**info**.

Смена **протокола**, **скорости порта** или **адресации инвертора** по `reload`
применяется сразу: слушатель перезапускается и порт открывается заново с новыми
параметрами (без перезапуска сервиса). Уровень логирования меняется на лету, без
перезапуска.

### Логирование

Свои уровни **debug / info / warn / error**. Уровень читается из настройки
`log_level` при старте и **меняется на лету по `reload`** (без перезапуска
сервиса): основной процесс применяет новый уровень при перечитывании настроек.
Уровень читается без учёта регистра (`INFO`, `warning`→`warn`), нормализуется к
канонической форме. Формат строки — `bms-proxy: <дата> <время> <LEVEL> <текст>`
(стандартные флаги `log`); переходы состояний и события порта/протокола —
`info`/`warn`, поштучные запросы/ответы — `debug`. В `debug` на serial и UDP
пишутся **только сырые кадры** запроса/ответа с точным временем (`t=<µs>`) и
диагностика ошибок (слот недоступен — молчу, не-PACE, ошибки записи); поля
телеметрии в лог не дублируются. Для **обоих** протоколов probe и слушатель
используют общий **burst-логгер** с разбиением по паузам **50 мс**: каждый
всплеск пишется целиком (время, направление RX/TX, длина, raw/hex); в probe
логируются и невалидные кадры с причиной (§5.1).

### Третье состояние C — «Остановлен»

Помимо A (поиск) и B (ответы по слоту) есть третье состояние:

- Если параметр **«Включено» = выключено**: основной процесс **останавливает
  горутину-слушателя** (если была) и переходит в состояние **C**.
- В состоянии C демон **ничего не делает** — не ищет порт, не читает shm.
  Крутит **цикл с длительным сном**, ожидая сигнал **перечитать
  настройки** (команда `reload` по control-socket).
- **C → A**: после `reload`, если «Включено» стало = да → считываем настройки и
  уходим в поиск порта (§6).
- Если после `reload` «Включено» по-прежнему = нет → остаёмся в C, продолжаем спать.

Переходы состояний:

```text
C (выключен, длинный сон) --reload + Включено--> A (поиск порта)
A --наш порт--> B (слушатель и ответы по слоту)
B --слушатель 5 с молчит--> A
B --reload + смена baud/адресации/протокола--> A (перезапуск слушателя, порт заново)
B/любое --reload + Выключено--> C (остановить слушателя, длинный сон)
```

## 9. Открытые вопросы (до реализации)

- [ ] **Занятость канала (полудуплекс):** как слушатель понимает, что инвертор
  закончил слать запрос, прежде чем отвечать (пауза/тайминг/маркер) и какое
  поведение при переполнении буфера.
- [ ] Набор данных порта (8N1? стоп-биты/паритет) — зафиксировать (в образце
  ASCII-hex, 8N1).
- [ ] **Поле `CapMAh`** контракта не используется (и «полная», и «номинальная»
  ёмкость берутся из `RatedMAh`, как в образце) — уточнить, нужна ли `CapMAh`.

Решено (не открытые вопросы):
- Формат INFO — **SEPLOS 75 Б** (67 ядра + 8 хвоста), как в рабочем референсе §10;
  сырой `bmscontract` не отдаём (§5). Маппинг полей 107-Б контракта → SEPLOS —
  в таблице §10; карта `16S_V20` (`energybms/protocol-485.md` §5): `dataflag=0`,
  `slaveNo` = номер слота пакета (0,1,2; `protocol-485.md` §5), temp count = **6**, field count = `0x00` (живой EnBMS отдаёт `0x0A`, инвертор принимает оба).
- Пути зафиксированы и совпадают с манифестом: контроль-сокет
  `/run/malina-bms-proxy/control.sock`, конфиг `/malina/etc/malina/bms-proxy.json`.
- Настройки прокси сохраняются **отдельно** от приёмника: кнопка «Сохранить
  прокси» постит на `/bms/proxy/settings` и вызывает `reload` только прокси;
  сохранение приёмника прокси не перезагружает.
- **Вид адресации инвертора** (`addr_mode`): `1-16` (умолчание) или `0-15`; мапинг
  «адрес инвертора → стабильный слот» делает слушатель (§5). На проде инвертор
  опрашивает адреса `01`, `02`, `03` на 19200 → нужен `1-16`.
- Скорость — **задаётся явно в настройке**, набор 2400/9600/19200/57600/115200/230400
  (умолчание 19200), перебора нет (§6/§8).
- Адресация `ADR → стабильный слот` — без компактной перенумерации (§5/§7);
  `seq` остаётся внутренним.
- Жизненный цикл — отдельный systemd-сервис со своим control-socket и reload (§8).
- Что делать при запросе отсутствующей BMS — **молчать** (§5/§7).
- Кэширования нет (§5/§7).

## 10. Источник-образец (референс)

`tools/seplos_bms_server.py` (проект `sunReceiver`) — **рабочий** мост, который
инвертор опрашивает сегодня. Это эталон протокола и логики ответа; наше
`bms-proxy` делает то же самое, но **на Go**, читает данные из shm `bms-reader`
(а не с `read_bms.php`) и работает **последовательным портом** вместо **UDP**.

Что берём как образец:

- **Протокол — PACE / YD-T1363.3 (ASCII-hex, формат SEPLOS):**
  - запрос: `~ 20 <ADR> 46 42 E002 <NN> <CHK> CR`;
  - ответ: `~ 20 <ADR> 46 <RTN> <LEN> <INFO…> <CHK> CR`;
  - `CID1=0x46`; запрос телеметрии `CID2=0x42` (TeleMeter) — единственный
    обрабатываемый;
  - `RTN=0x00` ok / `RTN=0x01` ошибка;
  - `LEN` — 16-бит: `LCHKSUM<<12 | LENID` (LENID = длина INFO в hex-символах).
- **Проверка** `CHK` (дополнение суммы ASCII-кодов строки `VER..INFO` до `0xFFFF`)
  на запросе и самопроверка на собранном ответе.
- **Сборка INFO — TeleMeter `0x42`, 75 Б** (раскладка сверена с официальной
  картой производителя `16S_V20_ADDR` — первоисточник `energybms/protocol-485.md`
  §5 и декодер `energybms-editor/telemetry.py`):

  | Смещ | Поле | Масштаб | Источник (bmscontract) |
  |---|---|---|---|
  | 0 | `dataflag` | — (=0) | конст. |
  | 1 | `slaveNo` — номер пакета в сборке | — (= слот: 0,1,2) | из слота |
  | 2 | cell count | — | `CellCount`, при 0 — по последней ненулевой `CellsMV` |
  | 3..34 | ячейки 1..16 | ×0.001 В (мВ) | `CellsMV` |
  | 35 | temp count | — | `TempCount` |
  | 36..47 | темп. 1..4, среды, силовой | ×0.1 К, −273.1 | `TempsDC` (+2731) |
  | 48 | ток (s16, − = разряд) | ×0.01 А | `−CurrentDA` |
  | 50 | напряжение сборки | ×0.01 В | `TotalCV`, при 0 — сумма ячеек |
  | 52 | остаточная ёмкость | ×0.01 А·ч | `RemainingMAh`/10 |
  | 54 | field count / customerp | — (=`0x00`, как в эталоне; живой EnBMS — `0x0A`) | конст. |
  | 55 | полная ёмкость | ×0.01 А·ч | `RatedMAh`/10, при 0 — `CapMAh`/10 |
  | 57 | SOC | ×0.1 % | `SocDP` |
  | 59 | номинальная ёмкость | ×0.01 А·ч | `RatedMAh`/10, при 0 — `CapMAh`/10 |
  | 61 | циклы | ×1 | `Cycles` |
  | 63 | SOH | ×0.1 % | `SohDP`, при 0 — 1000 (100 %) |
  | 65 | напряжение клемм | ×0.01 В | `PortCV`, при 0 — `TotalCV` |
  | 67..74 | temp-drift / zero-point / энергии | ×0.001 А, ×0.1 кВт·ч | **нет данных → 0** |

  Знак тока: контракт «разряд +»; SEPLOS «− = разряд» → знак инвертируется.
- **Поведение при недоступности:** в образце — ответ-ошибка (`RTN≠0`, пустой
  INFO). У нас **намеренное отличие**: при отсутствии запрошенной BMS прокси
  **молчит** (§5/§7), кадр ошибки не отправляется.
- **Кэш/логика** в образце заточена под «ровно 2 BMS» и блоки 1..3 (EnBMS из
  Redis) — нам **не нужна**: у нас адресация по номеру BMS (`0..15` или `1..16`,
  §8) и один
  источник (shm `bms-reader`).

Файл: `../sunReceiver/tools/seplos_bms_server.py` (относительно `docs/`).

## 11. Границы ответственности

- Прокси **не** опрашивает BMS, **не** знает типы `AntBMS-DSP`/`EnBMS-RS485`.
- Прокси **не** пишет в shm и **не** меняет контракт `bms-reader`.
- Прокси отдаёт телеметрию **по стабильному слоту**, который соответствует ADR
  инвертора; компактной перенумерации нет. `ID`/`BASE` — диагностическое поле и
  может совпадать у нескольких BMS.
- Порог живости 4 с — страховка от зависшего `bms-reader`: если данных нет или
  слот потерян, на запрос по этому номеру прокси **молчит**, а не отдаёт данные
  соседней батареи (см. §4/§5).

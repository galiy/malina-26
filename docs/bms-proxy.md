# БМС-Прокси: требования

> Статус: **каркас требований, реализация — по отмашке.**
> Документ фиксирует назначение, источник данных и алгоритм получения
> списка живых BMS. Контракт отдачи и внутреннее устройство — открытые вопросы
> (см. §9).

## 1. Назначение

`bms-proxy` — компонент, работающий **последовательным портом (RS485)** и
отдающий инвертору телеметрию конкретной BMS. Инвертор запрашивает номера
последовательно, в цикле; диапазон зависит от его настройки — **`0..15`** или
**`1..16`** (`addr_mode`, §8; на проде — `1..16`).

Прокси держит **собственный локальный список живых BMS**, который обновляет
раз в секунду из shm `bms-reader` и **нумерует от `0` до `N-1`** (только живые,
`N` — количество). Номер запроса (ADR) мапится на **индекс в этом живом списке**
согласно `addr_mode`, а не на физический слот контракта: по индексу слушатель
берёт из списка **адрес слота** и читает данные именно из него.

Прокси не опрашивает BMS сам, не знает протоколов типов и не пишет в
телеметрию — он читает уже подготовленный бинарный контракт `bms-reader` из
POSIX shared memory и транслирует его в ответ на порту.

Цель — дать инвертору простой доступ «номер → телеметрия» через живые BMS, не
заставляя его разбираться в раскладке shm, генерациях и диагностике живости.

## 2. Источник данных

- Сегмент: `/dev/shm/malina-bms-state`.
- Магия: `0x424D5342` (`"BSMB"`), версия `1`.
- Раскладка (синхронизирована с `daemons/bms-reader/shm.go` и
  `web/internal/web/bmsstate.go`):

  ```
  [header 64 Б][list: 16 записей × 200 Б][slots: 16 × (32 + 112 Б)]
  ```

- Реестр (`Items`) — по одному на слот: метаданные устройства
  (`id`/серийник `BASE-NNNNN`, `base`, `source`, `type_id`, `state`, `framing`,
  `gen`, `last_seen`).
- Телеметрия (`Slots`) — бинарный payload `bmscontract.Size` (107 Б), доступен
  по индексу слота при `state==1` и совпадении `gen`.

Реестр пишется **только** оркестратором `bms-reader` (архитектура §12), телеметрия
— пулером. Прокси — сторонний читатель, на запись не претендует.

## 3. Смещения записей реестра (200 Б)

| Поле | Смещение | Размер | Тип |
|---|---|---|---|
| `seqlock.state` | 0 | 4 | uint32 (1 = занят) |
| `seqlock.seq` | 8 | 8 | uint64 (bit0 = идёт запись) |
| `id` / серийник | 16 | 50 | строка, `BASE-NNNNN` |
| `base` | 66 | 50 | строка |
| `source` | 116 | 64 | строка |
| `type_id` | 180 | 1 | uint8 |
| `state` | 181 | 1 | uint8 (0 = lost, 1 = ok) |
| `framing` | 182 | 1 | uint8 |
| `gen` | 184 | 8 | uint64 LE |
| `last_seen` | 192 | 8 | uint64 LE (unix, секунды) |

## 4. Определение «живой» BMS

Живой считается BMS, **теледанные которого обновлены не позже 2 секунд назад**,
то есть:

```
живой ⇔ (state == 1) И (now − last_seen ≤ 2 с)
```

Пояснение:

- `state == 1` (слот занят) — необходимое, но **не достаточное** условие с точки
  зрения живости: `bms-reader` держит запись в реестре с `state==1` какое-то
  время после потери связи, пока `loseDevice` не освободит слот по
  `MissThreshold` (см. `daemons/bms-reader/orchestrator.go:382`).
- Решающий признак — свежесть `last_seen`: heartbeat публикуется пулером для
  каждого успешного опроса (`orchestrator.go:371`).
- Порог **2 с** — жёсткий, входной параметр по умолчанию; опрос идёт раз в
  секунду, поэтому 2 с = «пропущен не более одного цикла опроса».

## 5. Алгоритм ответа слушателя на запрос инвертора

Слушателю **нельзя** шариться по shm-листу и вычислять, кто жив — на запрос
надо отвечать максимально быстро. Поэтому слушатель читает готовые данные из
общей памяти (заполняются главным потоком — см. §7) и только потом ходит в shm
за payload слота.

Обработчик запроса `onRequest(adr)` — сначала мапит адрес инвертора на индекс
живого списка по виду адресации `addr_mode` (§8), затем отвечает:

```text
# idx — индекс в живом списке (0..N-1)
если addr_mode == "1-16": idx = adr - 1    # инвертор адресует 1..16
иначе:                   idx = adr        # инвертор адресует 0..15

lock(mx)                                   # защита списка + количества
n    = read(count)                         # количество живых BMS (N)
list = read(list)                          # список номер->слот (0..N-1)
unlock(mx)

если idx < 0 или idx >= n: вернуть МОЛЧАТЬ # такой BMS нет
slot = list[idx]                           # адрес слота из нашего списка

payloadSlot = read(shmPath, 64 + 16*200 + slot*slotSize, bmsSlotSize)  # слот
если payloadSlot.seqlock.state != 1: вернуть МОЛЧАТЬ
если payloadSlot.seqlock.seq & 1: вернуть МОЛЧАТЬ      # seqlock: идёт запись
если payloadSlot.gen != list_gen[idx]: вернуть МОЛЧАТЬ  # gen списка не совпал с телеметрией
тело = payloadSlot.payload[0:payloadSlot.len]            # контракт 107 Б
info = buildSeplosInfo(тело)                             # SEPLOS INFO (75 Б) из полей
вернуть info
```

Свойства:

- **Вид адресации `addr_mode`** — как инвертор нумерует BMS: `"1-16"` (по
  умолчанию) или `"0-15"` (§8). При `"1-16"` адрес инвертора `ADR` соответствует
  индексу `ADR-1` живого списка (`ADR=1 → первая живая`); при `"0-15"` — напрямую
  (`ADR=0 → первая живая`). Вне диапазона (`idx<0` или `idx≥N`) — молчим.
- **Ответный кадр** отдаётся с тем же номером `ADR`, что запросил инвертор
  (мапинг затрагивает только выбор BMS, не поле `ADR` в ответе).
- **Отсутствующая/мёртвая BMS → молчим.** Слушатель ничего не отвечает, ждёт
  следующий запрос (никакой ошибки/таймаута не шлёт).
- **Отдаём SEPLOS-блок телеметрии** (75 Б: 67 ядра + 8 хвоста) по протоколу
  SEPLOS (референс §10) — не сырой `bmscontract`. `buildSeplosInfo` раскладывает
  поля 107-Б контракта по полям SEPLOS (ячейки мВ, температуры 0.1 K, ток s16,
  напряжения 0.01 В, ёмкости, SOC/SOH, циклы). Число температур ограничиваем
  **6** (карта `16S_V20`), `field count = 0x00` — ядро ровно 67 Б, блок 75 Б
  (подробнее §10).
- **Ничего не кэшируем:** каждый ответ собирается заново из shm по слоту.
- **Целостность** — `seqlock` (bit0) и сверка `gen`: список хранит `gen` для
  каждого номера (`list_gen`), слушатель сверяет с `gen` telem-слота, чтобы не
  отдать чужие данные, если слот переписан под другое устройство.

## 6. Основной каркас и поиск своего порта

Каркас — как у `map-reader` / `bms-reader` / `kes-reader`: общий раннер
сканирования портов (`daemons/lib/scanner/runner.go`), где проба и регистрация —
колбэки демона. Отличие: у МАП/КЭС/BMS проба **активная** (демон шлёт запрос и
ждёт ответ), у прокси — **пассивная**: инвертор сам вещает запрос, а мы просто
слушаем порт.

Логика определения «наш порт»:

1. **Перебираем кандидатов** — свободные последовательные порты (те же шаблоны,
   что у остальных: `/dev/ttyUSB*`, `/dev/ttyACM*`, `/dev/ttyAMA*`, `/dev/ttyS*`,
   `/dev/serial/by-id/*`, `/dev/serial0`, `/dev/serial1`). Кандидат пропускается,
   если занят другим процессом (flock/rdev) или в бане.
2. **Слушаем порт 2 с** (бюджет пробы `probeDeadline = 2 s`, как в
   `map-reader/detect.go:16`): ждём входящий **правильный** запрос инвертора —
   валидный PACE-кадр `~ … CR` с `CID2=0x42` (телеметрия).
3. **Услышал правильный запрос → порт наш.** Регистрируем, **закрепляем** (не
   отпускаем), на этом **прекращаем поиск** остальных портов и запускаем
   основной сценарий (слушаем и отвечаем — §5).
4. **Не услышал за 2 с → бан порта на 10 с.** Порт в backoff, в следующих циклах
   не пробуется, пока не истечёт бан.
5. Цикл перебора повторяется (интервал сканирования) до тех пор, пока порт не
   найден; после закрепления поиск больше не идёт.

Требуемые параметры (удерживаются как константы/конфиг, по умолчанию):

| Параметр | Значение | Смысл |
|---|---|---|
| проба/прослушивание | **2 с** | бюджет на ожидание одного запроса на порту |
| бан порта | **10 с** | пауза для порта, где правильного запроса нет |
| после закрепления | — | порт не отпускается, другие порты не сканируются |

Замечания:

- **Скорость не перебираем.** Набор скоростей у прокси свой и **задаётся явно
  в настройке** (2400/9600/19200/57600/115200/230400, умолчание 19200 — §8), никакого
  перебора, как у map/kes, нет. Порт открывается сразу на заданной скорости.
- В самом переиспользуемом `scanner.Runner` проба активная, а у нас ожидание
  входящего кадра — поэтому либо добавить пассивный режим пробы в `scanner`
  (колбэк уже возвращает `(Result, error)`), либо выполнять перебор своим циклом
  на тех же принципах (дедуп по rdev, flock, backoff-карта один к одному).
- Поскольку «наш» порт один и после закрепления другие не нужны, `MaxDevices=1`,
  а `Foreign`-ветка не требуется (чужих MicroArt-устройств порт «наш порт»
  не принимает — при заглушке ток на кадр `~` просто бан).
- Критерий «правильного запроса» — строго проверка по §5: `~`, `CID1=0x46`,
  `CID2=0x42`, валидный `CHK`. Всё прочее → не наш порт.

## 7. Состояния основного процесса и горутина-слушатель

Основной процесс находится ровно в одном из трёх состояний:
**A — поиск порта** (§6), **B — обновление списка доступных BMS** (ниже),
**C — остановлен** (§8). В этом разделе — A и B.

**Состояние A — «Поиск порта»** (см. §6): перебор свободных портов, слушаем по
2 с, бан 10 с. Устройств/данных не отдаёт.

**Состояние B — «Обновление списка доступных BMS»**:
- раз в **1 с** перечитываем из shm `bms-reader` список **живых** BMS (критерий
  §4: `state==1` и `last_seen` не старше 2 с);
- **нумеруем их для себя `0..N-1`** (только живые), где `N` — количество;
- для каждого номера храним **адрес слота** (индекс слота shm) и его `gen`;
- храним **ячейку количества** (`N`).

Обновление — через **двойной буфер + мьютекс** (главный поток формирует новое
состояние локально, потом атомарно копирует в общее место, слушатель читает
консистентный снимок):

```text
# главный поток (раз в 1 с)
новый_список = buildAliveList()   # список номер->(слот, gen) + N, локально
lock(mx)
общий_список = новый_список       # быстро копируем
общая_N      = N
unlock(mx)

# слушатель (на запрос)
lock(mx)
n    = общая_N
list = общий_список
unlock(mx)
```

Это гарантирует, что слушатель не прочитает неконсистентную пару
«количество + список».

Переходы:
- **A → B**: найден наш порт (слышим валидный запрос) → запускается
  горутина-слушатель.
- **B → A**: слушатель **5 с** не слышал запросов (в норме инвертор опрашивает
  ≥ 1 раз/с хотя бы одну BMS, так что 5 с = инвертор отвалился) → завершается,
  основной возвращается в состояние поиска порта.

### Горутина-слушатель

Запускается из состояния B (после нахождения порта) и обслуживает порт
(циклически):

1. Читает запрос инвертора, извлекает **номер BMS (ADR)** и мапит его на индекс
   живого списка по `addr_mode` (§5): `1-16` → `idx=ADR-1`, `0-15` → `idx=ADR`.
2. Под мьютексом читает ячейку количества и список «индекс → (слот, gen)` —
   быстро, чтобы не мешать обновлению.
3. Сверяется со списком:
   - **`0 <= idx < N`** → берёт адрес слота из списка, **сам идёт в shm
     `bms-reader`**, читает payload нужного слота (с проверкой seqlock и `gen` —
     §5) и **отдаёт** (ответ с исходным `ADR` инвертора);
   - **`idx < 0` или `idx >= N`** (такой BMS нет) → слушатель **просто молчит**,
     ждёт следующий запрос (ничего не отвечает).
4. Каждый запрос сбрасывает таймер бездействия.

Таймаут бездействия **5 с**: если за это время не пришло ни одного запроса —
горутина завершается, освобождает порт, основной процесс уходит в состояние
поиска.

Замечания:

- Список для слушателя — **общий (разделяемый) снимок**, а не копия на момент
  запуска: главный поток обновляет его раз в 1 с через мьютекс, слушатель
  читает актуальную версию при каждом запросе.
- Если BMS «выпала» из живых между обновлениями, но в текущем снимке ещё есть —
  слушатель попытается прочитать слот; при несовпадении `gen`/seqlock (§5) —
  молчит.
- **Ничего не кэшируем** (§5).

### UDP-слушатель (§7а)

Помимо COM-порта, у демона есть **второй (UDP) слушатель** для случая, когда
инвертор подключён через прозрачный UDP-шлюз (RS485↔UDP). Он принимает те же
PACE-запросы `CID2 0x42` и отвечает **тем же форматом и теми же данными наших BMS**,
что и COM-порт:

- мапинг `ADR → индекс живого списка` по `addr_mode` (§5);
- данные читаются **напрямую из shm `bms-reader`** на каждый запрос (свежий снимок,
  без кэша), с проверкой seqlock/`gen`; нет BMS → **молчим**;
- ADR в ответе = ADR запроса.

**Управление — открытая настройка** в рамке «БМС-Прокси» на странице
`/bms/settings`: **явный переключатель «Включено»** (`udp_enabled`) + поле адреса
(`udp_listen`). Слушатель запускается только при `udp_enabled=true` **и** непустом
адресе. **По умолчанию выключен.**

| Ключ `bms-proxy.json` | Значение | Смысл |
|---|---|---|
| `udp_enabled` | `false` (по умолчанию) | UDP-слушатель выключен |
| `udp_enabled` | `true` + `udp_listen: "0.0.0.0:502"` | слушать этот UDP-адрес |

Адрес применяется **на старте и по `reload`** (смена значения запускает/останавливает
слушателя). UDP-слушатель **независим от состояний COM-процесса** (A/B/C) и от
`enabled`. Завершение — корректное: по `stop` сокет закрывается, `serve()` дожидается
выхода.

**Зачем и как настроить шлюз.** Нужно, когда инвертор физически не на COM-порту
ПАК, а подключён через сетевой **прозрачный шлюз RS485↔UDP** (инвертор шлёт
RS485-запросы, шлюз инкапсулирует их в UDP-датаграммы). Настройте шлюз пересылать
эти датаграммы на **адрес:порт ПАК**, указанный в `udp_listen` (например
`0.0.0.0:502` — слушать на всех интерфейсах, порт 502). Демон примет запрос, ответит
кадром SEPLOS, шлюз вернёт его в RS485. Пустое поле — UDP-путь выключен, работает
только COM.

## 8. Сервис, настройки и третье состояние (остановлен)

### Systemd и reload

- Прокси ставится как отдельный systemd-сервис (по образцу `bms-reader`-unit).
- У сервиса **свой Unix control-socket** (общий каркас `daemons/lib/control`:
  запрос — одна JSON-строка, ответ — одна JSON-строка), например
  `/run/malina-bms-proxy/control.sock`.
- Команда **`reload`** по сокету → демон **перечитывает настройки** (аналог
  `SIGHUP`). Также как у `bms-reader`: `ping`, `reload`.
- Настройки хранятся в отдельном конфиг-файле (например
  `/malina/etc/malina/bms-proxy.json`) рядом с `bms-reader.json`; запись —
  атомарная (temp + rename), как у остальных конфигов.

### Настройки на странице настроек БМС

Отдельная **рамка «БМС-Прокси»** на странице настроек БМС (`/bms/settings`,
`handleBmsSettings`). Поля:

| Параметр | Тип | По умолчанию | Допустимые значения |
|---|---|---|---|
| **Включено** | bool | **выключено** | да/нет |
| **Скорость порта** | int | **19200** | 2400, 9600, 19200, 57600, 115200, 230400 |
| **Уровень логирования** | string | **info** | debug, info, warn, error |
| **Адресация инвертора** | string | **1–16** | `1-16`, `0-15` |
| **UDP-слушатель** | bool + string | **выключен** | «Включено» (`udp_enabled`) + `host:port` (`udp_listen`, напр. `0.0.0.0:502`, §7а) |

Сохранение → запись конфига + `controlCall(sock, {cmd:"reload"})` (как у
`bms-reader.json` → демон `bms-reader`).

В поставляемом конфиге `system/bms/bms-proxy.json` уровень выставлен в **error**
(минимальный, только ошибки); встроенное умолчание кода (нет файла/невалидно) —
**info**.

Смена **скорости порта** или **адресации инвертора** по `reload` применяется сразу:
слушатель перезапускается и порт открывается заново с новыми параметрами (без
перезапуска сервиса). Уровень логирования меняется на лету, без перезапуска.

### Логирование

Свои уровни **debug / info / warn / error**. Уровень читается из настройки
`log_level` при старте и **меняется на лету по `reload`** (без перезапуска
сервиса): основной процесс применяет новый уровень при перечитывании настроек.
Уровень читается без учёта регистра (`INFO`, `warning`→`warn`), нормализуется к
канонической форме. Формат строки — `bms-proxy: <дата> <время> <LEVEL> <текст>`
(стандартные флаги `log`); переходы состояний и события порта/протокола —
`info`/`warn`, «шумные» периодические обновления списка живых BMS и поштучные
запросы/ответы — `debug`.

### Третье состояние C — «Остановлен»

Помимо A (поиск) и B (обновление списка) есть третье состояние:

- Если параметр **«Включено» = выключено**: основной процесс **останавливает
  горутину-слушателя** (если была) и переходит в состояние **C**.
- В состоянии C демон **ничего не делает** — не ищет порт, не читает shm, не
  обновляет список. Крутит **цикл с длительным сном**, ожидая сигнал **перечитать
  настройки** (команда `reload` по control-socket).
- **C → A**: после `reload`, если «Включено» стало = да → считываем настройки и
  уходим в поиск порта (§6).
- Если после `reload` «Включено» по-прежнему = нет → остаёмся в C, продолжаем спать.

Переходы состояний:

```text
C (выключен, длинный сон) --reload + Включено--> A (поиск порта)
A --наш порт--> B (обновление списка, горутина-слушатель)
B --слушатель 5 с молчит--> A
B --reload + смена baud/адресации--> A (перезапуск слушателя, порт заново)
B/любое --reload + Выключено--> C (остановить слушателя, длинный сон)
```

## 10. Источник-образец (референс)

`tools/seplos_bms_server.py` (проект `sunReceiver`) — **рабочий** мост, который
инвертор опрашивает сегодня. Это эталон протокола и логики ответа; наше
`bms-proxy` делает то же самое, но **на Go**, читает данные из shm `bms-reader`
(а не с `read_bms.php`) и работает **последовательным портом** вместо **UDP**.

Что берём как образец:

- **Протокол — PACE / YD-T1363.3 (ASCII-hex, формат SEPLOS):**
  - запрос: `~ 20 <ADR> 46 42 E002 <NN> <CHK> CR`;
  - ответ: `~ 20 <ADR> 46 <RTN> <LEN> <INFO…> <CHK> CR`;
  - `CID1=0x46`; запрос телеметрии `CID2=0x42` (TeleMeter) — единственный
    обрабатываемый;
  - `RTN=0x00` ok / `RTN=0x01` ошибка;
  - `LEN` — 16-бит: `LCHKSUM<<12 | LENID` (LENID = длина INFO в hex-символах).
- **Проверка** `CHK` (дополнение суммы ASCII-кодов строки `VER..INFO` до `0xFFFF`)
  на запросе и самопроверка на собранном ответе.
- **Сборка INFO — TeleMeter `0x42`, 75 Б** (раскладка сверена с официальной
  картой производителя `16S_V20_ADDR` — первоисточник `energybms/protocol-485.md`
  §5 и декодер `energybms-editor/telemetry.py`):

  | Смещ | Поле | Масштаб | Источник (bmscontract) |
  |---|---|---|---|
  | 0 | `dataflag` | — (=0) | конст. |
  | 1 | командная группа/адрес пака | — (=`0x01`, как в эталоне) | конст. |
  | 2 | cell count | — | `CellCount`, при 0 — по последней ненулевой `CellsMV` |
  | 3..34 | ячейки 1..16 | ×0.001 В (мВ) | `CellsMV` |
  | 35 | temp count | — | `TempCount` |
  | 36..47 | темп. 1..4, среды, силовой | ×0.1 К, −273.1 | `TempsDC` (+2731) |
  | 48 | ток (s16, − = разряд) | ×0.01 А | `−CurrentDA` |
  | 50 | напряжение сборки | ×0.01 В | `TotalCV`, при 0 — сумма ячеек |
  | 52 | остаточная ёмкость | ×0.01 А·ч | `RemainingMAh`/10 |
  | 54 | field count / customerp | — (=`0x00`, как в эталоне) | конст. |
  | 55 | полная ёмкость | ×0.01 А·ч | `RatedMAh`/10, при 0 — `CapMAh`/10 |
  | 57 | SOC | ×0.1 % | `SocDP` |
  | 59 | номинальная ёмкость | ×0.01 А·ч | `RatedMAh`/10, при 0 — `CapMAh`/10 |
  | 61 | циклы | ×1 | `Cycles` |
  | 63 | SOH | ×0.1 % | `SohDP`, при 0 — 1000 (100 %) |
  | 65 | напряжение клемм | ×0.01 В | `PortCV`, при 0 — `TotalCV` |
  | 67..74 | temp-drift / zero-point / энергии | ×0.001 А, ×0.1 кВт·ч | **нет данных → 0** |

  Знак тока: контракт «разряд +»; SEPLOS «− = разряд» → знак инвертируется.
- **Поведение при недоступности:** в образце — ответ-ошибка (`RTN≠0`, пустой
  INFO). У нас **намеренное отличие**: при отсутствии запрошенной BMS прокси
  **молчит** (§5/§7), кадр ошибки не отправляется.
- **Кэш/логика** в образце заточена под «ровно 2 BMS» и блоки 1..3 (EnBMS из
  Redis) — нам **не нужна**: у нас адресация по номеру BMS (`0..15` или `1..16`,
  §8) и один
  источник (shm `bms-reader`).

Файл: `../sunReceiver/tools/seplos_bms_server.py` (относительно `docs/`).

## 11. Границы ответственности

- Прокси **не** опрашивает BMS, **не** знает типы `AntBMS-DSP`/`EnBMS-RS485`.
- Прокси **не** пишет в shm и **не** меняет контракт `bms-reader`.
- Прокси отдаёт телеметрию **по номеру из своего живого списка** (`0..N-1`),
  который запросил инвертор; стабильные идентификаторы не выдаёт (серийник —
  справочное поле).
- Порог живости 2 с — контракт прокси: если свежих данных нет, соответствующая
  BMS не попадает в список, а на запрос по отсутствующему номеру прокси **молчит**
  (см. §5/§7).

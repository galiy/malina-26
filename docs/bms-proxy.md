# БМС-Прокси: требования

> Статус: **каркас требований, реализация — по отмашке.**
> Документ фиксирует назначение, источник данных и алгоритм получения
> списка живых BMS. Контракт отдачи и внутреннее устройство — открытые вопросы
> (см. §6).

## 1. Назначение

`bms-proxy` — компонент, отдающий **внешнему потребителю** нумерованный список
**живых** BMS-устройств, собранных демоном `bms-reader`. Прокси не опрашивает
BMS сам, не знает протоколов типов и не пишет в телеметрию — он читает уже
подготовленный бинарный контракт `bms-reader` из POSIX shared memory и
транслирует его в простой нумерованный список.

Цель — дать потребителю «плоский» срез: «вот N живых BMS, вот их номера
`0..N-1`», не заставляя его разбираться в раскладке shm, генерациях, слотах и
решённой на стороне `bms-reader` диагностике живости.

## 2. Источник данных

- Сегмент: `/dev/shm/malina-bms-state`.
- Магия: `0x424D5342` (`"BSMB"`), версия `1`.
- Раскладка (синхронизирована с `daemons/bms-reader/shm.go` и
  `web/internal/web/bmsstate.go`):

  ```
  [header 64 Б][list: 16 записей × 200 Б][slots: 16 × (32 + 112 Б)]
  ```

- Реестр (`Items`) — по одному на слот: метаданные устройства
  (`id`/серийник `BASE-NNNNN`, `base`, `source`, `type_id`, `state`, `framing`,
  `gen`, `last_seen`).
- Телеметрия (`Slots`) — бинарный payload `bmscontract.Size` (107 Б), доступен
  по индексу слота при `state==1` и совпадении `gen`.

Реестр пишется **только** оркестратором `bms-reader` (архитектура §12), телеметрия
— пулером. Прокси — сторонний читатель, на запись не претендует.

## 3. Смещения записей реестра (200 Б)

| Поле | Смещение | Размер | Тип |
|---|---|---|---|
| `seqlock.state` | 0 | 4 | uint32 (1 = занят) |
| `seqlock.seq` | 8 | 8 | uint64 (bit0 = идёт запись) |
| `id` / серийник | 16 | 50 | строка, `BASE-NNNNN` |
| `base` | 66 | 50 | строка |
| `source` | 116 | 64 | строка |
| `type_id` | 180 | 1 | uint8 |
| `state` | 181 | 1 | uint8 (0 = lost, 1 = ok) |
| `framing` | 182 | 1 | uint8 |
| `gen` | 184 | 8 | uint64 LE |
| `last_seen` | 192 | 8 | uint64 LE (unix, секунды) |

## 4. Определение «живой» BMS

Живой считается BMS, **теледанные которого обновлены не позже 2 секунд назад**,
то есть:

```
живой ⇔ (state == 1) И (now − last_seen ≤ 2 с)
```

Пояснение:

- `state == 1` (слот занят) — необходимое, но **не достаточное** условие с точки
  зрения живости: `bms-reader` держит запись в реестре с `state==1` какое-то
  время после потери связи, пока `loseDevice` не освободит слот по
  `MissThreshold` (см. `daemons/bms-reader/orchestrator.go:382`).
- Решающий признак — свежесть `last_seen`: heartbeat публикуется пулером для
  каждого успешного опроса (`orchestrator.go:371`).
- Порог **2 с** — жёсткий, входной параметр по умолчанию; опрос идёт раз в
  секунду, поэтому 2 с = «пропущен не более одного цикла опроса».

## 5. Алгоритм получения списка живых BMS

Псевдокод `aliveBmsList(shmPath)`:

```text
data = read(shmPath, 0, 64 + 16*200)
если len(data) < 64: вернуть []
если data[0:4] != 0x424D5342 или data[4:8] != 1: вернуть []   # магия/версия

out = []; seq = 0
для i в 0..15:
    b = data[64 + i*200 : 64 + i*200 + 200]
    если b.seqlock.state != 1: continue              # слот свободен
    если b.seqlock.seq & 1: continue                 # seqlock: идёт запись
    если b.state != 1: continue                      # state=0 → lost
    если now - b.last_seen > 2 c: continue           # не живая
    out.add({seq, slot: i, gen: b.gen, serial: b.id, last_seen: b.last_seen})
    seq = seq + 1
вернуть out
```

Свойства:

- **`seq`** — порядковый номер `0..N-1` **только по живому подмножеству**.
- **`slot`** — физический индекс слота shm (он же `id` в контракте): по нему
  читается `gen` и payload (107 Б).
- **Нестабильная нумерация**: при выпадении/возврате устройства номера `seq`
  сдвигаются. Это принято — стабильный ключ потребителю не нужен; маппинг
  `seq ↔ slot` актуален только в рамках одного вызова `aliveBmsList`.
- Целостность чтения — `seqlock` (чет-нечет + bit0); при незавершённой записи
  запись пропускается и читается заново на следующем вызове.

## 6. Открытые вопросы (до реализации)

- [ ] Контракт отдачи прокси потребителю (HTTP-эндпоинт, SNMP-таблица, свой
  shm/поток) — не выбран.
- [ ] Какая часть контракта BMS нужна потребителю: только список или ещё payload
  (107 Б) на каждую живую.
- [ ] Формат нумерации: `0..N-1` либо `1..N` (в требованиях — от 0).
- [ ] Жизненный цикл прокси (демон `systemd` / встраивание) и место запуска.
- [ ] Формат `last_seen` (unix-сек) и порога 2 с как конфигурируемой величины.

## 7. Границы ответственности

- Прокси **не** опрашивает BMS, **не** знает типы `AntBMS-DSP`/`EnBMS-RS485`.
- Прокси **не** пишет в shm и **не** меняет контракт `bms-reader`.
- Прокси **не** выдаёт стабильные идентификаторы (серийник доступен как
  справочное поле `serial`, но не является ключом).

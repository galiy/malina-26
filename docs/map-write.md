# Запись в МАП через map-reader — требования (черновик)

Статус: **требования согласованы; базовая реализация сделана** — native (Микроарт)
полностью; Modbus — команды (0x06) и выровненные блоки (0x10, чётный адрес +
чётная длина), нечётные блоки отклоняются (§6).
Источники: `docs/map-reader.md`, `docs/map.md`, `docs/map-contract.md`,
`protocol_MAP_cells_2026_07_15.doc`, референс `sunReceiver/docs/map/mapread/mapread.py`.

## 1. Область задачи

- Обсуждаем **только `map-reader`**. Команда приходит по Unix-сокету
  `/run/malina-map/control.sock` (как `ping`/`list`). Клиенты (web, внешние) —
  отдельно, в этой задаче не рассматриваются.
- **Одна команда — запись в одно устройство.** Цель задаётся уникальным
  идентификатором из `map-list` (`id` слота + `gen` — защита от переиспользования
  слота).
- Команда может содержать **несколько операций** записи, выполняемых
  последовательно (разные адреса, EEPROM и/или RAM).

## 2. Протокол записи

Протокол выбирается по режиму пулера для конкретного МАП; **логическая
последовательность записи одинакова** для native и Modbus.

- **Нативный Микроарт:** посылка `w P A1 A0 D0..Dp S \n`; ответ `o S \n`
  (подтверждение, `S=0x91`) или `e D S \n` (ошибка, код `D`). Побайтовое эхо,
  экранирование (`\n`→`0xDB 0xDC`, `0xDB`→`0xDB 0xDD`), `S=0x100−Σ`.
- **Modbus-RTU:** `0x10` — запись нескольких регистров (страница, **чётное**
  число байт, словами); `0x06` — запись одного байта. Для **нечётного** размера —
  `0x10` для чётной части + `0x06` для последнего байта. Байтовый порядок в слове:
  чётный адрес — первый (старший) байт слова, нечётный — второй (младший). Наш
  `modbus.go` читает проводной порядок байт как есть — запись зеркалит его.
- Один запрос — **либо регистры, либо команда**: `reg` **xor** `cmd`. Смешение
  `reg` и `cmd` в одном запросе (в т.ч. при выставленном `no_frame`) — **наша
  ошибка**, в МАП не пишем. Регистры EEPROM и RAM **можно смешивать** в одном
  запросе (обрамление у них одинаковое).
- Область записи: **EEPROM `0x000..0x3FF`** и **RAM `0x400+`**. Ячейки
  **`0x000..0x004` — только чтение** (официально). **Фильтрации ячеек нет** —
  запрет отдаёт сам МАП (ошибку возвращаем как есть).

## 3. Сущности записи и обрамление

1. **Регистр(ы)** — блок `1..256` байт по последовательным адресам от заданного.
2. **Команда** — один байт-команда, записывается по адресу 0 (значения 1..9:
   OFF=1, ON=2, EEPromWR=3, ChargeOFF=4, ChargeON=5, Reset=6, Call_load_EEProm=7,
   StatReset=8, DischOff=9). **В одном запросе допустима ровно одна `cmd`-операция**;
   больше одной (или `cmd` вместе с `reg`) → ошибка (`bad_request`), в МАП не пишем.

**Обрамление служебными командами навешивает демон; клиент его не задаёт:**
- Регистры (EEPROM и/или RAM, **можно смешивать**): `pre = cmd 3`
  (`ComMAP_EEPromWR`) — **перед КАЖДОЙ посылкой записи** (МАП потребляет
  разрешение на одну запись), затем один `post = cmd 7`
  (`ComMAP_Call_load_EEProm`). Проверено на железе: без `pre` запись (и EEPROM,
  и RAM) → `ecode=16`; второй блок без собственного `pre` → тоже `ecode=16`.
- Команда (`cmd`): без обрамления.

**Пример (время МАП):** `_LCD_TimeCyr` (`0x1B6`, EEPROM) и `_TimeCyr_MINUT`
(`0x44B`, RAM) пишутся **одним** запросом — регионы смешивать можно.

**Необязательный флаг клиента «не обрамлять» (`no_frame`):** при его установке
демон **не навешивает обрамление ни для каких адресов**. Для регистров это значит
отсутствие `pre 3` — ответственность клиента (МАП вернёт `map_error` с `ecode=16`).
Правило «либо регистры, либо команда» при `no_frame` **сохраняется**.

## 4. Контракт сокета (проект, финал)

**Запрос** — одна JSON-строка + `\n`:

```json
{"cmd":"write","id":3,"gen":12345,"no_frame":false,"ops":[ ... ]}
```

| поле | тип | обяз. | смысл |
|---|---|---|---|
| `cmd` | string | да | `"write"` |
| `id` | int | да | id слота устройства из `map-list` |
| `gen` | int | да | `gen` слота (защита от переиспользования) |
| `no_frame` | bool | нет (по умолч. `false`) | «не обрамлять» (см. §3) |
| `ops` | array | да | операции; все — одного типа |

Операции:

| op | формат | смысл |
|---|---|---|
| регистр | `{"op":"reg","addr":414,"data":[0,0,130]}` | блок 1..256 байт с адреса `addr`; `addr ≤ 0x3FF` → EEPROM, `addr ≥ 0x400` → RAM |
| команда | `{"op":"cmd","code":7}` | байт-команда по адресу 0; **ровно одна на запрос** |

**Ответ:**
- успех: `{"ok":true}`
- неуспех: `{"ok":false,"code":"<машинный>","error":"<текст>","op":<индекс>,"ecode":<код МАП>}`

| code | когда |
|---|---|
| `bad_request` | невалидный запрос/поля/размер блока/смешение сущностей/`>1` `cmd` |
| `no_device` | `id`/`gen` не найден (устройство ушло или слот переиспользован) |
| `retry_exhausted` | исчерпаны попытки на «невнятной» ошибке / нет ответа |
| `map_error` | явная ошибка МАП (`ecode`, напр. `0x10` — нет разрешения записи) |
| `internal` | внутренняя ошибка |

Ответ — строго success/failure без частичного успеха: сбой любой операции
(после её ретраев) прекращает выполнение, следующие не выполняются (`post` не
посылаем).

## 5. Выполнение

- Команда приходит **в пулер целевого МАП**; пулер **прерывает пулинг** на время
  команды, выполняет запись(и), затем **полный успешный цикл чтения**, публикует
  обновление в **shm до ответа** клиенту (МАП сам меняет зависимые ячейки), и
  возвращается к пулингу.
- **Синхронизация:** доступ к порту — через **мьютекс**; **один write-запрос
  обрабатывается за один цикл пулинга** (пулинг на это время приостановлен).
- **`_put_eeprom` (0x403):** пулер читает её как обычную ячейку и отдаёт в shm в
  общем порядке; **не обнуляет**.
- **Ретраи (для write-запросов):** **5 попыток**, принудительная пауза **0.5 с**
  между попытками. Ретраим «невнятные» ошибки (`ErrRS_sum=1`, `ErrRS_eco=2`,
  `ErrRS_cod=4`) и отсутствие ответа. **Явные** ошибки (например
  `ErrRS_NoEEWR=0x10`) — **без** ретраев, сразу ошибка. Ретраится **каждая
  операция** отдельно, **включая служебные** `pre`/`post`; при исчерпании лимита —
  остальные операции не выполняем.
- **Таймауты:** **эхо — только для microart** (~50 мс); таймаут **ответа** — для
  обоих протоколов (~200 мс).
- **Лимиты блока:** native — до 256 байт (`P=0..255`); Modbus — до 250 байт
  (125 регистров) и с учётом чётности (см. §2).

## 6. Открытые вопросы (Modbus-запись)

Логическая запись — блок `data[0..N-1]` байт с байтового адреса `A`. В native это
одна посылка `w`. В Modbus блок надо выразить словами/регистрами. Ответы ниже
снимаются только на **реальном Modbus-МАП**; до их получения реализация
Modbus-записи не начинается (native-запись не блокируется).

### 6.0. Что уже установлено (закрыто, для контекста)

- Команды: `0x03` — чтение страницы, `0x10` — запись страницы (**чётное** число
  байт, `N = 2P`, `P` — число слов), `0x06` — запись одного байта/слова.
- Адресация **побайтовая**, байтовый адрес передаётся **как есть** (делить на 2
  не нужно).
- Правило позиции байта в слове: слово `W = floor(A/2)`; **чётный адрес — первый
  (старший, первый в кадре) байт слова, нечётный — второй (младший)** (пример
  чтения: `0x400` → первый байт, `0x401` → второй).
- Команда МАП (`1..9`) — `0x06` по адресу `0`, значение в байте слова; для
  регистровой записи — предварительный `0x06` addr0 = `3`, затем запись.
- **Пример записи из док-та (`0x06` по `0x586` со `0x0001`, «данные в младшем
  байте») — игнорируется** как противоречащий правилу чётности (согласовано).

### 6.1. Вопрос 1 — позиция байта в слове для `0x06`

**Формулировка.** При `0x06` по адресу `A` — байт попадает в позицию, выбранную
**чётностью `A`**:

- чётный `A` → первый (старший) байт слова `floor(A/2)`;
- нечётный `A` → второй (младший) байт слова `floor(A/2)`;

**или** МАП **всегда** пишет **младший** байт слова `floor(A/2)`, игнорируя
чётность (как буквально сказано в описании `0x06`: «данные в младшем байте
слова, старший байт игнорируется»)?

**Почему важно.** От этого зависит: корректность одиночных записей, команд
(`0x06` по адресу `0`), и запись «хвоста»/«ведущего» байта блока (см. 6.2).
Плюс — что происходит со вторым байтом слова: сохраняется или обнуляется.

**В чём противоречие.** Описание `0x06` («всегда младший байт») не согласуется с
замечанием о чётности («нечётный адрес → второй байт»): при чётном адресе байт
должен быть первым/старшим, а не младшим.

**Как проверить (на реальном Modbus-МАП):**
1. Записать `0x06` по **чётному** адресу `A` значением `v`.
2. Прочитать `0x03` слово `floor(A/2)` (2 байта) — определить, в какой байт
   попал `v` и что со вторым байтом.
3. Повторить для **нечётного** адреса.
4. Сверить с правилом чётности из 6.0.

**Варианты реализации (по результату):** (i) если чётность учитывается — писать
байт нужным адресом; (ii) если всегда младший — использовать read-modify-write
слова (прочитать слово → заменить байт → записать `0x10`).

### 6.2. Вопрос 2 — `0x10` при нечётном старте и/или нечётной длине

**Формулировка.** Как блок байт выражается словами, если `A` нечётный и/или `N`
нечётное:

1. Можно ли начинать `0x10` с **нечётного** `A`, или требуется выравнивание на
   границу слова (`A` чётный)? Если нельзя — как писать ведущий невыровненный
   байт (одиночным `0x06` по адресу `A`? — зависит от 6.1).
2. Как пары байт объединяются в слова при нечётном старте.
3. Как записать **завершающий нечётный** байт: `0x10` для чётной части +
   `0x06` для последнего байта — по какому адресу и в какой байт слова (зависит
   от 6.1).
4. Проверить допустимость схемы `0x10` + `0x06` и что при нечётной длине
   «середина» пишется корректно.

**Что известно.** Док-т: для `0x10` — «должно быть чётное значение байт», и
разрешена «комбинация `C_wp` и потом `C_w1` для записи последнего нечётного
байта». Про нечётный **старт** — молчит.

**Варианты реализации:**
- (a) ведущий и хвост — одиночными `0x06`, середина — `0x10`;
- (c) read-modify-write граничных слов (не зависит от трактовки `0x06`);
- (b) запретить нечётный старт в Modbus (`bad_request`), в native — без
  ограничений.

**Как проверить (на реальном Modbus-МАП):**
1. Блок с **чётным** стартом и **нечётной** длиной (`0x10` + `0x06`).
2. Блок с **нечётным** стартом (чётная и нечётная длина).
3. После каждой записи — читать `0x03` и сверять с **native**-эквивалентом
   (та же последовательность байт по тем же адресам).

### 6.3. Влияние на требования

- **Реализовано (текущее состояние):** Modbus-команды (`0x06`) и выровненные
  блоки (`0x10`, чётный адрес + чётная длина) — поддержаны; нечётный старт/длина
  и нечётный хвост — отклоняются как `bad_request` до выяснения 6.1/6.2.
- Как получить Modbus-МАП для проверки: переключить `_LCD_RS_Protocol` (значение
  `1`/`2`) у имеющегося МАП, либо использовать отдельный прибор; фиксируется
  отдельным шагом.

  (`docs/api-auth.md`).
- Легаси-путь (`write_eeprom`) не трогаем.

# Сервис записи в МАП — внешнее API (контракт)

Статус: **черновик**. Зона действия документа — «Сервис записи в МАП».
Реализация — в `map-reader`; транспорт — Unix-сокет. **Тот же API** будет
доступен по **HTTP** через web-модуль (`malina-web`).

Связанные документы: `docs/map-write.md` (требования/дизайн), `docs/map-reader.md`
(демон, control-сокет), `docs/api-auth.md` (авторизация HTTP), `docs/map-contract.md`,
`docs/map.md`.

---

## 1. Назначение

Сервис принимает **команду записи в одно устройство МАП**, выполняет её через
`map-reader` (нативный протокол Микроарт или Modbus-RTU — по режиму пулера этого
устройства) и возвращает результат.

- Одна команда = **одно устройство**.
- Внутри команды — **несколько операций** записи, выполняемых последовательно.
- Сервис гарантирует: после ответа `ok:true` данные МАП в **shm** (общий для
  системы источник) **уже обновлены** (выполнен полный цикл чтения).

## 2. Модель устройства (идентификация цели)

Активные МАП публикуются в **`map-list`** (через `map-reader`/shm). Клиент
получает список и адресует запись парой:

- `id` — индекс слота (0..8);
- `gen` — «номер аренды» слота.

`id` сам по себе **не идентифицирует устройство во времени**: слоты
переиспользуются. `gen` увеличивается при каждой новой аренде слота, поэтому пара
(`id`, `gen`) однозначна. Если к моменту выполнения команды `gen` не совпал —
сервис вернёт ошибку `no_device` (устройство ушло / слот занят другим).

## 3. Транспорт A — Unix-сокет (первичная реализация, `map-reader`)

- Путь: **`/run/malina-map/control.sock`** (права `0660`, владелец `root`) —
  для доступа нужен **root/`sudo`**. Тип — Unix-сокет, без токенов.
- Протокол: **одна JSON-строка + `\n`** на запрос; ответ — **одна JSON-строка +
  `\n`**. Одно соединение — один запрос-ответ, синхронно.
- Команды сокета: `ping`, `list`, **`write`**.

Примеры (shell). `socat` на устройстве может отсутствовать — тогда `nc -U`:
```sh
# через socat (если есть)
printf '%s\n' '{"cmd":"write","id":3,"gen":12345,"ops":[{"op":"cmd","code":"07"}]}' \
  | socat - UNIX-CONNECT:/run/malina-map/control.sock

# через nc (OpenBSD/pyc)
printf '%s\n' '{"cmd":"write","id":3,"gen":12345,"ops":[{"op":"cmd","code":"07"}]}' \
  | sudo nc -U /run/malina-map/control.sock
```

## 4. Транспорт B — HTTP (web-модуль `malina-web`)

> **Статус: реализовано.** `POST /api/map/write` в web проксирует в `map-reader`
> через control-сокет. Авторизация — `cookie || Bearer` (см. `docs/api-auth.md`).

Тот же контракт, доступный по HTTP. Web-модуль **проксирует** запрос в `map-reader`
через control-сокет и возвращает тот же JSON-ответ.

Legacy-запись `POST /write_eeprom.php` (`data=[[addr,val],…]`, `addr==0` — команда)
идёт через этот же контракт: авторизация Basic+PAM, исполняется в цикле legacy-модуля
(см. `docs/api-auth.md`, `web/README.md`).

- Метод/путь: **`POST /api/map/write`**.
- `Content-Type: application/json`.
- Тело — **тот же объект**, что и для сокета (поле `"cmd"` можно опускать — его
  задаёт эндпоинт). Размер тела — до 64 КиБ.
- **Авторизация:** cookie-сессия **или** `Authorization: Bearer <token>`
  (единый скоуп) — см. `docs/api-auth.md`. Cookie защищён `SameSite=Lax`.

Маппинг HTTP-статусов:

| HTTP | когда |
|---|---|
| `200` | `ok:true` |
| `400` | `bad_request` (кривой JSON/поля/размер/смешение сущностей) |
| `401` | нет/невалидный/протухший токен (слой авторизации) |
| `404` | `no_device` |
| `422` | `map_error` (явная ошибка МАП) |
| `502` | `retry_exhausted` (устройство не ответило «внятно») |
| `500` | `internal` |

Тело ответа — всегда тот же объект (`{"ok":...}` / `{"ok":false,"code":...}`).

Пример (HTTP):
```
POST /api/map/write HTTP/1.1
Authorization: Bearer <token>
Content-Type: application/json

{"id":3,"gen":12345,"ops":[{"op":"cmd","code":"07"}]}
```

## 5. Запрос

Одна JSON-строка (сокет) / тело (HTTP):

```json
{"cmd":"write","id":3,"gen":12345,"no_frame":false,"ops":[ ... ]}
```

| поле | тип | обяз. | смысл |
|---|---|---|---|
| `cmd` | string | для сокета да; для HTTP опц. | `"write"` |
| `id` | int | да | индекс слота устройства из `map-list` |
| `gen` | int | да | `gen` слота (защита от переиспользования) |
| `no_frame` | bool | нет (`false`) | «не обрамлять» (см. §5.2) |
| `ops` | array | да | операции; все — **одного типа** |

### 5.1. Операции

Все числовые поля — **шестнадцатеричные, без префикса `0x`**; в JSON hex-литералов
нет, поэтому `addr` и `code` — строки, `data` — строка из 2 символов на байт:

| op | формат | смысл |
|---|---|---|
| регистр | `{"op":"reg","addr":"1B6","data":"000082"}` | блок байт с адреса `addr`; `addr ≤ 3FF` → EEPROM, `addr ≥ 400` → RAM; `data` — 1..256 байт (2..512 hex-символов, чётная длина) |
| команда | `{"op":"cmd","code":"07"}` | байт-команда МАП по адресу 0; **ровно одна на запрос** |

Правила (суммарно):

- **Либо регистры, либо команда:** `reg` **xor** `cmd`. Смешение `reg` и `cmd`
  (в т.ч. при `no_frame`) → `bad_request`, в МАП ничего не пишем. Регистры EEPROM
  и RAM **можно смешивать** в одном запросе.
- В запросе типа `cmd` — **ровно одна** `cmd`-операция (больше → `bad_request`).
- Размер одного блока: native — до 256 байт; Modbus — до 250 байт (125 регистров).
- Максимум операций в одном запросе — **64**.

Команды МАП (`code`, hex-строка): `1` OFF, `2` ON, `3` EEPromWR (служебная),
`4` ChargeOFF, `5` ChargeON, `6` Reset, `7` Call_load_EEProm (служебная),
`8` StatReset, `9` DischOff. Служебные `3`/`7` клиент, как правило, не задаёт —
их навешивает сервис (см. §5.2).

**Для smoke-проверки безопасен `7` (`Call_load_EEProm`)** — перечитка настроек
из EEPROM, состояние не меняет. Коды `1/2/4/5/6/8/9` переключают режим/заряд/
сброс/статистику — на живом железе вслепую не посылать.

### 5.2. Обрамление (служебные команды)

Клиент **не задаёт** обрамление — его добавляет сервис:

- **Регистры (EEPROM и/или RAM):** `pre = cmd 3` **перед каждой** записью, затем
  один `post = cmd 7` в конце.
- **Команда (`cmd`):** обрамления нет.

**Флаг `no_frame`:** при `true` сервис **не навешивает** обрамление ни для каких
адресов. Для регистров это значит отсутствие команды разрешения — ответственность
клиента (МАП вернёт `map_error` с `ecode="10"`).

## 6. Ответ

- Успех: `{"ok":true}`
- Неуспех: `{"ok":false,"code":"<машинный>","error":"<текст>","op":<индекс>,"ecode":"<hex>"}`

| код | HTTP | смысл |
|---|---|---|
| `bad_request` | 400 | невалидный запрос/поля/размер/смешение сущностей/`>1` `cmd` |
| `no_device` | 404 | `id`/`gen` не найден (устройство ушло / слот переиспользован) |
| `map_error` | 422 | явная ошибка МАП: `ecode` — hex-код, `error` — формулировка из документации |
| `retry_exhausted` | 502 | исчерпаны попытки на «невнятной» ошибке / нет ответа |
| `internal` | 500 | внутренняя ошибка сервиса |

- `op` — десятичный индекс упавшей операции в `ops` (для `bad_request` может отсутствовать).
- `ecode` — hex-строка кода ошибки МАП (без префикса), только для `map_error`
  (напр. `"10"` = `ErrRS_NoEEWR`); `error` при этом — формулировка из документации,
  для неизвестного кода — `МАП вернул неописанную ошибку 0xNN`.

## 7. Семантика выполнения

- Команда исполняется **в пулере целевого МАП**: пулер **приостанавливает пулинг**
  на время команды, выполняет запись(и), затем **полный успешный цикл чтения**,
  публикует обновление в **shm до ответа** клиенту, и возвращается к пулингу.
- Доступ к порту сериализован (команда исполняется в горутине пулера); обрабатывается **один write-запрос за цикл
  пулинга**.
- **Ретраи** (для write): **5 попыток** с принудительной паузой **0.5 с**.
  Ретраятся «невнятные» ошибки (`1` CRC, `2` нет эхо, `4` неверный код) и
  отсутствие ответа. **Явные** ошибки МАП (напр. `16`) — **без** ретраев.
  Ретраится каждая операция **отдельно**, включая служебные `pre`/`post`.
- **Таймауты запроса:** эхо — только для протокола Микроарт (~50 мс); таймаут
  ответа — для обоих протоколов (~200 мс).
- **Атомарность:** ответ `ok:true` означает, что **все** операции выполнены. При
  сбое любой операции после её ретраев выполнение **прекращается**, остальные не
  выполняются, `post` не посылается, ответ — `ok:false`.
- **Таймаут ответа транспорта** должен покрывать худший случай (несколько
  операций × 5 попыток × (0.5 с + таймаут ответа)); для HTTP-клиента read-timeout
  задавать с запасом.

## 8. Ограничения и особенности

- **Область записи:** `0x000..0x7FF` (EEPROM `0x000..0x3FF`, RAM `0x400..0x7FF`).
  Адрес вне диапазона → `bad_request` («адрес вне области `0x000..0x7FF`»).
  **Фильтрации ячеек нет** — поведение определяет МАП.
- **Ячейки `0x000..0x004` (по железу):** записи формально read-only, но МАП
  реагирует по-разному:
  - `0x000` — принимает `ok:true`, значение **не меняется** (напр. `_Device`);
  - `0x004` — `map_error` `ErrRS_reserve` `ecode="20"`;
  - `0x001..0x003` — не проверено (ожидается отказ `map_error`).
  Проверять поведение по конкретной ячейке — на железе.
- **Modbus:** блок регистров поддержан только с **чётным** адресом и **чётной**
  длиной (fc `0x10`); нечётный старт/длина и нечётный хвост — `bad_request` до
  выяснения байтового порядка (см. `docs/map-write.md`, §6). Команды (`cmd`) —
  через `0x06`, работают. Native (Микроарт) поддержан полностью.
- **Сигнальная ячейка `_put_eeprom` (0x403)** — читается пулером как обычная
  ячейка и отдаётся в shm; сервис её не обнуляет.

## 9. Примеры

**EEPROM-блок (обрамление навешивает сервис):**
```
{"cmd":"write","id":3,"gen":12345,"ops":[{"op":"reg","addr":"19E","data":"000082"}]}
→ {"ok":true}
```

**RAM-блок (обрамление тоже навешивает сервис):**
```
{"cmd":"write","id":3,"gen":12345,"ops":[{"op":"reg","addr":"400","data":"03"}]}
→ {"ok":true}
```

**Часы МАП одним запросом (EEPROM `1B6` + RAM `44B`):**
```
{"cmd":"write","id":3,"gen":12345,"ops":[{"op":"reg","addr":"1B6","data":"4D"},{"op":"reg","addr":"44B","data":"04"}]}
→ {"ok":true}
```

**Команда МАП:**
```
{"cmd":"write","id":3,"gen":12345,"ops":[{"op":"cmd","code":"02"}]}
→ {"ok":true}
```

**Ошибка — смешение сущностей:**
```
{"cmd":"write","id":3,"gen":12345,"ops":[{"op":"reg","addr":"19E","data":"01"},{"op":"cmd","code":"02"}]}
→ {"ok":false,"code":"bad_request","error":"смешение сущностей reg/cmd в одном запросе"}
```

**Ошибка — МАП отклонил запись (нет разрешения, `no_frame` для регистров):**
```
{"cmd":"write","id":3,"gen":12345,"no_frame":true,"ops":[{"op":"reg","addr":"19E","data":"000082"}]}
→ {"ok":false,"code":"map_error","error":"ErrRS_NoEEWR: не было предварительной команды разрешения записи в EEPROM","op":0,"ecode":"10"}
```

**Ошибка — устаревший слот:**
```
{"cmd":"write","id":3,"gen":12340,"ops":[{"op":"cmd","code":"02"}]}
→ {"ok":false,"code":"no_device","error":"устройство не найдено (несовпадение id/gen)"}
```

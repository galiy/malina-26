# BMS-Receiver: контракт телеметрии и общие циклы

**Статус:** рабочая часть (не заморожена). **Архитектура** — отдельный
замороженный документ `docs/bms-reader-arch.md` (изменения — только по явному
разрешению автора). **Типы BMS** — `docs/bms/`.

**Связанные документы:** `docs/bms-reader-arch.md` (архитектура),
`docs/bms/README.md` (проекты-источники и индекс типов), `docs/bms/<TYPE>.md`
(контракты типов, мэппинг, probe/опрос).

**Идентификатор устройства:** `ID = BASE` (без суффикса `-NNNNN` и без реестра
`bms-ident.json`). BASE формирует probe: EnBMS — аппаратный SN, AntBMS — ёмкость.
Уникальность BASE не гарантируется: несколько BMS с одинаковым BASE дают один
`device_id` и один ряд в tsdb (принятый риск; уникальность обеспечивает
пользователь). `slot`/`gen` — только для чтения текущей телеметрии.

---

## 1. Общий контракт телеметрии BMS

**Контракт бинарный, фиксированной длины. Максимум ячеек — 16.** Никаких
переменных (динамических) массивов: набор полей и их смещения фиксированы для
всех типов BMS; число значащих элементов задаётся счётчиками (`cell_count`,
`temp_count`), «хвосты» массивов игнорируются. **Знак тока:** разряд «+», заряд «−».

**Тип-специфичные поля и покомпонентный мэппинг** — в `docs/bms/<TYPE>.md`
(индекс типов — `docs/bms/README.md`).

### Раскладка (многобайтовые — big-endian, выравнивания нет)

| Offset | Размер | Поле | Тип | Ед. | Смысл |
|---|---|---|---|---|---|
| 0 | 1 | `cell_count` | u8 | — | число значащих ячеек (1..16) |
| 1 | 1 | `temp_count` | u8 | — | число значащих датчиков T° |
| 2 | 2 | `flags` | u16 | биты | b0 `charge_mos`, b1 `discharge_mos`, b2 `balancer` |
| 4 | 32 | `cells_mv[16]` | u16×16 | мВ | напряжения ячеек |
| 36 | 16 | `temps_dc[8]` | i16×8 | 0.1 °C | температуры |
| 52 | 4 | `current_da` | i32 | 0.01 А | ток (разряд +) |
| 56 | 4 | `power_w` | i32 | Вт | мощность |
| 60 | 2 | `soc_dp` | u16 | 0.1 % | заряд |
| 62 | 2 | `soh_dp` | u16 | 0.1 % | здоровье |
| 64 | 4 | `cap_mah` | u32 | 0.001 А·ч | полная/номинальная ёмкость |
| 68 | 4 | `remaining_mah` | u32 | 0.001 А·ч | остаток |
| 72 | 4 | `rated_mah` | u32 | 0.001 А·ч | rated-ёмкость |
| 76 | 2 | `cycles` | u16 | — | число циклов |
| 78 | 2 | `total_cv` | u16 | 0.01 В | напряжение сборки |
| 80 | 2 | `port_cv` | u16 | 0.01 В | напряжение клемм |
| 82 | 4 | `balance_mask` | u32 | — | битовая маска балансировки |
| 86 | 2 | `mode` | u16 | enum | режим: **младший байт — код**, старший — резерв (0) |
| 88 | 19 | `alarm` | bytes[19] | битфилд | тревоги/защиты; раскладка — по типу (`docs/bms/<TYPE>.md`) |

**Фиксированный размер записи — 107 байт.**

### Замечания

- «Необязательность» отдельных полей выражается **отсутствием смысла** (0 / 0xFFFF-
  sentinel для целочисленных), а не переменной длиной: раскладка одна на все типы.
- **Производные по ячейкам** (max/min/avg напряжения и их индексы) в записи **не
  хранятся** — вычисляются потребителем по `cells_mv[0..cell_count-1]`.
- `temps` — ёмкость 8 (макс); при `temp_count < 8` значащи первые `temp_count`.
- Тип-специфичное в контракте: **только `alarm`** (битфилд тревог/защит, раскладка — по
  типу); `mode` — **канонический** (общий). Остальные поля типов — **вне контракта**:
  `model` — только для probe/ID; `cycle_ah`, `uptime_s`, MOS-напряжения, `customerp`,
  `keys`, `balance_cells` — отказ (дублируют ядро либо низкая ценность).

### Решено

- **Разрядности/единицы** (таблица выше) — подтверждены; **отличий по разрядностям между
  AntBMS и EnBMS нет** (различаются лишь набор полей — отсутствующие заполняются
  сентинелом — и единицы источника, которые приводятся к контракту).
- **Порядок байт** — **big-endian** (сетевой порядок; как в протоколах проекта).
- **Максимум температур** — **8** (с запасом).
- **`mode`** (младший байт) — **канонический enum** (см. ниже); типы мэппят источник на
  канон (EnBMS — `Mode_Byte`, AntBMS — по знаку тока).
- **tsdb:** единая схема **`bms` v1** (union, `(bms, version)`); ячейки/температуры —
  **отдельными колонками** (`cells_1..16`, `temps_1..8`).
- **`alarm`** — фиксированный битфилд **19 байт (152 бита)**; раскладка по типу
  (AntBMS: 28 бит — коды MOS + `system log`; EnBMS: 147 бит — ячейки 64, температуры
  32, одиночные warn 4, `Ext_Bit` Byte0..5 = 47). Незначимые биты — `0`. `bms_type` в
  контракт **не входит** (тип — из shm-списка).

### Канонический `mode` (enum)

Общий для всех типов; код — в младшем байте `mode`:

| Код | Режим |
|---|---|
| `0x00` | Ожидание / standby |
| `0x01` | Разряд |
| `0x02` | Заряд |
| `0x03` | Поддержание |
| `0x04` | Полный заряд |
| `0x05` | Выключение |

Типы мэппят свой источник на канон (см. `docs/bms/<TYPE>.md`); в контракт пишется канон.

### Следствие: реестр типов у потребителя

`alarm` остаётся **тип-специфичным** по раскладке (AntBMS 28 бит / EnBMS 147 бит), поэтому
потребитель (web/UI, аккумулятор) ведёт **реестр «typeId → раскладка alarm»** (тип — из
shm-списка). `mode` — канонический, доп. реестра не требует.

### Два представления (не путать)

- **Бинарный контракт 107 Б (big-endian)** — **shm-снимок телеметрии слота** (per device),
  читает `malina-web` через **`/api/bms/raw`** (аналог `map-contract`/`kes-contract`);
  пишет **пулер**.
- **tsdb-схема `bms` v1 (`field_id` 1..58)** — **raw/avg** через **`tscontract`**
  (presence-bitmap + varint/LE); публикация `stat.Publish` как у `map-reader`/`kes-reader`.
- **Пулер даёт два выхода:** бинарный 107 Б → **shm** (телеметрия слота);
  `tscontract` (`field_id`) → **raw** tsdb.
- В **shm** также **список** (метаданные: `base, id, typeId, gen, lastSeen, source, state,
  framing`) — пишет оркестратор (`docs/bms-reader-arch.md` §12).
- Обе формы несут **одну семантику**; соответствие «раскладка ↔ `field_id`» — по таблицам
  ниже.

### tsdb-схема `bms` v1: поля и агрегация

`(device_type = bms, version = 1)`. Полный упорядоченный реестр (`field_id`, тип, агрегация):

| field_id | Поле | Тип | Ед. | Агрегация (avg-бакет) |
|---|---|---|---|---|
| 1 | `cell_count` | u8 | — | last |
| 2 | `temp_count` | u8 | — | last |
| 3 | `flags` | u16 | биты | **OR** |
| 4..19 | `cells_1..16` | u16 | мВ | avg |
| 20..27 | `temps_1..8` | int | 0.1 °C | avg |
| 28 | `current_da` | int | 0.01 А | avg |
| 29 | `power_w` | int | Вт | avg |
| 30 | `soc_dp` | u16 | 0.1 % | avg |
| 31 | `soh_dp` | u16 | 0.1 % | avg |
| 32 | `cap_mah` | int | 0.001 А·ч | last |
| 33 | `remaining_mah` | int | 0.001 А·ч | avg |
| 34 | `rated_mah` | int | 0.001 А·ч | last |
| 35 | `cycles` | u16 | — | last |
| 36 | `total_cv` | u16 | 0.01 В | avg |
| 37 | `port_cv` | u16 | 0.01 В | avg |
| 38 | `balance_mask` | int | — | **OR** |
| 39 | `mode` | u16 | enum | last |
| 40..58 | `alarm_1..19` | u8 | биты | **OR** |

- **`alarm`** — 19 колонок `u8`, агрегация **побитовое ИЛИ** за бакет (как `Relay` в
  `map` v2, `docs/stat.md`); хранится и в raw, и в avg.
- **`flags`** (incl. `balancer`) и **`balance_mask`** — **OR** (факт активности за бакет,
  как `Relay`); **`mode`** — `last` (текущий режим). Т.е. факт балансировки в бакете
  отражают `flags.balancer` и `balance_mask`.

## 2. Общий цикл probe

- Оркестратор **открывает источник и задаёт транспорт/скорость**; probe получает
  **уже открытый источник** и сам порт не открывает и скорость не меняет.
- Probe-функции типов вызываются **последовательно** (набор типов, на каждой
  скорости — свой проход; см. `docs/bms-reader-arch.md` §6.1/§8).
- Результат **одного** probe: `Found` | `NotMine` | `NoAnswer`.
- **`NotMine` не банит и не останавливает последовательность**: устройство может
  опознать **другой** probe (другое семейство/диалект). Продолжаем.
- Решение **оркестратора** — после всей последовательности:
  - есть `Found` → устройство наше (регистрация, `docs/bms-reader-arch.md` §6.1);
  - нет `Found`, но есть `NotMine` → **бан 5 мин** (чужое устройство: семейство
    ответило, но ни один probe не признал);
  - только `NoAnswer` → отстойник (backoff-лестница 15 с → 5 мин).
- Критерии `Found`/`NotMine` для конкретного типа — в `docs/bms/<TYPE>.md`.

## 3. Пулер: перебор слотов и вызов модуля

- Пулер закреплён за **одним источником** (шиной).
- **Итерирует слоты** источника (адреса, напр. `0..15`) **последовательно**.
- На каждый слот вызывает **модуль телеметрии того типа**, что закреплён за слотом,
  передавая ему **источник + адрес слота**.
- Модуль возвращает **контракт (телеметрию)** либо **«слот потерян»**; ID/BASE присваивает оркестратор по результату probe.
- Пулер пишет payload телеметрии в tsdb и шлёт оркестратору heartbeat `lastSeen`.
- **Пассивная шина** (одно вещающее устройство, без адресации) — отдельная
  горутина-слушатель, без перебора слотов.
- Цикл 1 с, сон между опросами, порог потери — `docs/bms-reader-arch.md` §7/§10;
  команды слота — в `docs/bms/<TYPE>.md`.
- **Serial-чтение — пакетное:** `lib/transport.Port.Read` делает один
  `syscall.Read` на доступную пачку (до `len(buf)`), дедлайн — через `select`.
  fd открыт `O_NONBLOCK`, ожидание — `select`; `VMIN=1/VTIME=0` выставлены как
  raw-настройка и при `O_NONBLOCK` не управляют ожиданием. Это сокращает число
  `syscall.Read`/холостых пробуждений; влияние на bulk-IN/IRQ
  **не измерялось** — критерии `review/kworker-fix.md` §5 проверяются на `.68`
  после выкладки. `readAntFrame`/`readPace` не меняются.
- `ttyUSB3` по логам `.68` — EnBMS-RS485 (PACE), рабочий источник телеметрии;
  опрос 1 Гц сохранён, порт не отключается.

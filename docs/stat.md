# Хранение статистики по устройствам

Документ определяет **контракты телеметрии** устройств (МАП/КЭС) для хранилища
рядов `daemons/tsdb`. Два уровня (`docs/telemetry-store.md` §14): **raw** пишут
**пулеры** (`map-reader`/`kes-reader`) как сырьё 1 Гц; **avg** — **аккумулятор** в
`malina-web` усредняет raw за период (кратный минутам 1, 2, 3, 4, 5, 6, 10) и пишет в
persist.
Механика хранилища, раскладка, версии, проекция — `docs/telemetry-store.md`
(§5, §8, §10); здесь — только **состав полей контрактов и их типы**.

## Соглашения

- Строка статистики = **снапшот всех полей устройства** за интервал; усреднение
  делает **аккумулятор** (`web`), хранилище раскладывает поля на колонки по реестру
  версий `(device_type, version)` (`docs/telemetry-store.md` §1.2, §5, §8).
- У каждого типа устройства — **своя нумерация версий** и свой состав полей
  (`map`: v1/v2/v3, `kes`: v1, `mbms`: v1..v32), независимо
  (`docs/telemetry-store.md` §1.2).
- **Значения — сырые** (как в `map-contract.md`/`kes-contract.md`); физический
  пересчёт — только на отображении, в контракт не входит.
- Поля, **не меняющиеся во времени** (паспорт, уставки/настройки), в ряд **не входят**.
- Типы полей: `u8`, `u16` (little-endian) — соответствуют исходным типам ячеек.
- **Контракт описывает поля и их типы**, а не «сырость» значений: одна и та же схема
  используется и в **raw** (сырьё 1 Гц), и в **avg** (усреднённые) — это **разные серии**
  с разной семантикой значений (raw/avg — `docs/telemetry-store.md` §14). «Значения
  сырые» означает «без физического пересчёта», а не «мгновенные».

## Общий пакет контрактов

Схемы и кодеки — общий Go-пакет **`daemons/lib/tscontract`**
(`github.com/galiy/malina-26/daemons/lib/tscontract`), импортируемый и хранилищем
(`daemons/tsdb`), и продюсерами (пулеры `map-reader`/`kes-reader` — сырьё; аккумулятор
в `malina-web` — усреднение): обе стороны обязаны кодировать
`payload` одинаково. Реестр ключуется парой `(device_type, version)`;
`NewDefaultRegistry()` возвращает реестр с `map`/`kes`/`mbms`/`bms`/`grid`.

# Контракт телеметрии МАП (map v1/v2/v3)

Контракт `map` v1 — **сырые данные регистров МАП**, без пересчёта/шкалирования
(значения пишутся как есть; физический пересчёт — только на отображении, в
контракт не входит). Снапшот — **фиксированные 26 колонок**; BMS вынесен в
отдельный тип `mbms` (ниже). Реализуется в хранилище рядов —
`docs/telemetry-store.md` (§5, §8, §10).

## Оценка объёма строки

26 фиксированных колонок: 4 × `u16` (`PNET`,`PLoad`,`UAcc_med`,`IAcc_med_A_u16`) =
8 Б + 22 × `u8` = 22 Б = **30 Б** на строку.

## map v2 — добавлены реле

`map` v2 = v1 + **одно поле** `Relay` (`id 27`, тип `u8`): состояние реле МАП,
источник — ячейка `Status_RELEdop` (`0x586`), `бит0/1/2 = реле 1/2/3` (как в панели 1
`map.js`). UI **разворачивает битфилд в 3 колонки** `Relay1/2/3` (значения `0`/`1`).

Публикуется пулером `map-reader` (`daemons/map-reader/publish_raw.go`, `buildMapV2`);
потребители (хранилище/аккумулятор/UI) различают версии по полю `version` строки.
Граница перехода v1→v2 допустима внутри одной серии (разные версии — разные
блоки/строки, `docs/telemetry-store.md` §1.2). Усреднение: `Relay` — по правилу
«ИЛИ» (`docs/accumulator.md` §5).

## map v3 — частота выхода и MPPT (план, для графиков)

`map` v3 = **v2 + поля**:

| id | Поле | Тип | Ед./смысл |
|---|---|---|---|
| 28 | `ThFMAP` | `u8` | частота на выходе, `6250/значение` (Гц) |
| 29..32 | `I_Akb_MPPT0..3` | `u16` | ток канала MPPT (А); суммарный ток MPPT = **сумма** (на клиенте) |
| 33 | `PNET_Sign_P` | `u8` | флаг знака мощности сети (`0` → `Pnet` отрицательна; иначе «+») |

Первые **4 канала** MPPT — **ограничение реализации** (полный набор до 16 — если
понадобится позже). Из-за этого суммарный ток MPPT **в графиках** (по `map v3`, 4
канала) может быть **меньше**, чем в событиях/legacy (`imppt`, до 16) для устройств
с >4 каналами (осознанно, `docs/ui-stat.md` §3.2).

Нужна для графиков МАП (`docs/ui-stat.md` §3.2: «Частота на выходе», линии MPPT в
«Токах»/«Мощностях»).

**Влияние на «Таблицы» (`docs/ui-stat.md` §4.3):** при переходе на `map v3` в таблице
появятся **новые колонки** — `ThFMAP` (Гц) и `I_Akb_MPPT0..3` (А; первые 4 канала);
к каждой —
**заголовок** (имя поля как есть), **единица** (`measure.Freq6250` → «Гц»,
`measure.MpptCurrent` → «А») и **описание-хинт** (ключ `stats.f.map.<имя>` во всех
8 языках). Разделение версий в периоде — по колонке «версия» (§4.3).

Реализация — по отмашке (публикация в `map-reader`, версия `3`; `units.go`/i18n).

# Контракт телеметрии BMS (mbms v1..v32)

Статистика BMS хранится **отдельным типом устройства** `mbms`, не в ряду МАП;
идентификатор устройства — **тот же серийник, что у МАП**. Запросы по МАП и по его
BMS — **раздельные** (составной запрос не нужен). См. `docs/telemetry-store.md`
§1.5 (набор типов открыт), §4.

Число ячеек жёстко задаёт контракт: для `n` ячеек (1..32) — версия `Vn`
(`V1`..`V32`). Схема ячейки **фиксирована и не меняется**. `Vn` = `n` повторений
ячейки (3·n колонок):

```
ячейка (повтор ×n):
  UakbCell  u16   # L/H: 0x480+2i / 0x481+2i
  TakbCell  u8    # 0x4C0+i
  Q_Cell    u8    # 0x4E0+i
```

Нумерация колонок в `Vn`: ячейка `i` (1..n) → `field_id` `3·(i−1)+1` (`UakbCell`),
`+2` (`TakbCell`), `+3` (`Q_Cell`). `V1` — 1 ячейка (3 колонки), `V32` — 32 ячейки
(96 колонок). Состав полей в версии постоянен, длина строки фиксирована
(колоночные блоки однородны). Число ячеек меняется — пишется соответствующая
версия (`V8` → `V10`); строки разных версий в одном ряду допустимы
(`docs/telemetry-store.md` §1.2, §5).

## Оценка объёма строки (`Vn`)

`n` × (`UakbCell` 2 Б + `TakbCell` 1 Б + `Q_Cell` 1 Б) = `4·n` Б; `V32` → ~128 Б.

Контракт `kes` v1 — **сырые данные ячеек КЭС**, без пересчёта/шкалирования
(физический пересчёт — только на отображении, в контракт не входит). Снапшот —
фиксированный набор из 15 колонок; порядок полей = `field_id` (ключ метрики,
`docs/telemetry-store.md` §5). Адреса ячеек — `docs/kes-contract.md` (§ «KESR»).

10 × `u16` (`VcPV`,`IcPV`,`PPV`,`Windspeed`,`VBat`,`ICh`,`PCurr`,`POut`,`PLoad`,`IOut`)
= 20 Б + 5 × `u8` (`TempBat`,`TempInt`,`Mode`,`RelayC`,`RSErrSis`) = 5 Б = **~25 Б** на
строку.

# Контракт `bms` v1 — описание в одном месте

Полное описание контракта `bms` v1 (раскладка 107 Б, поля `field_id` 1..58, единицы,
агрегация) — **единственный источник: `docs/bms-reader.md` §1**. Здесь (в `stat.md`)
контракт **не дублируется** — только запись в «Реестре версий» выше.

**Идентификатор:** `device_id = BASE` (без суффикса `-NNNNN` и без реестра).
Уникальность BASE не гарантируется: несколько BMS с одинаковым BASE пишут в один
ряд `bms/<BASE>`, raw/avg смешиваются. При инверсии времени между пулерами
tsdb-writer (raw и avg) может отбросить строку (`r.Time < floor`), а не только смешать данные —
это принятый риск; уникальность BASE обеспечивает пользователь.

При миграции одноразово удаляется **весь namespace `bms`** (avg+raw):
`deploy/deploy.sh --purge-bms-history --only bmsr`. Запускать до накопления
новых рядов `bms/<BASE>` — операция разрушающая. После успеха ставится маркер
`.bms-history-purged`; повторный запуск без его удаления пропускает только
удаление, но выполняет деплой/рестарт и проверки.

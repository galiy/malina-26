# КЭС: `kes-reader` — требования (согласование)

Статус: **реализован и задеплоен** (см. `daemons/kes-reader/`, `deploy/`); `web`-модуль
отдаёт часть ручек через legacy-совместимость (`docs/legacy-api.md` §7).
Связано: `docs/kes-memory.md` (карта измерений и **настроек** КЭС, модели),
`docs/kes-contract.md` (бинарный контракт shm/слота),
`docs/map-reader.md`, `docs/map-contract.md`, `docs/events.md` (§11 — заглушки КЭС),
`docs/legacy/kes-legacy-malina2.md` (разбор legacy КЭС из бэкапа `.60`).

## 1. Что делаем

Новый демон **`kes-reader`**: читает один/несколько **КЭС** по **протоколу MicroArt**
(Modbus КЭС **не умеет** — только MicroArt), публикует данные в **shared memory**
(свой сегмент) и ведёт **свой список устройств** (`kes-list`) — по образцу `map-reader`
и `map-list`. Данные КЭС доступны панелям, «Мастер-Узлу» и менеджеру событий.

## 2. Ключевые ограничения

- **Протокол КЭС — только MicroArt.** Никакого Modbus.
- **Железа КЭС нет** → разработка и тесты **без железа**, на программном эмуляторе;
  финальная приёмка — на реальном КЭС (когда появится).
- Общий код с `map-reader` — **обязательно переиспользуем** (без дублирования).

## 3. Общий код (рефакторинг)

Вынести из `map-reader` в общие пакеты (используются и `map-reader`, и `kes-reader`) —
конкретный раскрой, границы и порядок выноса: **`docs/daemons-shared.md`** (единый модуль
`daemons`, пакеты `lib/{transport,microart,shm,control,ports,device}`). Статус:
`transport`, `microart`, `shm` (механика), `control` (каркас), `ports` (примитивы портов),
`device` (коды `_Device`) — **уже вынесены**; `map-reader` переведён без изменения поведения.

- транспорт: открытие serial, RS485-режим, latency/тайминги, ретраи → `lib/transport` ✅;
- протокол **MicroArt**: кадры чтения/записи, эхо, адресация/unit → `lib/microart` ✅;
- **shared memory**: механика сегмента/seqlock (`Segment/Slot/Item`) → `lib/shm` ✅;
- **unix-сокет управления**: каркас `Serve`+JSON → `lib/control` ✅;
- **порты**: `ListPorts/RdevOf/BusyRdevs` (device-agnostic) → `lib/ports` ✅;
- **идентификация**: коды `_Device` (3/5/7/9) → `lib/device` ✅;
- контракт `*-list` (формат полей записи) и оркестрация пробы (**Modbus/скорости**) —
  остаются у демона (MAP-специфика).

Требование: рефакторинг **не ломает** `map-reader` (MAP) — тесты и контракт `map-*`
остаются валидными.

## 4. Контракт КЭС

Полная раскладка бинарного контракта (сегмент, `kes-list`, под-блоки слота
`KESE`/`KESR`/`KESS` с полями и смещениями) — **`docs/kes-contract.md`**; ниже — краткая
версия.

**Источники истины (только два):** `Карта Памяти_MPPT_WG_2021_01_18.xlsx` и наши
подтверждённые ячейки — сведены в **`docs/kes-memory.md`**. Всё непроверенное (карта настроек,
имена из МАП, паспорта, гипотезы) — **`docs/kes-memory-not-accepted.md`**. Дубли ячеек здесь
не храним.

- **Probe:** `_Device (0x0000) == 5` — штатное MicroArt-чтение 1 байта; провал → не КЭС
  (`docs/legacy/kes-legacy-malina2.md` §1a).
- **Контракт списка (`kes-list`):** отдельная **секция того же** сегмента
  `/dev/shm/malina-kes-state` (layout `[header][list][slots]`, `lib/shm/shm.go`), запись 72 Б
  (`id/gen/port/baud/serial/lastSeen` — по образцу `map-list`, поля `model`/`protocol`/`state`
  убраны); серийник `serial` (uint16, как у МАП, `b[28:30]`).
- **Контракт слота (три независимых под-блока по 512 Б, с резервом, `daemons/kes-reader/kes.go`):**
  - **EEPROM** (`"KESE"`, v1) — параметры устройства (паспорт/номинал, адрес «как есть»):
    `Serial`(6:8), `Device`(8), `Pow`(9), `FW`(10), `ModelPow`(11), `ModelVolt`(12),
    `Pic`(13), `Net`(14).
  - **RAM** (`"KESR"`, v1) — служебное (`LastSeen`(6:14)) + телеметрия и BMS/параллельные MPPT
    (адрес = RAM + `0x1F0`): `RelayC`(14), `RSErrSis`(15), `I2CErr`(16), `VcPV..PExts1`(18..48),
    `Mode`(50), `Sign`(51), `MPP`(52), `windspeed`(53–54, u16 LE), массивы BMS/MPPT(55..).
  - **Настройки** (`"KESS"`, v1) — 40 штук, `len×uint16` сырых значений RAM-копий
    (`docs/kes-memory.md` §3, условно подтверждённые).
  Суммарный payload слота = `3 × 512 = 1536 Б` (укладывается в `kesSlotData=16384`);
  поля `Mode`/`Sign`/`MPP`/`windspeed` — `0x2C2`/`0x37A`/`0x379`/`0x3F8`, публикуются и
  отдаются в `read_json?device=mppt` (смещения контракта зафиксированы `TestContractGolden`).
- **Серийник:** `0x2C9` (мл.) + `0x2CA` (ст.), сырое десятичное — `docs/kes-memory.md` §2.
- Поля и адреса ячеек — `docs/kes-memory.md` (§1 — RAM/измерения, §2 — подтверждённые,
  §3 — настройки условно подтверждённые).

## 4.1. Что даёт `docs/map` (сканирование `~/src/sunReceiver/docs/map`)

Просканированы **все** документы папки (не только КЭС/MPPT): `protocol_*_cells_*.doc`,
`protocol_2016/2020.doc`, паспорта МАП/Титанатор (PDF), `malina2.pdf`, `speed.pdf`,
`reverse-firmware/*.md`, `mppt/*.xlsx`, `mapread/`. Извлечённое — `/tmp/kilo/mapscan`.

**Протокол.** КЭС(MPPT) использует **тот же MicroArt-протокол**, что МАП:
`protocol_MAP_cells_2026_07_15` («поддерживается всеми моделями МАП и КЭС(MPPT)»),
`protocol_2020_12_29` (схема `PC → МАП (КЭС)`). Кадр `r/w`+P+A1A0+CRC+`\n`, эхо,
экранирование `0xDB 0xDC`(=LF)/`0xDB 0xDD`(=0xDB), CRC=сумма mod256, дефолт **19200**,
диапазон **19200–115200**, пауза >5с = разрыв.

**Отличия КЭС(MPPT) от МАП (документированы, кандидат в probe):**
- `7 ComMAP_Call_load_EEProm` — **только МАП** (у MPPT настройки вводятся при настройке прибора);
- `8` — у МАП `StatReset` (v≥25.4d), у **MPPT(ИЗУ)** = `Read_EEProm` (EEPROM→RAM);
- `1/2/4/5/9` (ON/OFF/Charge*/DischOff) — **только МАП**.

**Карта КЭС и подтверждённые ячейки** — только в `docs/kes-memory.md`
(неподтверждённое — `docs/kes-memory-not-accepted.md`).

## 4.2. Запись в КЭС (target API)

Реализация — `daemons/kes-reader/write.go`; эталон для МАП — `docs/map-write.md`;
запись/реле legacy — `docs/legacy/kes-legacy-malina2.md` §1c/§5, `docs/kes-memory.md` §4.

**Область.** Только `kes-reader`. Команда — по Unix-сокету `/run/malina-kes/control.sock`
(как `ping`/`list`). Одна команда — запись в **один КЭС** (`id` слота + `gen` из `kes-list`,
защита от переиспользования). **Протокол — только MicroArt** (КЭС Modbus не умеет).

**Суть.** Единственная «запись» — **ячейки**. У КЭС **нет команд** (`op=cmd` 1..9, как у МАП)
и **нет отдельной операции реле**: управление реле **сведено к обычной записи ячейки**
(см. §4.2.5). То есть в целевом API остаётся **только `op=reg`**.

### 4.2.1. Протокол записи

MicroArt: посылка `w P A1 A0 D0..Dp S \n`; ответ `o S \n` (подтверждение) или `e D S \n`
(ошибка, код `D`). Побайтовое эхо, экранирование (`\n`→`0xDB 0xDC`, `0xDB`→`0xDB 0xDD`),
`S = 0x100 − Σ`. Обрамление навешивает демон, клиент его **не задаёт**:

- На **каждую** записываемую ячейку: сначала команда **`3` (`EEPromWR`)** в адрес `0x0000`
  (разрешение записи), затем — **байт(ы) по адресу «как есть»** (без `+0x1F0`).
- **Post-команда не требуется** (в отличие от МАП — нет `cmd 7`).
- Одинаково для **EEPROM** (`<0x400`) и **RAM** (`≥0x400`): разделение — на стороне клиента.

**Область адреса.** Адрес пишется **как есть**: EEPROM `0x000..0x3FF`, RAM `0x400..0x7FF`,
плюс командная ячейка реле **`0x0E3D`** (write-only, **вне** `0x000..0x7FF`). **Фильтрации
ячеек нет** (допустимость адреса — сам КЭС); диапазон `op=reg` — `0x000..0xFFFF`.

### 4.2.2. Сущности записи

- **Регистр(ы)** — блок `1..256` байт по последовательным адресам (`data` — hex,
  2 символа на байт, чётная длина); до `64` операций в одном запросе.
- Команды (`op=cmd`) и отдельная операция реле (`op=relay`) — **отсутствуют** (см. §4.2.5).

### 4.2.3. Контракт сокета

**Запрос** — одна JSON-строка + `\n`:

```json
{"cmd":"write","id":3,"gen":12345,"no_frame":false,"ops":[{"op":"reg","addr":"1B6","data":"000082"}]}
```

| поле | тип | обяз. | смысл |
|---|---|---|---|
| `cmd` | string | да | `"write"` |
| `id` | int | да | id слота устройства из `kes-list` |
| `gen` | int | да | `gen` слота (защита от переиспользования) |
| `no_frame` | bool | нет | «не обрамлять» — **отладочный «сырой» режим**: пред-команда `3` не шлётся, для EEPROM/RAM КЭС запись почти гарантированно вернёт `0x10` (`ErrRS_NoEEWR`). Только для диагностики транспорта, не для боевого пути |
| `ops` | array | да | операции; **все — `{op:"reg",...}`** |

Операции (`op=reg`): `addr` — hex без префикса (`"1B6"`), `data` — hex-строка
(2 символа на байт, чётная длина, 1..256 байт). Числовые поля — **hex без префикса `0x`**.

**Ответ:** успех `{"ok":true}`; неуспех
`{"ok":false,"code":"<машинный>","error":"<текст>","op":<индекс>,"ecode":"<hex>"}`.

| code | когда |
|---|---|
| `bad_request` | невалидный запрос/поля/размер блока/не `op=reg` |
| `no_device` | `id`/`gen` не найден |
| `retry_exhausted` | исчерпаны попытки на «невнятной» ошибке / нет ответа |
| `kes_error` | явная ошибка КЭС: `ecode` — hex-код, `error` — формулировка |
| `internal` | внутренняя ошибка |

`op` — десятичный индекс упавшей операции, `ecode` — hex-код и только для `kes_error`.
Коды MicroArt (общие с МАП): `01`=ErrRS_sum, `02`=ErrRS_eco, `04`=ErrRS_cod,
`10`=ErrRS_NoEEWR («не было предварительной команды разрешения записи в EEPROM»),
`20`=ErrRS_reserve. Неизвестный код: `"КЭС вернул неописанную ошибку 0xNN"`.
Ответ — строго success/failure без частичного успеха.

### 4.2.4. Выполнение

- Команда приходит в **пулер целевого КЭС**; пулер **прерывает пулинг**, выполняет
  запись(и), затем **пробует контрольное чтение и публикацию — best-effort**: до
  `kesPollRetries` попыток; при неудаче пишет только debug-сообщение и всё равно
  возвращает `ok:true` **без публикации** (слот обновится следующим циклом пулинга).
  Затем возвращается к пулингу.
- Доступ к порту сериализован (команда в горутине пулера, через канал команд);
  один write-запрос обрабатывается за один цикл пулинга.
- **Ретраи:** 5 попыток, пауза 0.5 с; ретраим «невнятные» ошибки (`01`/`02`/`04`) и
  отсутствие ответа; **явные** (например `10`) — без ретраев. Ретраится каждая операция,
  включая `pre 3`; при исчерпании — остальные не выполняем. Таймауты: эхо ~50 мс,
  ответ ~200 мс. Лимиты: блок 1..256 байт, ≤64 операций.

### 4.2.5. Реле (сведено к записи ячейки)

- **Состояние** — `Relay_C` (`0x3E3`), байт: **бит0 = реле1, бит1 = реле2, бит2 = реле3**.
- **Запись** — **байт-маска в командную ячейку `0x0E3D`** (write-only, вне `0x000..0x7FF`).
  Это **не команда**, а обычная запись ячейки: `op=reg {addr:"E3D", data:<маска>}` по общему
  пути §4.2.1 (pre `3` + байт as-is).
- **Read-modify-write — на стороне клиента**: прочитать `0x3E3` → выставить/снять бит →
  записать байт в `0x0E3D`. Демон абстракцию «реле» не знает.
- Подтверждено (эмулятор/сниф): `relay=1, on` → в устройство уходит `0x01` в `0x0E3D`.
  ⚠️ **`0x0E3D` требует подтверждения на железе** (в карте `mppt/` не описана).

## 5. Эмулятор (без железа)

Архитектура — `daemons/kes-emu/readme.md`. Кратко:

**Решение:** «настоящий COM-порт» делаем **USB-serial gadget на самом устройстве** (`.60`),
без usbip и без сети:

- `dummy_hcd` + `g_serial` → появляются **`/dev/ttyGS0`** (gadget-сторона) и
  **`/dev/ttyACM0`** (host-сторона, реальный ttyACM).
- **`kes-emu`** — **один процесс**, обслуживает **несколько портов** (старт — **3 КЭС**):
  по одному gadget-CDC-ACM (или PTY) на КЭС; отвечает по **MicroArt** (регистры — сценарий/
  случайно; 3 реле). `kes-reader` читает host-стороны (`ttyACM*`).
- `kes-emu` — отдельная программа (не встроенный `sim`), чтобы гонять ридер максимально
  «по-настоящему». (В прежних версиях дока назывался `kes-sim` — переименован в `kes-emu`.)

**Разведение портов (важно):**
- Скан readers включает `/dev/ttyACM*`, но **не** `/dev/ttyGS0` — gadget-сторону ридеры
  не трогают.
- Host-сторона (`ttyACM0`) от эмулятора **отсеивается probe'ом**: **маркер КЭС — `_Device`
  (0x0000) == 5** (см. §7.6), поэтому `map-reader` отбрасывает порт как «не МАП» (`_Device≠3`),
  а `kes-reader` принимает по `_Device==5`.
- Занятый порт защищён flock (`scan.go`) — два ридера за один порт не борются.

**Запасной вариант (проще, без ядра):** `socat` PTY-пара `/dev/ttyUSBa ↔ /dev/ttyUSBb`
(протокол тестируется полностью, но без USB-слоя). **usbip** — только если появится
физический USB-serial-адаптер на другом хосте; как основной путь не берём.

- Временный `simInjectKesBms` в `map-reader` — **убрать**, когда `kes-reader` станет
  реальным источником данных КЭС/BMS для веб/UI (см. §6 — интеграция). Пока потребитель
  не подключён, эмуляция в `map-reader` нужна стенду.
- Тесты: unit (протокол/парсинг) на эмуляторе; e2e на `.60` с gadget-эмулятором.
- **Устройства эмулятора:** `kes-emu` создаёт в `/dev` симлинки **`/dev/ttyUSB9..11`**
  (PTY; старые битые чистятся); сами device-порты — **`ttyACM0..`** (host-стороны
  gadget-CDC-ACM). Шаблон скана `kes-reader`/`map-reader` — `/dev/ttyACM*`
  (gadget-сторону `ttyGS*` ридеры не трогают).
- **`kes-emu` в деплой не входит:** собирается/ставится вручную на конкретный хост при
  необходимости (dev/test); в образ и `deploy/` не включается (см. `daemons/kes-emu/readme.md` §0).

## 6. Интеграция

- **Native REST (web):** `/api/kes/{devices,raw,write}` (`web/internal/web/kesapi.go`).
  `devices` — список КЭС из `kes-list`; `raw` — бинарный payload слота (id+gen);
  `write` — прокси тела (§4.2.3) в control-сокет `kes-reader` с аудитом `kes_write`.
  Авторизация — cookie-сессия **или** `Bearer` (как `/api/map/*`, `docs/api-auth.md`);
  это нативный контракт без legacy-обвязки и без Basic+PAM.
- Панели (1/2/3), «Мастер-Узел» и менеджер событий — поддержка **источника КЭС**
  (в событиях уже есть тип `kes` с заглушками, см. `docs/events.md` §11).
- Менеджер событий: поля КЭС, реле КЭС (3), режим КЭС — по контракту КЭС.
- **Деплой:** бинарник → `/malina/usr/local/sbin/kes-reader`, юнит `kes-reader.service`
  → `/etc/systemd/system/`; CPU-приоритет как у `map-reader` (`Nice=-5`, `CPUWeight=1000`).
  Включён в общий деплой ПАК (`deploy/manifest.tsv`, `deploy/local/stage2.sh`,
  `deploy/restore.md`); `install.sh` демон точечно ставится отдельно (как `map-reader`).
  **`kes-emu` в деплой не входит** (см. §5) — только dev/test стенд.

## 6.1. Публикация сырья в raw-хранилище (требование)

**Статус:** требования (согласование); реализация — по отдельной отмашке.

- После **каждого цикла** опроса (после обновления shm) пулер **отдаёт raw-снапшот** —
  `{тип, id, время, значения полей}` по контракту `kes` v1 (`docs/stat.md`; RAM-блок
  `KESR`) — в **модуль сохранения** (in-process) и продолжает пулинг. Вызов **простой и
  неблокирующий** (fire-and-forget): **в пулере нет логики окон/ключей/роутинга и
  расчётов**.
- **Куда попадает:** модуль батчит и пишет в **raw-tsdb** (`docs/telemetry-store.md` §14);
  структура хранения — у tsdb.
- Статика (`KESE`) и настройки (`KESS`) не публикуются. **BMS КЭС не публикуется** —
  в контракте и карте памяти КЭС его нет (решено).

### Доработка `kes-reader` (что менять)

- После публикации в shm (каждый цикл) — вызов `stat.Publish("kes", id, time, version,
  payload)`, `payload` через `lib/tscontract` (схема `kes` v1, `field_id`). Модуль
  сохранения — общий с `map-reader` (см. `docs/map-reader.md`, § «Модуль сохранения»).

## 7. Открытые вопросы

1. **Поля контракта** — **все** из карты `sunReceiver/docs/map/mppt` (см. §4).
2. **Адресация** — только MicroArt, **один КЭС на порт** (шины/unit-id нет).
3. **Скорости/тайминги** — тайминги как у МАП (эхо ~50 мс, ответ ~200 мс); **порядок
   скоростей пробы — только legacy-диапазон КЭС** `115200 → 19200 → 57600` (R0/R1/R2,
   дефолт 19200, `9600` у КЭС не подтверждён — не пробуем); общий **бюджет пробы порта —
   `probeDeadline` = 2 с** (как у МАП, чтобы не удерживать порт дольше).
4. **Серийник КЭС — РЕШЕНО:** EEPROM **`0x2C9` (мл.) + `0x2CA` (ст.)**, сырое десятичное — `docs/kes-memory.md` §2.
5. Формат shm/контракта — **`docs/kes-contract.md`** (по аналогии с `docs/map-contract.md`):
   полная раскладка сегмента, `kes-list` и трёх под-блоков слота (`KESE`/`KESR`/`KESS`).
   Краткая версия — §4 здесь; зафиксировано тестом (`kes_test.go`, `TestContractGolden`).
6. **Сигнатура/probe КЭС — РЕШЕНО (дизасм `usbscanner`):** probe = штатное MicroArt-чтение
   1 байта по адресу **`0x0000`**; **маркер КЭС = значение ячейки `0x0000` == `5`**
   (МАП — `3`, зарядник — `7/9`); провал/нет ответа → `0`. Подробности —
   `docs/legacy/kes-legacy-malina2.md` §1a. Осталось принять этот критерий в `kes-reader`
   (`_Device==5`) и в `map-reader` (отвергать `_Device!=3`).
7. **Реле РЕШЕНО:** состояние — `Relay_C` (`0x3E3`, биты 0/1/2 = реле 1/2/3); запись реле —
   отдельная командная ячейка `0x0E3D` (детали — в `docs/legacy/kes-legacy-malina2.md`).
   **Оптимальная разбивка регионов чтения** (минимум страниц ≤240 Б, без слияния удалённых
   кластеров; `адрес_устройства = RAM + 0x1F0`, ID-окно — «как есть») — `daemons/kes-reader/kes.go`:

   | № | devAddr | Длина | RAM (куда) | Что |
   |---|---|---|---|---|
   | 1 | `0x0000` | 156 | `0x000..0x09B` | ID/паспорт (as-is) |
   | 2 | `0x0400` | 185 | `0x210..0x2C8` | настройки + `Mode`(0x2C2) |
   | 3 | `0x04B9` | 240 | `0x2C9..0x3B8` | Serial + измерения |
   | 4 | `0x05A9` | 85 | `0x3B9..0x40D` | реле/знаки/изм. хвост |
   | 5 | `0x0F4A` | 240 | `0xD5A..0xE49` | I2C_Err + BMS |
   | 6 | `0x103A` | 54 | `0xE4A..0xE7F` | BMS/MPPT хвост |

   Итого: **6 страниц, 840 Б** (старая разбивка — 6×~240 Б ≈ 1270 Б и теряла `0xDE0..0xDFF`;
   покрытие всех контрактных адресов зафиксировано тестом `TestWindowsCover`).
   Контракт слота **разделён на три** независимых под-блока — **EEPROM** (`"KESE"`, параметры
   устройства), **RAM** (`"KESR"`, телеметрия + BMS/MPPT) и **настройки** (`"KESS"`, 40 значений
   RAM-копий) — по 512 Б каждый, без перекрытия адресов/отображений (payload 1536 Б).
   (_`windspeed` `0x3F8`, `Mode` `0x2C2`, `Sign` `0x37A`, `MPP` `0x379` — публикуются в RAM-контракте и отдаются в `read_json?device=mppt` (окно №2 расширено до `0x2C8`
   для `Mode`, окно №4 покрывает `0x379/0x37A/0x3F8`)._)

_(решено: КЭС — только MicroArt; **probe: `_Device`(0x0000)==5**; **серийник = `0x2C9`/`0x2CA`**;
один КЭС на порт; скорости как у МАП; эмулятор — USB-gadget на `.60`; лимит КЭС — 32;
один процесс на все порты; реле КЭС 3 шт., биты 0/1/2 в `Relay_C` 0x3E3; запись — только
ячейки (`op=reg`), реле — ячейкой `0x0E3D`. Формат `<id>:<cell>:<value>:<ts>` — **legacy**
`mpptd`, см. `docs/legacy/kes-legacy-malina2.md` §1c/§5; в целевом API его нет.)_

## 8. План (черновой)

1. ✅ Спека: протокол MicroArt + карта регистров КЭС (карта `mppt/`, дизасм `usbscanner`/`mpptd`).
2. ✅ Общий пакет транспорта/протокола/публикации (`daemons/lib`, см. `docs/daemons-shared.md`),
   `map-reader` переведён без регрессий.
3. ✅ `kes-reader` — каркас готов к тестированию на железе (сканирование/проба `_Device==5`,
   опрос окон, shm/`kes-list`, control, запись ячеек (`op=reg`; реле — ячейкой `0x0E3D`),
   ретраи). `kes-emu` — следующий.
4. ⏳ Интеграция в панели/мастер-узел/события + legacy API КЭС (`docs/legacy/kes-legacy-malina2.md`).
5. ⏳ Тесты: unit ✅; e2e на `kes-emu` (`.60`); приёмка — на реальном КЭС.

Связано: артефакты реверса — локально `./disasm` (gitignored, см. `disasm/README.md`).
